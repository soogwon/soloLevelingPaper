[자료·환경 사전 점검 기록](approved-preflight-20261116.md)에 해시와 미확인 항목을 구분한다.

대상은 `synthetic-embedding-v3-reviewed`의 청크 17개·질의 12개다.

## 1. 적용 조건과 판정 구분

- 첫 비교 대상은 **CPU ONNX FP32 대 PyTorch FP32**로 제안한다. INT8/FP16·다른 provider는
  이 수치를 재사용하지 않고, 후보를 실행하기 전에 별도 기준을 합의한다.
- 같은 모델/tokenizer revision·pooling·L2·최대 길이 128·384차원·cosine·고정 입력을 사용한다.
  runtime·runtime 버전·정밀도·산출물 지문 차이는 기록하며 기존 계약 검사를 완화하지 않는다.
- 과거 v1의 cold 30.585~36.187초·warm 1.275~1.759초·RSS 약 1.37 GiB는 배경 관측이다.
  새 자료·공통 v2 절차의 기준선이 아니므로 아래 비율의 분모나 서버 최소 사양으로 쓰지 않는다.
- **호환성**, **운영 채택 가치**, **제품 품질**을 따로 판단한다. 기준선의 검색 실패를 그대로
  보존한 후보는 비퇴행 조건을 만족할 수 있지만 제품 품질을 충족했다고 선언할 수 없다.
- 허용값을 승인하더라도 현재 비교기는 자동 합격을 출력하지 않는다.
  `decision=pending_thresholds`를 유지하며 승인된 기준에 따른 판정 연결은 별도 작업이다.

## 2. A가 승인한 FP32 품질·호환성 기준

아래 필수 수치는 A가 승인한 이번 소규모 FP32 전환 평가의 기준이다. 보편적 허용 오차나 실측으로
입증된 상한이 아니다. 필수 상한을 벗어나면 실패·원인을 기록하며 사후에 값을 넓히지 않는다.
좌표 오차를 주 수치 기준으로 사용하고, 방향 오차·순위는 진단으로 기록해 중복 탈락을 줄인다.
여기서 ‘진단’으로 바꾼 것은 승인 전 제안값뿐이다. 기존 범위·차원·유한성·0벡터·L2 정규화
유효성 검사나 head AND tail 판정은 그대로 유지하며 제품 코드·비교기 코드는 수정하지 않았다.

| 항목 | 수치·단위 제안 | 집계 방식 | 기준의 이유 |
|---|---|---|---|
| 사용자·출처·검색 범위 혼입 | **0건** | 모든 질의·모든 실행의 top_k를 해당 질의의 허용 후보 집합과 대조. 한 건이면 중단 | 평균 회수율이 좋아도 다른 사용자의 근거나 다른 게시본은 허용할 수 없음. 11번은 페이지 전체라 99쪽도 허용 |
| 차원·비유한·0벡터·설정 불일치 | **0건** | 청크와 질의 전체·모든 실행. 기존 유효성 검사 실패 시 비교 무효 | 오염된 입력을 품질 오차로 흡수하지 않음. 기존 L2 검사 허용치 1e-5도 그대로 유지 |
| 청크 벡터 좌표 오차 | 최대 절대 오차 **≤ 1e-4**, 무차원 | 각 청크·각 좌표의 PyTorch/ONNX 차이 중 최댓값. 모든 비교 실행에서 만족 | 평균이 일부 청크의 큰 오차를 숨기지 못하게 함 |
| 청크 벡터 방향 오차 | 최대 cosine distance 기록, **독립 탈락 상한 없음** | 각 청크의 `1 − cosine` 중 최댓값 | L2 벡터의 좌표 오차와 상당 부분 중복되므로 기존 ≤1e-5 제안을 별도 필수 조건에서 제외. 방향 이상은 원인 분석에 사용 |
| 질의 벡터 좌표 오차 | 최대 절대 오차 **≤ 1e-4**, 무차원 | 질의 전체·좌표 전체의 최댓값. 청크와 별도로 판정 | 청크 개수가 더 많아 질의 오차가 전체 평균에서 희석되는 것을 방지 |
| 질의 벡터 방향 오차 | 최대 cosine distance 기록, **독립 탈락 상한 없음** | 질의별 `1 − cosine`의 최댓값. 청크와 별도 표시 | 주 수치 기준과 실제 근거 회수 비퇴행으로 판정하고 방향 오차의 이중 제한은 두지 않음 |
| 검색 근거 회수 비퇴행 | 질의별 그룹 recall 감소 **0**, 완료→미완료 전환 **0건** | 기준선 6회의 질의별 그룹 충족 결과가 일치하는 것을 먼저 확인하고, 후보 6회 각각을 그 고정 결과와 대조 | 전체 평균·유리한 실행 쌍으로 탈락을 숨기지 않음. 기준선 자체의 회수가 흔들리면 후보를 실패 처리하지 않고 비교를 보류해 기준선 원인부터 확인 |
| 페이지 연결 회수 | 두 그룹 모두 회수, 그룹 recall **1.0**, 완료율 **100%** | connection 1개의 head AND tail이 모든 실행에서 top_k 안에 있어야 함 | 한 조각의 0.5를 성공으로 세지 않음. 단, 현 k=5는 전수 반환이라 검색 선별력·실제 문장 연결 증거는 아님 |
| 필수 그룹 순위 | 그룹별 변화 기록, **독립 탈락 상한 없음** | 각 그룹의 최상위 순위 차이를 같은 실행 쌍별로 기록. retrieval과 connection을 분리 | 고정 +1위 제한은 동점·근접 점수·전수 반환에서 과도함. 필수 근거가 k 밖으로 밀리는 경우는 recall 비퇴행으로 이미 검출 |
| 잘림 관측 일치 | 토큰 수·잘림 플래그 불일치 **0건** | 모든 청크·질의·실행에서 ID별 `tokens_before_truncation`과 `truncated` 일치 | 누락은 일치로 세지 않음. 같은 토큰 수가 같은 token ID를 증명하지는 않으므로 실제 tokenizer 경로 검토는 A와 별도 확인 |

다음 지표는 함께 기록하되 별도의 합격 수치를 중복 적용하지 않는다.

| 관측 항목 | 집계·해석 |
|---|---|
| 검색 완료 수·평균 그룹 recall | retrieval 10개만 분모. 질의별 그룹 recall의 단순 평균. 비퇴행 판정은 위의 질의별 검사로 결정 |
| top_k 교집합·개별 ID 순위·cutoff margin | 진단용. 8·9번의 유효 대안 교환은 top_k 교집합이 0이어도 성공할 수 있어 일률적 교집합 하한을 두지 않음 |
| long-tail 문서 회수 | truncation_observation 1개로 별도 기록. 품질 분모에서 제외. 허용 문서가 하나여서 회수 성공은 자명하며 잘린 끝 구절 이해를 증명하지 않음 |

**합성 세트 품질 표시는 별개다.** retrieval 10개 모두 그룹 recall=1.0인 경우에만 ‘이 합성
검색 세트의 모든 정답 회수’를 표시한다. 모든 반복에서 만족해야 하며 10/10이 아니면 미충족 질의를 공개하고 전체 품질
통과로 표현하지 않는다. 이 수치는 ONNX 호환성 비퇴행 판정과 구분한다. 과거 기준선의
strict-page·near-scores 실패를 숨기거나 해당 질문을 품질 분모에서 빼지 않는다.
10/10이어도 실제 논문·ANN·생성·의미 검증을 포함한 제품 전체 품질을 보증하지 않는다.

## 3. 승인된 로컬 측정 기준과 별도 운영 협의

로컬 반복·집계와 RSS ≤0.80·warm ≤1.10은 A가 승인했다.
worker 메모리 상한·동시성·제한 시간·25% 여유율은 별도 A/Soo 운영 결정이며 승인으로 간주하지 않는다.
호환성 조건을 만족했더라도 성능·메모리 목표 미달은 운영 채택 보류로 구분한다.
목적이 작은 worker의 메모리 절감이므로 **메모리 우선안**을 제안한다.
필수 채택 목표는 RSS 20% 이상 감소와 warm 중앙값 악화 10% 이내이며,
warm 10% 개선·cold·최악 관측값은 별도 관측으로 둔다. 이 로컬 비교 우선순위는 A 승인에 포함된다.

| 항목 | 수치·단위 제안 | 집계 방식 | 이유 / A가 확인할 사항 |
|---|---|---|---|
| 실측 반복 | 런타임별 fresh process **6회**, 각 warm **3회** | 실행 쌍 순서는 `(PyTorch→ONNX), (ONNX→PyTorch)`를 3번 반복. 런타임별 cold 6개·warm 18개 | 항상 ONNX가 나중에 실행되는 순서 편향을 줄임. warm 수만 늘리지 않고 독립 프로세스 반복을 늘림. 통계적 유의성·p95/p99 보장은 아님 |
| cold 시간 | 중앙값·최댓값·비율 기록, **독립 탈락 상한 없음** | fresh 6개 cold_ms의 중앙값과 최댓값. A가 실제 worker 준비 제한을 정하면 절대 시간과 별도 대조 | 상주 worker에서 cold 비율만으로 메모리 절감 후보를 탈락시키지 않음. 기존 ≤1.10 조건은 필수에서 제외 |
| warm 비퇴행 목표 | ONNX / PyTorch **≤ 1.10** | 각 process의 warm 3회 중앙값을 먼저 구하고, process 중앙값 6개의 중앙값끼리 비교 | 메모리 절감과 교환 가능한 지연 악화를 10% 이내로 제한하는 협의안. 같은 process의 반복을 독립 표본 18개로 취급하지 않음 |
| warm 개선·최악 관측값 | 10% 개선(`비율 ≤ 0.90`) 여부 및 전체 최댓값 기록, **독립 탈락 상한 없음** | 위 process 단위 중앙값으로 개선율 계산. 원시 warm 18개 최댓값도 병기 | 개선 목표와 비퇴행 조건을 동시에 필수로 두지 않음. 소표본 최댓값의 ≤1.20 제한도 제거하고 이상 지연은 원시값과 함께 공개 |
| 모델 캡처 RSS 목표 | ONNX 최대 관측 RSS / PyTorch 최대 관측 RSS **≤ 0.80** | 각 런타임 fresh 6개 process-tree peak RSS 중 최댓값. bytes로 계산 | 작은 worker를 위한 20% 감소 목표 제안. 공유 페이지 중복·표본 간 peak 누락 한계도 기록. 실제 worker 적합성과 별도 |
| 운영 worker 메모리 예산 | 실제 worker 메모리 제한의 **25% 이상 여유**, 즉 실제 제한과 같은 지표의 peak **≤ 75%** | 임베딩 외 파싱·번역·큐·동시 작업을 포함한 실제 worker에서 별도 측정 | worker 사양·동시성·컨테이너 과금 지표는 A/Soo 결정 필요. 로컬 process-tree RSS를 컨테이너 사용량과 직접 비교하지 않음 |
| 측정 중 OOM·timeout·runtime 오류 | 실패 수 전부 기록. **‘0건’ 별도 채택 기준은 B 추가 제안이며 A 명시 승인값에 포함하지 않음** | 제한 시간·실패 분류는 실행 전 확정. 실패 표본을 삭제해 성공 표본만 채우지 않음 | 유효한 완료 캡처가 없으면 해당 비교는 미완료다. runtime 실패와 측정 수집 실패를 구분 |

비율은 ONNX/PyTorch이며 작을수록 좋다. 시간 원시값은 ms, 메모리는 bytes다.
분모가 0이거나 양쪽 환경·절차·스레드·배치·반복 수·측정 방법이 다르면 해당 비율은 판정 불가다.
기존 `performance_comparable=false`를 숫자 계산만으로 뒤집지 않는다.

승인된 로컬 메모리 우선안에서는 RSS ≤0.80과 warm ≤1.10을 함께 만족해야 한다.
cold 비율·warm 10% 개선·최댓값은 진단이며 별도의 필수 수치를 추가하지 않는다.
속도 우선으로 바꾸거나 절대 준비 시간 제한을 추가하려면 **후보 실행 전에** A/B가 합의한다.
worker 실제 메모리 상한(bytes)은 현재 정보만으로 임의 지정하지 않는다.
모델 캡처 목표 통과와 실제 worker 적합성 검증은 별도이며, 후자가 없으면 배포 사양을 승인하지 않는다.

측정 도구의 결과 누락 등 수집 실패는 후보의 runtime 실패와 같은 결론으로 처리하지 않고
‘측정 무효’로 기록한다. 재측정 허용 사유·횟수·대상 범위는 사전에 정한다. 실행 쌍 전체를 다시 측정하는 것은 B의 실행안이며 별도 확정이 필요하다. 재측정하더라도
실패 증적은 보존한다. 높은 시간·RSS나 낮은 회수율 자체를 측정 무효 사유로 삼지 않는다.

협의 책임은 다음과 같이 구분한다. B 단독으로 A의 배포 사양이나 예산을 확정하지 않는다.

| 담당 | 사전 확인 범위 |
|---|---|
| A 승인 반영 / A+B 사전 점검 | FP32 좌표 오차 상한·질의별 회수 비퇴행·연결 회수 및 관측 지표 구분은 승인됨. 실제 FP32 실행 경로에서 비교가 성립하는지는 별도 점검 |
| A+B 공동 | 실제 tokenizer·입력 인코딩 경로와 세션/manifest 대조. 승인된 6×3 반복·집계·RSS/warm 목표는 유지하며, 준비 시간·실패/재측정 세부 정책을 실행 전에 확정 |
| A/Soo 운영 결정 | worker 메모리 상한(bytes)·동시성·준비/작업 제한 시간·25% 여유율의 최종 채택과 비용. 다른 여유율이 필요하면 후보 실행 전에 변경 이유 기록 |
| C 후속 | 현재 새 MCP·카드 계약은 없음. 실제 호스트/중계 대기와 Desktop 지연은 이 로컬 비교로 대체하지 않고 별도 검증 |

## 4. 동일 환경과 재현 조건

- 같은 CPU/device·OS·Python·토크나이저·모델 고정 snapshot, batch 8, intra/inter-op 1,
  OMP/MKL 1, L2·최대 길이 128을 제안한다. A는 실제 ORT CPU provider·실행 모드·thread
  관측과 graph/tokenizer/외부 weight manifest의 일치를 확인한다.
- 공통 v2의 worker 측정 절차를 사용한다. cold는 process 시작·import·로딩·전체 입력 임베딩·토큰 관측을
  포함하고 warm도 전체 입력 임베딩·토큰 관측이다. 단일 질문 응답 시간으로 해석하지 않는다.
- 양쪽 모두 파일 해시를 같은 준비 단계에서 계산한다. 재부팅·파일 캐시 비움을 하지 않으면
  process-cold로만 부르며 디스크까지 차가운 상태로 주장하지 않는다.
- RSS는 같은 psutil 버전과 10ms 간격의 worker+자식 RSS 합을 사용한다. 현재 capture의
  RSS는 cold와 warm을 포함한 전체 worker 수명 최대 관측값이며 실제 컨테이너 한도 지표가 아니다.
- 공통 v2 프로토콜·입력 산출물 해시·환경·장치·배치·스레드·측정 방법·반복 수가 일치해야 한다.
  런타임별 exporter/opset·정밀도·provider·runtime 버전·산출물 지문은 따로 보존한다.
- 좌표 오차·필수 회수는 평균 실행 하나로 판정하지 않는다. 모든 실행 쌍의 좌표 오차와 기준선 안정성·후보 회수 결과를 확인하고 순위는 진단으로 기록한다.
  기존 캡처 파일을 덮어쓰거나 첫 실행 결과만 대표로 삼지 않는다.
- backend 실행 순서와 process별 시간의 2단계 집계는 기존 capture 명령의 기본 동작이 아니다.
  A/B가 실행 계획 버전·순서·집계 방식을 별도 동결하고 전체 원시 실행을 연결해야 한다.
  같은 process의 warm 반복을 독립 표본으로 간주하지 않으며 유의성·tail 지연 보장을 주장하지 않는다.
- 토큰 수·잘림 일치만으로 토큰 ID·mask까지 같다고 주장하지 않는다. A/B는 실제 입력 인코딩
  경로와 tokenizer 산출물·설정을 대조한다. 다른 경로를 사용하면 같은 길이라는 이유로 비교를 승인하지 않는다.

## 5. 현재 구현으로 확인할 수 있는 것과 남은 연결

| 구분 | 상태 |
|---|---|
| 그룹 recall·전체 그룹 충족·개별/그룹 순위·분류별 집계 | #521의 비교기에서 관측 가능. 기준선 반복 안정성 확인·자동 허용값 판정은 없음 |
| 청크/질의 최대 절대 오차·최대 cosine distance | 비교기에 있음. 모든 실행 쌍 비교와 최악값 집계는 실측 실행 절차에서 연결 필요 |
| 토큰 수·잘림 플래그 | 캡처에 관측값이 있으나 비교기는 일치 판정을 하지 않음. 누락을 성공으로 취급하지 않는 별도 대조 필요 |
| cold/warm 원시값·RSS·환경 | 캡처에 있음. 제안된 6쌍 교대 순서·process별 2단계 집계·비율과 승인 기준의 판정 연결은 미구현 |
| 실제 worker 메모리 제한·동시성·OOM | A/Soo 확인 및 별도 운영 실측 필요. 로컬 캡처만으로 대체 불가 |
| 기준 승인·동결 | FP32 수치·측정 계획 A 승인 반영. 자료/정책 해시 기록 완료. 환경은 관측 지문만 기록했으며 ONNX 산출물·세션 확인이 남아 최종 동결 미완료 |

## 6. 승인 반영 후 남은 순서

1. **A 승인 반영 완료:** FP32 좌표 오차 상한, 질의별 회수 비퇴행·기준선 안정성, 연결 100%,
   토큰/잘림 관측 일치와 품질·호환성 구분을 확인한다. 방향 오차·순위는 진단으로 유지한다.
2. **A+B 사전 점검:** 실제 산출물·입력 인코딩·세션 설정, 6×3 반복·교대 순서·process 단위 집계,
   승인된 메모리 우선 목표를 유지한다. 실패를 보존하고 재측정 사유·여부를 기록하며, 자동 재측정은 하지 않는다. 구체적인 수집 실패 재측정 상한은 실행 전 확정한다. worker 메모리 상한·25% 여유·동시성·제한 시간은 A/Soo가 결정한다.
3. 승인자·시각·자료/기준 문서 digest·버전·환경·미검증 항목을 동결 기록에 남긴다.
   이 문서 작성일이나 에이전트의 작성 행위는 승인 기록이 아니다.
4. 승인된 기준을 관측값과 연결할 검증·집계를 준비하고 PyTorch v2를 재캡처한 뒤 같은
   환경의 ONNX 후보와 비교한다. 실제 실행·다운로드/export가 필요하면 그 범위를 별도로 확인한다.
5. 실패와 원시 반복값을 보존하고 근거 회수/운영 채택/제품 품질 결과를 나눠 기록한다.
   통과해도 기존 context·embedding set·publication을 자동 교체하지 않는다.

#391과 ADR25 미결 3은 계속 열어둔다. 최종 환경 동결·자동/수동 판정 연결·실제 모델 비교와
제품 적용 판단이 남아 있으며 이번 문서에서는 실행하지 않았다.
