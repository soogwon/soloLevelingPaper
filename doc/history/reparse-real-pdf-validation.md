# #116 실제 PDF 재파싱 검증

2026-11-09, main `4a10f51` 기준. Windows / Python 3.12.14.
브랜치: `codex/test/issue-116-real-pdf-validation`.

## 검증 범위

기존 Attention Is All You Need 테스트 자료의 PDF와 DB를 별도 작업 디렉터리에 복사했다.
원본 DB는 SQLite로 열지 않고 파일로 복사했으며, 복사 전 WAL/SHM/journal이 없는지 확인했다.
복사 전후 파일 상태와 해시를 확인하고, 검증 종료 후에도 원본 PDF·두 테스트 DB의 SHA-256이
처음 복사한 파일과 일치함을 확인했다. 이는 온라인 DB의 원자적 백업을 제공한다는 뜻이 아니다.

최신 스키마 이관·관리 PDF 경로 변경·새 번역/색인 게시·학습 맥락 선택은 복사본에만 적용했다.
기존 벡터 저장소는 열지 않았다. 기존 성공 번역의 파생 벡터도 별도 Chroma에 합성 값으로 구성했다.
requests/httpx 호출은 오류를 내도록 차단하고 Chroma 원격 telemetry를 껐다.
실제 번역·임베딩 모델·생성 API 호출은 0회다.

## 청크 경계와 내용 포함

| 항목 | 결과 |
|---|---:|
| PDF 물리 페이지 | 15 |
| 기존 파싱의 청크 | 98 |
| 최신 파싱의 청크 / 섹션 | 109 / 10 |
| 최신 청크의 비공백 문자 사이 절단 | 0 |
| 추출된 페이지 텍스트에서 청크가 포함하지 못한 비공백 문자 | 0 |

각 최신 청크를 해당 페이지의 추출 텍스트에서 순서대로 찾아 시작·끝 위치를 대조했다.
청크 양옆의 두 문자가 모두 비공백인지 검사했고, 전체 청크 구간의 합집합이 모든 비공백
문자를 포함하는지 검사했다. PDF 6페이지를 렌더링해 본문과 페이지 경계도 육안 확인했다.
기존 저장 청크에서는 동일 페이지의 정확한 겹침을 찾을 수 있는 쌍에 한해 단어 내부
시작·끝 사례가 존재함을 확인했다. 겹침을 복원할 수 없는 쌍의 경계는 추측하지 않았다.

109개라는 수치는 최신 섹션 분리·본문 추출 등의 변화도 포함한다. 청크 수 증가 전체를
단어 경계 수정만의 효과로 해석하지 않는다. 추출 텍스트의 포함 검사는 원래 PDF의 모든
글자·표·그림을 정확히 추출했다는 보증도 아니다. 회전 텍스트 제외 등 기존 파서 정책을 유지했다.

이 PDF의 최신 청크에서는 공백 없는 긴 수식·URL의 강제 절단 예외가 나타나지 않았다.
다른 입력의 예외는 기존 청킹 합성 회귀로 확인하며 모든 문서에서 절단이 없다고 일반화하지 않는다.
페이지 경계의 문장 보충과 의미 검증 정책(#108)은 이번 검증에서 변경하지 않았다.

## 실제 PDF + 모의 제공자의 게시 흐름

현재 `ReparseService`와 `ReparseManager`를 사용했다. 번역은 명시적인 테스트 표식을 붙이는
모의 제공자, 임베딩은 결정론적 합성 384차원 벡터다. 실제 번역 품질·검색 순위를 평가하지 않는다.

| 확인 항목 | 결과 |
|---|---|
| 준비 조회 | 번역·임베딩 호출 0회 |
| 재파싱 완료 | COMPLETED, 새 청크 109개, 번역 실패 0개 |
| 모의 번역 / 임베딩 | 청크별 109회 / 배치 1회 |
| 완료 조회 전후 맥락 수 | 기존 3개 유지 |
| 명시적 새 맥락 선택 | 4개로 증가, 반복 선택은 같은 맥락 반환 |
| 기존 / 새 맥락 검색 | 96개 / 109개, 청크 ID와 파싱 리비전 분리 |
| 같은 키 재접수 | 완료 결과 재생, 추가 번역·임베딩 0회 |

| 기존 근거 조회 | 맥락 3개의 근거 84건에서 전체 조회 응답 동일 |
| 참조 무결성 | foreign_key_check 위반 0건 |

기존 98개 청크 중 성공 번역이 96개라 기존 검색 결과도 96개다. 초기 검증 코드에서 이를
98개로 기대해 검사 한 건이 실패했다. 게시 자체는 성공했으며, 새 복사본에서 성공 번역 수를
기준으로 바로잡아 전체 검증을 재실행했다. 실패했던 복사본을 원본이나 정상 측정 결과로 대체하지 않았다.

이 실제 자료에는 저장된 요약·메모·하이라이트가 없다. 빈 테이블의 내용이 유지된 것은
확인했지만, 존재하는 기록의 보존을 실측했다고 표현하지 않는다. 해당 내용은 합성 회귀에서 확인한다.
직접 서비스/manager를 호출한 오프라인 검사이며 Desktop의 사용자 동의 화면 실측을 대신하지 않는다.

최신 main의 재파싱 실행·MCP·A 저장 계약·청킹 회귀는 **92 passed, 1 skipped**
(85.79초)였다. skip은 Windows 심볼릭 링크 생성 권한 부족 한 건이다.
`tests/integration/test_reparse_service.py`, `tests/integration/test_reparse_mcp.py`,
`tests/unit/test_reparse_contract.py`, `tests/unit/test_chunker.py`를 새 임시 경로에서 실행했다.

공유 문서는 본문·기존 ID·키·원본 해시를 포함하지 않는 이 기록으로 한정한다.

## 다음 실제 제공자 검증의 호출 예산

현재 파싱 설정을 고정하면 원문 청크는 109개다. 기본 `TranslationRetryPolicy`는 청크당
최초 포함 최대 3회와 전체 배치의 추가 재시도 최대 20회를 함께 적용한다.
`TranslationService.translate`를 한 번 실행하는 재파싱 한 건의 상한은 다음과 같다.

```
최초 번역 109회 + 전체 배치 추가 재시도 최대 20회 = 번역 HTTP 호출 최대 129회
```

번역 어댑터는 각 시도에서 OpenAI Responses API를 한 번 호출한다. 준비·상태 조회·맥락 선택과
로컬 임베딩은 이 번역 API 횟수에 추가되지 않는다. 이 예산에는 ask_paper·답변 생성·의미 검증을
포함하지 않으며, 추가 실측을 하려면 별도 범위로 합의한다. 문서·설정 변경이나 재파싱 재실행에
이 예산을 자동 재사용하지 않는다. 최대 호출 수는 성공 보장이 아니며 기본 정책은 부분 번역 게시를 거부한다.

다음 단계는 별도 테스트 DB/벡터 복사본과 관리 PDF에서, 고정한 제공자·모델·예산에 대한
사용자 승인 후 Desktop의 재파싱 안내 → 동의 → 접수 → 완료 조회 → 명시적 새 맥락 선택을 확인하는 것이다.
이 문서의 오프라인 성공만으로 #116을 닫지 않는다.

## 실제 제공자 + Windows Desktop 검증

2026-11-10, 같은 main `4a10f51` wheel을 별도 디렉터리에 설치해 Claude Desktop
4.23118.0에서 확인했다. 테스트 전용 DB·PDF·Chroma만 사용했으며, 원본 벡터 저장소는 열지 않았다.
원문 109개 청크를 OpenAI Responses API `gpt-5.4-mini`로 전송하고 재시도를 포함해 최대
129회 호출하는 범위를 사용자가 승인했다. 테스트 실행기는 번역 지침·모델·원문 해시를 제한하고,
HTTP 요청마다 원자적인 예산 파일을 먼저 생성해 다른 API와 130번째 호출을 차단했다.

| 확인 항목 | 실측 결과 |
|---|---|
| Desktop 준비 안내 | 실제 카드 표시 및 서버 HTML 리소스 요청 확인 |
| 사용자 동의 | 사용자가 카드 체크박스와 제출 버튼을 직접 조작 |
| 재파싱 접수 | 제출 1회, 저장된 재파싱 요청 1건 |
| 카드 상태 조회 | 접수됨 → 진행 중 → 게시 완료 |
| 번역 | 109회, 전부 HTTP 200, 재시도 0회, 저장된 번역 실패 0개 |
| API 토큰 집계 | 입력 33,383 / 출력 14,935; 응답 usage 합산이며 비용 계산은 하지 않음 |
| 새 색인 | 청크 109개 / 벡터 109개 / 384차원, 유한값과 색인·버전 메타데이터 확인 |
| 완료 직후 context | 기존 3개 유지, 자동 생성 없음 |
| 카드에서 새 맥락 선택 | 새 context 1개 생성, 총 4개; 기존 context의 파싱·색인 연결 유지 |
| 기존 근거 | 84건 전체 행 보존 및 저장소 조회 응답 동일 |
| 기존 청크·파싱·번역 | 기존 행의 전체 내용 해시 보존; 새 리비전은 별도 추가 |
| 참조 무결성 | foreign_key_check 위반 0건 |
| 원본 보호 | 원본 DB 2개·PDF의 SHA-256이 최초 사본과 일치; 관리 PDF 사본도 변경 없음 |
| 답변 생성 | ask_paper·생성·의미 검증 API 호출 0회 |

준비 안내를 다시 연 것은 접수 기록 0건·외부 호출 0회임을 확인한 뒤였다.
처음 카드에서는 접수 전 상태 조회 후 동의 토큰이 비워져 재동의할 수 없었다.
새 준비 안내의 사용자 동의 후에는 제출이 한 번만 서버에 도착했으며, 이후는 같은 요청 키의
상태 조회만 사용했다. 해당 카드의 접수 전 조회 후 재동의 UX는 이 검증에서 수정하지 않았다.

로컬 모델은 오프라인 캐시를 사용했다. 별도 준비 검사에서 기본 90초 제한은 차가운 라이브러리
로드 중 만료됐고, 테스트 전용 설정을 180초로 고정한 준비 검사는 성공했다. 실제 재파싱의
임베딩 worker 처리도 약 78.3초로 정상 종료했다. 기본 90초에서 Desktop 전체 흐름이
항상 성공한다고 해석하지 않으며, 시작 지연 문제는 #119와 구분한다.

기존 색인의 테스트용 벡터는 합성 값이다. 새 색인은 실제 로컬 모델 벡터이지만 이번 검증에서는
질문 검색·번역 품질·의미 일치 정확도를 측정하지 않았다. 저장된 요약·메모·하이라이트는
이 자료에 없어, 존재하는 기록의 보존에 대한 실측 결과로 일반화하지 않는다.

개인 디렉터리 `runtime/issue116-desktop-live-*`에 본문 없는 호출 감사 기록·호출 예산·보존
비교 결과와 테스트 데이터를 보관했다. 원문·번역·기존 ID·자격 증명·동의 토큰은 공유 문서에
포함하지 않았다. 실측 중 제품 구현 파일은 변경하지 않았으며, 공유 대상은 이 검증 문서뿐이다.
