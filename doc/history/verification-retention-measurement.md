# 검증 이력 크기·지연·정리 실측 (#82)

## 범위와 표본

2026-11-07, main `3322d39` 기준. Windows / Python 3.12.14 / SQLite 3.53.1.
기존 #108 전용 테스트 DB에 실제 모델 호출로 저장된 이력 3건·주장 7개·근거 참조 10개를
오프라인 파일 읽기로 새 DB에 복사했다. 원본은 SQLite로 열지 않았다. 실패 이력은 0건이며 주장 문구 UTF-8 합계는 1,146바이트다.
이 문서·측정 JSON·stdout에는 주장·논문 원문·질문·키·식별자를 포함하지 않는다.

**독립적인 실제 요청 300건이 아니다.** 실제 표본 3건을 새 run_id로 100회씩 복제한 저장소 부하 측정이다.
원본 데이터는 그대로 두고, 복사본에만 최신 스키마 이관·기준선 VACUUM·복제·시간 변경·정리·공간 회수를 적용했다.
외부 API·모델·벡터 저장소는 사용하지 않았다. 소스에 WAL·SHM·rollback journal이 없음을 확인하고 DB 파일의 identity·크기·수정 시각·SHA-256을 복사 전후와 측정 종료 시 비교했다.

## 크기

| 상태 | DB 본체 | 이력 테이블 할당량 | 이력 인덱스 할당량 |
|---|---:|---:|---:|
| 복사·이관 후 실제 이력 3건 | 626,688 B | 12,288 B | 24,576 B |
| 이력만 비우고 VACUUM한 기준선 | 618,496 B | 12,288 B | 24,576 B |
| 표본 복제 153건 | 970,752 B | 245,760 B | 143,360 B |
| 표본 복제 300건 | 1,294,336 B | 462,848 B | 249,856 B |

측정 DB는 DELETE 저널 모드, 4,096바이트 페이지, synchronous=2(FULL)이며 WAL은 각 측정 시점 모두 0바이트다. 이력 테이블/인덱스는 SQLite dbstat의 할당 페이지 크기 합계다.
300건에서 기준선 대비 **675,840 B(660 KiB), 평균 약 2.20 KiB/건** 증가했다.
빈 테이블도 루트 페이지를 사용하므로 소량 이력의 총 할당량을 요청 수로 나누면 과대 추정한다.
무작위 run_id에 따른 인덱스 페이지 분할·표본 구성·본문 길이에 따라 결과는 달라진다.

## 저장·조회 지연

| 작업 | 반복/행 수 | 중앙값 | p95 | 최대 |
|---|---:|---:|---:|---:|
| 공개 저장소 save_verification_history | 300회 | 11.404 ms | 16.198 ms | 1,390.975 ms |
| 단건 get_verification_history | 300회 | 3.411 ms | 5.031 ms | 8.541 ms |
| 한 context의 전체 이력 조회 | 300행 × 5회 | 21.302 ms | 22.297 ms | 22.297 ms |

정상 저장과 단건 조회의 반환 내용을 매회 비교했다. 목록 조회는 전체 300행 반환을 확인했다.
연결 생성·참조 검증·커밋 비용이 포함되고, API·임베딩·MCP 비용은 포함되지 않는다.
같은 머신에서 반복한 warm-cache 측정이며 p95는 nearest-rank다. 목록 표본 5회는 분포 추정에 충분하지 않다.
저장 최대값이 크게 튄 이유는 확정하지 않았으며 중앙값만으로 상한을 약속하지 않는다.

## 90일 보존·정리

복제 DB에서 298건을 91일 전으로 설정하고, 90일 경계 1건·최근 1건을 남겼다.
실제 사용자의 이력 생성 시각은 변경하지 않았다.

| 작업 | 결과 | 소요 시간 |
|---|---|---:|
| plan | 실행 298·주장 696·참조 994개가 후보, 전체 테이블 내용·크기 무변경 | 2.995 ms |
| backup | 전체 테이블 내용 해시·integrity_check로 백업 검증, 이력 300건 보존 | 24.300 ms |
| run | 후보 이력 298건 삭제, 경계·최근 2건 보존 | 46.357 ms |
| reclaim | completed, WAL 0, 실제 본체 618,496 B | 23.036 ms |

행 삭제 직후 DB 파일은 **1,294,336 B 그대로**이고 내부 빈 공간이 675,840 B였다.
별도 reclaim 후 **675,840 B를 실제 회수**했다.
이력 외 모든 사용자 테이블은 행 수와 전체 내용 해시가 정리·VACUUM 전후 같았고 FK 위반은 0건이었다.
이는 context·근거·청크·요청 결과 등의 저장 내용 보존 검증이며, 정리 후 새 질문의 답변 품질 실측은 아니다.

## 재현 방법

```powershell
python scripts/measure_verification_retention.py --source-db <기존 테스트 DB> --output-dir <새 측정 디렉터리> --copies 100
python -m pytest tests/unit/test_retention_measurement.py tests/unit/test_verification_retention.py -q
```

측정기는 기존 출력 디렉터리를 거부하고 원본을 SQLite로 열지 않는다. 실행 중인 DB를 직접 넘기지 말고,
앱/서버를 종료한 오프라인 사본을 지정해야 한다. 원본 옆에 -wal/-shm/-journal이 있으면(0바이트도 포함)
거부하며, 파일 변화가 감지되면 실패하고 성공 report.json을 쓰지 않는다. 진행 중 WAL을 무시하거나
원본에서 checkpoint·VACUUM·스키마 초기화를 실행하지 않는다.

파일 비교는 동시 작성자에 대한 잠금이나 스냅샷 보증을 대신하지 않는다. 온라인 DB의 일관된 사본이
필요하면 소유자가 먼저 백업을 마련해야 한다. 측정기의 검증은 python -O에서도 실행된다.
복제 후 총 이력은 최대 10,000건이며, 초과 요청은 복제 전에 거부한다.
측정 디렉터리의 DB와 backup에는 원래 표본 본문이 포함되므로 공유·커밋 대상이 아니다. 실패해도 진단용 사본을 자동 삭제하지 않으므로 실패 디렉터리도 같은 기준으로 관리한다.
공유할 수 있는 결과는 본문 없는 report.json과 이 문서다. dbstat 미지원 환경에서는 할당량을 null로 기록한다.
기존 데이터나 파일을 자동 정리하지 않으며 재실행할 때도 새 출력 디렉터리를 사용한다.

보완 후 측정기·기존 보존 회귀 **67개 통과**. 원본의 SQLite 미접속, sidecar 거부,
복사 중 변경 감지, 같은 건수의 손상된 백업 거부, Python 최적화 모드에서 검사 유지,
복제 상한 초과 시 추가 저장 차단을 포함한다. 이 검사는 임시 합성 DB로 수행했다.
추가 검토에서는 보존 실행의 주장·참조 전체 내용, 공간 회수 전후 모든 사용자 테이블,
삭제된 실행·주장·참조 건수의 일치를 검사하도록 보강했다. BLOB과 문자열도 해시에서 구분한다.
보존된 주장 수정·공간 회수 중 참조 삭제를 주입하면 성공 보고서를 생성하지 않는다.

## 판단과 남은 범위

- 현재 표본에서는 90일 권장값을 바꿀 근거가 없다. **90일 권장·DB 소유자의 수동 실행·기간 명시** 합의를 유지한다.
- 다양한 논문·주장 수·실패 이력, 수만 건 이상, WAL 장기 연결, 다른 OS/저장장치의 성능은 이번 수치로 일반화하지 않는다.
- 실제 사용자 DB의 정리·예약 자동 삭제는 활성화하지 않는다.
- 원문 변경·유실 시 재검토 불가 표시는 별도 이력 조회 계약이며 이번 측정 범위가 아니다.
