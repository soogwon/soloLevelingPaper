작성일: 2026-11-15. **협의 전 초안**. #396·ADR25의 미결 2·6을 확정하지 않는다.

## 1. B 권장 단위

| 단위 | 제안 | 책임 |
|---|---|---|
| 논리 실행 | 인증 owner + 작업 종류 + request key + 전체 입력 해시 | A 저장, B 입력 범위, C 재사용 |
| 호출 슬롯 | **실제 제공자 전송 시도 1회**. 최초/형식 보완/의미 검증/허용 재시도 모두 차감 | B 실행 직전 검사, A 지속 원장 |
| 입력·출력 토큰 | 호출별 상한 예약 및 사용량 관측. 예산용 토큰과 금전 정산은 구분 | B 모델별 입력/출력 한계, A 정산 |
| 단계 | generation / repair / coverage / semantic_verification / translation | B 고정 단계 코드; 실제 전송이 없으면 호출 슬롯을 차감하지 않음 |
| 실행 세대 | 같은 논리 실행의 lease token / attempt | A 저장·게시 fencing, B 인계한 잔여 예산만 사용 |

- 복합 질문·주장 수·청크 수가 늘어도 실행별 상한을 우회하지 않는다. 한 제공자 요청에 여러
  청크/주장이 있으면 슬롯은 1회지만 토큰 예약은 그 전체 요청에 대해 수행한다.
- 호출 슬롯과 토큰 한도, 단계 시간 제한, 번역 재시도 정책을 **모두** 만족해야 한다.
  허용 재시도 수가 남아도 전체 예산이 부족하면 실행하지 않는다.
- 로컬 CPU 임베딩은 제공자 호출 슬롯에서 제외한다. 훗날 유료 임베딩 제공자를 도입하면
  별도 단위·요금 계약을 먼저 연결한다. 모델 다운로드·worker 자원 비용은 운영 한도에서 따로 본다.
- 상태·근거·메모·저장 결과 조회는 유료 실행을 새로 만들지 않는다. 조회만으로 번역/보완/재파싱하지 않는다.

## 2. 실행 전 예약과 실제 사용량

```text
인증 검증 → 검증 identity의 명시적 서버 owner 매핑
    ↓ 성공한 owner 범위에서만
기존 키 조회 → 같은 입력이면 상태·기존 결과 재생 / 다른 입력이면 충돌
    ↓ 새 유료 작업이고 동의·한도 확인이 끝난 경우만
A: 작업 생성 + 사용자/서비스 예산 예약 (같은 transaction)
    ↓
B: 각 실제 전송 직전에 현재 세대·시간·호출 슬롯·입출력 토큰 잔여 확인
    ↓ A: 호출 시도 ID별 예약/상태를 원자적으로 확보
제공자 요청 → 사용량 확인 / 전송 여부·사용량 불명
    ↓
A: 같은 시도 ID로 중복 없이 정산 또는 보류
    ↓
B: 남은 예산으로 다음 단계 실행 여부 결정 → A: 원자 결과 게시·완료
```

- 프로세스 내 카운터만으로 사용자·서비스 전체 한도를 지키지 않는다. 재시작·다중 worker·lease 회수 후에도
  **소비/보류된 예산은 같은 논리 실행에 남고**, 새 세대가 총예산을 다시 받지 않는다.
- 호출 전에 입력의 안전한 토큰 상한과 해당 요청의 출력 제한을 확보한다. 문자 수만을 정확한 토큰 수로
  간주하지 않는다. 상한을 보장할 방법/모델 규칙이 없으면 엄격한 토큰 예산 실행을 허용하지 않는다.
- 실제 요청의 출력 상한은 제공자·단계 제한과 남은 예약의 최소값이다. 출력 제한만 줄여 필수 검증을
  생략하거나 불완전한 검증을 통과 처리하지 않는다. 가능한 최소 실행량에도 못 미치면 전송하지 않는다.
- 이미 응답이 유실된 논리 실행을 새 키로 재접수해 해결하지 않는다. 전송 시도 ID도 서버가 부여하며
  모델이 넘긴 키/confirmed 값은 동의·사용량·잔여 예산의 증명이 아니다.

### #413 인증 스파이크와 비용 경계

#413은 `whoami`·`probe_card`·`probe_delay`만 제공한다. `spike:read` 인증 성공은 유료 자료 처리
권한·사용자 동의·예산 예약의 증명이 아니다. 지금 이 도구들에 유료 pipeline을 연결하지 않는다.
이후 실제 자료 도구는 인증 → 서버 owner 매핑 → 별도 처리 권한/동의 → 예약 순서를 지킨다.
웹의 user_id와 MCP의 `issuer#sub`를 동일 문자열로 가정하지 않으며 매핑 계약은 #390에서 A·C와 확인한다.

| 관측 계층 | 처리 제안 |
|---|---|
| MCP 인증 거부·토큰 만료·scope 불충족 | 유료 job·호출 예약·AI 전송을 만들지 않음. AI 호출 슬롯/토큰 소비 0 |
| JWKS 조회 등 인증 제공자 장애 | 인증 경계에서 중단, 유료 job·예약·AI 전송 0. AI usage unknown으로 분류하지 않음 |
| owner 매핑 없음/장애 | 다른 owner/subject로 대체하지 않고 중단. 동일하게 유료 접수/전송 0 |
| 인증 후 동의 없음·철회·고지 버전 불일치 | 새 유료 처리 거부. 인증만으로 동의로 승격하지 않음 |
| 이미 접수된 AI 전송 뒤 호스트 응답 유실 | 기존 논리 실행/예약을 유지하며 AI usage는 관측 결과에 따라 observed/unknown으로 분류 |

인증/JWKS의 네트워크 요청·abuse 비용은 운영 rate limit/관측(#400) 대상이며 유료 AI 호출 슬롯과
혼동하지 않는다. 인증이 끊겨도 이미 전송한 AI 호출의 예약을 소급 환급하지 않는다.
위 표는 **원격 진입 시의 신규 처리 정책 제안**이다. #413의 실제 401/인증 장애 응답을 변경하거나
기존 job 정산 동작을 구현한 것이 아니다. 각 계층의 장애 표시·재연결은 C와 별도 확정한다.

## 3. 정산 상태 제안 — A 확인 필요

아래는 **내부 상태 의미 제안**이며 새 DB 컬럼이나 외부 사유 코드가 아니다.

| 상태 | 의미 | 예산 처리 제안 |
|---|---|---|
| reserved | 호출 실행권·상한을 예약했으나 전송 확정 전 | 동시 실행이 같은 잔여 예산을 중복 사용하지 못하게 함 |
| observed | 신뢰하는 제공자 사용량 관측 | 같은 시도 ID의 관측값으로 정산; 중복 이벤트 합산 금지 |
| unknown | 전송했을 수 있으나 사용량·완료 여부 불명 | **예약을 즉시 전액 반환하지 않고 보류**, 추가 유료 재시도 금지 기본 |
| not_sent | 전송 전 로컬 거부/명시적으로 전송하지 않음이 증명됨 | 예약한 미사용량 반환 가능, 호출 슬롯 소비 여부도 원장에 명시 |

- timeout·연결 종료·worker 종료·잘못된 JSON·HTTP 오류만으로 사용량 0을 단정하지 않는다.
  제공자별 무과금/미전송 증명 기준은 A·B가 먼저 합의한다. 사용량 없는 성공 응답도 unknown으로 다룬다.
- 제공자 usage의 입력/출력·cached/reasoning 등 세부 항목을 어떻게 합산/과금할지는 제공자 정의를
  확인해 정산 adapter에서 처리한다. 세부 항목과 상위 사용량을 중복 합산하지 않는다.
- stale worker는 저장·게시 권한을 얻지 못한다. 다만 늦게 도착한 사용량 관측을 무조건 버리면
  비용이 누락될 수 있으므로, **게시 fencing과 중복 없는 사용량 접수 권한을 분리할지 A가 결정**해야 한다.
- unknown을 언제 해제/상한 정산하는지, 외부 조회가 추가 비용을 만드는지, 관리자 조정·보존 기간은
  A·운영자가 정한다. B가 임의로 영구 보류 또는 전액 환급을 구현하지 않는다.

### 숫자 예시 — 운영 기본값 아님

총 토큰 예약 100, 호출 슬롯 3인 가상 실행이다. 모델·가격 단위와 관계없는 설명용 값이다.

| 단계 | 결과 | 확인 사용량 | 보류 | 다음 예약 가능량 |
|---|---|---:|---:|---:|
| 호출 1: 입력 20+출력 20 예약 | 실제 입력 18+출력 10 확인 | 28 | 0 | 72 |
| 호출 2: 입력 20+출력 20 예약 | 전송 후 timeout, usage 불명 | 28 | 40 | 32 |
| 호출 3: 40 필요 | **전송하지 않음** | 28 | 40 | 32 |

호출 슬롯이 남아도 토큰 예약이 부족하면 거부한다. unknown 때문에 거부된 요청을 새 lease나
다른 단계 이름으로 바꿔 재시도하지 않는다. 실제 사용자별·월 금전 한도는 Soo 결정 사항이다.

## 4. 상한 도달 시 B 처리 제안

| 도달 시점 | 처리 |
|---|---|
| 유료 생성 전 | 추가 전송 없이 예산 제한에 따른 실행 거부. 근거 부족으로 분류하지 않음 |
| 일부 주장만 검증 완료 | 기존 기준을 통과한 답변만 보존; 누락 항목·예산 제한을 구분해 안내하는 응답 계약을 C와 확정 |
| 의미 검증 전/도중 | 미검증 주장을 model_checked로 표시하지 않음. structural_only로 강등해 통과시키지도 않음 |
| 보완 단계 | 검증된 기존 내용을 유지하되 대상 외 주장 추가·근거 추측 금지; 검증할 수 없는 새 보완은 제외 |
| 번역·복구·재파싱 중 | 추가 유료 요청 중단. 임시 결과를 임의 게시하지 않고 기존 publication/context 유지 |
| 기존 완료 결과 조회 | 예약/한도 소진과 무관하게 인증된 조회 허용; 삭제/철회 정책의 별도 제한은 준수 |

검증된 내용이 하나도 없으면 실행 오류/제한을 전달하며 `insufficient_evidence`라고 단정하지 않는다.
`semantic_limited`/`extraction_limited`를 비용 거부의 대체 코드로 사용하지 않는다.
**외부 status·reason_code·재시도 가능성의 실제 표현은 C와 확정 전 새 코드로 배포하지 않는다.**
호스트 대기 종료는 서버 취소·미과금 증명이 아니며 #119/#395 원칙을 유지한다.

## 5. 구현 시 대역 테스트 기준

이번 문서는 구현 전 초안이므로 아래는 **미실행 인수 기준**이다.

1. 전송 경계 N번째까지 허용하고 N+1은 provider 호출 0회. 생성·보완·검증·번역 재시도가 동일 총예산 공유.
2. 두 worker가 동시에 마지막 슬롯/토큰을 예약해도 하나만 확보. 같은 시도 ID·관측 재생은 중복 차감하지 않음.
3. unknown 뒤 재시작·lease 변경·호스트 재연결에도 보류를 유지하고 새 실행/예산을 만들지 않음.
4. not_sent와 usage 불명을 구분. 늦은 usage는 한 번만 정산하며 stale worker의 게시 권한은 복구하지 않음.
5. 한도 직전의 정상 호출·저장 결과 재생·조회는 정상. 무효화된 동의/다른 owner는 유료 호출 전 거부.
6. 상한 도달 뒤 미검증 주장·대상 외 보완·페이지 밖 새 설명이 통과하지 않음. 기존 유효 내용·context 보존.
7. 기본 로그에는 고정 단계/제한/실행 결과와 필요한 수치만 남기고 인증 토큰 값·질문·원문·주장·동의 비밀값은 제외.
8. 예산 저장/조회 실패는 유료 실행을 시작하지 않는 방향으로 처리. 로그 실패만으로 완료 결과 조회를 파괴하지 않음.
9. #413 인증/만료/scope 거부, JWKS 장애, owner 매핑 실패 각각에서 job 생성·유료 예약·AI 전송이 0회.
   반대로 이미 AI에 전송한 실행의 인증/호스트 연결이 끊겨도 기존 unknown 보류가 해제되지 않음.
