# #110 퀴즈 MCP 연결 계약안

작성일: 2026-10-28. 갱신일: 2026-10-31. 상태: 저장 계약 일부 합의 및 C 대역 검증 준비이며 운영 도구 명세가 아니다.
관련: [#110](https://github.com/soogwon/soloLevelingPaper/issues/110).

## 확인한 현재 구현

- `application/quiz/attempts.py`의 `QuizAttemptService`는 제출·시도 상세·이력·단계별 점수·오답 근거 조회를 제공한다.
- `submit(context_id, step, answers)`는 현재 context·단계의 최신 퀴즈를 조회한다. 호출자가 본 `quiz_id`와 요청 키를 받지 않는다.
- `answers`는 정수 문항 위치를 키로 사용한다. 객관식 답은 0부터 시작하는 선택지 위치, 단답형은 문자열이다. 빈 매핑은 거부하고 누락 문항은 무응답으로 처리한다.
- `repository.save_quiz()`는 같은 context·단계의 기존 퀴즈를 교체한다. 과거 시도는 제출 당시 문항 스냅샷을 보존한다.
- `interfaces/mcp/server.py`에는 퀴즈 도구가 아직 없다.

따라서 현행 제출 서비스를 그대로 노출하지 않는다. A의 원자적 저장 계약과 B의 제출 대상 검증이 선행되어야 한다.

## 도구 구성 제안

| 도구 | 필수 입력 | 선택 입력 | 출력 중심 |
|---|---|---|---|
| `get_quiz` | context_id, step | 없음 | quiz_id, 공개 문항, 채점 방식 |
| `submit_quiz` | context_id, step, quiz_id, request_key, answers | 없음 | 저장된 attempt, 재사용 여부 |
| `get_quiz_attempt` | context_id, attempt_id | 없음 | 제출 당시 문항별 결과·점수 |
| `list_quiz_attempts` | context_id | step, limit, cursor | 시도 요약 목록·next_cursor |
| `get_quiz_scores` | context_id | 없음 | 단계별 최신·최고 점수와 시도 수 |
| `review_quiz_attempt` | context_id, attempt_id | 없음 | 오답 문항·정답·근거 |

이름과 분할은 협의 대상이다. 조회는 저장된 자료만 반환하고 퀴즈를 자동 생성·재생성하지 않는다.
기존 생성 기능의 MCP 노출은 별도 결정이 필요하다. 아직 퀴즈가 없으면 `QUIZ_NOT_READY`로 안내한다.
단계는 기존 `preview`, `structure`, `deep_read`, `review`를 사용한다.
조회 도구는 읽기 전용, 제출은 쓰기 도구로 선언한다. 멱등성 힌트는 DB 중복 방어 구현 이후에만 부여한다.

## 공개 문항과 제출 형식

공개 문항 예시:

```json
{
  "context_id": "context-example",
  "step": "preview",
  "quiz_id": "quiz-example",
  "grading_mode": "normalized_exact_match",
  "questions": [
    {"question_index": 0, "question_type": "multiple_choice", "prompt": "문항 예시", "choices": ["선택지 A", "선택지 B"]},
    {"question_index": 1, "question_type": "short_answer", "prompt": "단답형 예시", "choices": []}
  ]
}
```

`grading_mode`는 단답형에 적용되는 기본 규칙을 안내한다. 객관식은 선택지 위치 일치로 채점한다.
문항 식별은 `(quiz_id, question_index)` 조합이다. index만 단독으로 다른 퀴즈에 재사용하지 않는다.
공개 응답은 허용 필드만 직접 구성하고 도메인 객체 전체를 직렬화하지 않는다.
정답·정답 위치·채점 기준·정답 근거 ID 및 원문은 제출 전 응답에서 제외한다.
이는 공개 퀴즈 응답의 누출 방지이며 일반 논문 질의로 정답을 추론하는 것까지 차단하는 정책은 아니다.

제출 예시:

```json
{
  "context_id": "context-example",
  "step": "preview",
  "quiz_id": "quiz-example",
  "request_key": "submission-example",
  "answers": [
    {"question_index": 0, "selected_index": 1},
    {"question_index": 1, "text": "사용자 답안"}
  ]
}
```

- JSON 객체의 문자열 키를 정수로 암묵 변환하지 않고 배열을 검증한 뒤 내부 매핑으로 바꾼다.
- 문항·선택지 index는 0부터 시작하는 정수이며 불리언·문자열·실수를 거부한다. 호스트의 표시 번호가 1부터라면 전달 전 명시적으로 변환한다.
- 객관식에는 selected_index, 단답형에는 text만 허용한다. 알 수 없는 필드·중복 문항·범위 밖 위치·유형에 맞지 않는 답안을 거부한다.
- 답하지 않은 문항은 배열에서 생략한다. null 답안은 거부한다. 공백 문자열의 거부 여부는 B/C 협의 후 확정하며, 준비 코드에서는 명시적인 정책 설정으로 받는다.
- 빈 배열은 기존 서비스와 동일하게 거부한다. 전 문항 무응답 제출 지원은 별도 합의 없이는 추가하지 않는다.
- request_key는 공백만 있는 값 거부, 최대 200자라는 기존 MCP 규칙을 따른다. 각 ID도 빈 문자열을 거부한다.
- 문항 수·단답 길이·전체 요청 크기 제한값은 B와 확정한다. 길이 초과 답안을 조용히 잘라 채점하지 않는다.

## 중복 제출과 재생성 경쟁

요청 키는 A의 2026-10-30 협의 답변에 따라 동일 DB 내에서 유일하게 관리한다.
동일 입력 판정에는 context_id·step·quiz_id·답안을 포함한다.
문항 순서는 정렬해 비교하되 답안 문자열을 채점용으로 정규화한 뒤 비교하지 않는다.
같은 점수를 받는 다른 입력도 같은 요청으로 간주하지 않는다.

저장 경계의 합의 방향(실제 저장 구현은 A/B 담당):

1. 입력 형식을 검증하고 요청 입력의 일관된 비교값을 만든다.
2. 같은 키의 완료 기록이 있으면 같은 입력은 기존 attempt를 반환하고 다른 입력은 충돌로 거부한다.
3. 완료 기록이 없다면 제출 quiz_id와 context·step의 현재 퀴즈 일치를 확인한다.
4. 채점한 퀴즈가 저장 시점에도 유효한지 원자적으로 확인하고 시도·요청 기록을 함께 저장한다.
5. 다른 요청이 먼저 저장했다면 유일성 충돌을 재조회하여 같은 입력은 기존 결과로 반환한다.

2번을 최신 퀴즈 검사보다 먼저 적용하여, 제출 성공 후 퀴즈가 재생성되어도 같은 요청의 재전송은 기존 결과를 받는다.
이미 완료된 요청이 없는 오래된 quiz_id는 `QUIZ_CHANGED`로 거부하며 최신 퀴즈로 바꾸어 채점하지 않는다.
조회 후 저장 사이의 재생성은 C의 사전 조회만으로 막을 수 없다. A의 DB 제약·트랜잭션과 B의 버전 검증이 필요하다.
실패 시 불완전한 시도나 재시도를 막는 예약 기록이 남지 않아야 한다.
초기 구현에는 예약 테이블을 두지 않는다. 저장 결과는 SAVED / REUSED_EXISTING / REQUEST_CONFLICT / QUIZ_CHANGED와 attempt로 구분하는 방향이다. 프로세스 메모리 캐시만으로 멱등성을 구현하지 않는다. 구체적인 Python 타입과 B 서비스 오류 매핑은 후속 연결 때 맞춘다.

## 응답·오류·호스트 안내

- 제출 출력 제안: `attempt_id`, `context_id`, `quiz_id`, `step`, `submitted_at`, `correct_count`, `total_count`, `score`, `results`, `reused`.
- score는 기존 모델의 0~1 비율을 유지한다. 재전송 시 attempt_id·점수·제출 시각·문항 결과는 동일하며 reused만 달라질 수 있다.
- 문항 결과는 제출 당시 스냅샷을 사용한다. 제출 후에는 답안·정답·채점 기준·근거 ID를 반환할 수 있다.
- 상세·복습 조회는 attempt가 요청 context에 속하는지 검사한다. 기존 서비스는 attempt_id만 받으므로 B 계약 또는 C 어댑터의 추가 검증이 필요하다.
- 이력 목록은 답안·정답 전체 대신 시도 요약을 반환한다. 기본 20개, 최대 100개와 안정적인 커서 순서를 제안한다. 현재 history는 전체 목록이므로 B/A 조회 계약을 먼저 확인한다.
- 단계별 점수에서 시도 없는 단계는 기존 null 값을 유지한다. 저장하지 않은 실패 제출을 시도 수에 포함하지 않는다.
- 현재 준비 코드의 오류 코드: `INVALID_ARGUMENT`, `NOT_FOUND`, `QUIZ_NOT_READY`, `QUIZ_CHANGED`, `REQUEST_CONFLICT`, `INTERNAL_ERROR`. 운영 MCP 오류 매핑은 아직 연결하지 않았다.
- `SUBMISSION_IN_PROGRESS`는 현재 지원하지 않는다. 초기 구현에 예약 테이블을 두지 않는 방향이므로, 진행 중 제출을 별도 상태로 노출할 필요가 생기면 A/B/C 후속 협의로 상태 판정과 응답 계약을 정한다.
- 예외 원문·답안·정답·키를 오류나 진단 로그에 넣지 않는다. 구체적인 코드 매핑은 A·B 예외 계약과 함께 확정한다.
- 통신 결과가 불명확하면 같은 키·같은 입력으로 재조회 효과를 얻도록 재전송한다. 사용자에게 묻지 않고 새 키로 다시 제출하지 않는다.
- 의도적 재응시만 새 키를 사용한다. 오래된 퀴즈 오류 시 자동 재생성·재제출하지 않는다.
- 단답형은 정규화 후 완전 일치라는 점을 안내한다. AI 의미 채점, AI 해설, 단계 자동 완료는 추가하지 않는다.

## 담당 및 구현 순서

| 담당 | 변경 예상 영역 | 먼저 확정할 계약 |
|---|---|---|
| A | database/schema.py, repository.py | 요청 키 저장·유일성, 시도와 원자적 저장, 퀴즈 재생성 경쟁, 기존 DB 이관 |
| B | application/quiz/attempts.py, domain/quiz_attempt.py | quiz_id·request_key를 받는 제출 인터페이스, 오류·재사용 결과, 조회 범위·페이지 처리 |
| C | interfaces/mcp/server.py 및 응답 변환·오류·호스트 지침·테스트 | 공개 응답 허용 목록, JSON 답안 변환, MCP 도구 연결 |

계약 검토 → A 저장 보완 → B 제출 연결 → C 도구 연결 → Desktop 검증 순서로 제안한다.
C의 공개 문항 변환·입력 검증은 계약 확정 후 독립 구현할 수 있지만, 제출 도구 활성화는 A·B 안전성 구현 후에 한다.
현재 C 준비 코드는 운영 서버에 연결하지 않으며 A/B 파일을 수정하지 않는다.

## 2026-10-31 준비 범위

- `interfaces/mcp/quiz_contracts.py`: 공개 퀴즈·제출·시도 상세의 입력/응답 모델, 이력 목록의 초안 모델, 대역용 서비스 포트와 변환 어댑터.
- `tests/unit/mcp/test_quiz_contracts.py`: 입력 거부, 정답 필드 제외, 답안 문자열과 요청 키 보존, 재사용 결과 전달, 다른 context 차단, 안전한 오류 및 운영 도구 미등록 확인.
- 문항 수·단답 길이·빈 문자열 정책은 `InputPolicy`로 명시한다. 테스트의 10문항/100자 설정은 운영 한도가 아니다. 전체 요청 크기, 실제 문항/선택지 범위와 답안 유형의 적합성은 후속 서비스 연결에서 검증해야 한다.
- 이력의 기본 20개/최대 100개는 여전히 제안이다. 목록 서비스 연결·커서 처리, 단계별 점수·복습의 응답 모델과 도구 연결은 후속 범위다.
- 대역이 반환한 기존 결과를 C가 그대로 전달하는지 검증한다. DB 동시성·재시작·원자성이나 실제 멱등성이 구현됐다는 의미는 아니다.
- 완료 요청 재사용을 막지 않도록 C에서 최신 퀴즈를 먼저 조회하지 않는다. 신규 요청의 퀴즈 검증은 A/B 저장 경계에서 수행한다.
- 자동 테스트: 32개 통과. 객관식 정답 위치 제외와 시도 상세의 제출 당시 스냅샷 반환을 포함한다. MCP 도구를 통한 실제 호출 및 Desktop 검증은 A/B 연결 후 진행한다.

## 검증 체크리스트

- 공개 문항의 structuredContent와 text 모두 정답·채점 기준·정답 근거를 포함하지 않음.
- 객관식·단답형·누락 답안, 빈 배열, 중복 문항, 불리언 index, 알 수 없는 필드 검증.
- 다른 context·step·quiz_id 및 저장 사이 재생성에서 오채점·시도 저장 없음.
- 같은 키·같은 입력의 동시 요청·응답 유실·재시작 후 재전송에서 시도 하나만 유지.
- 재생성 후 완료 요청 재전송은 기존 결과 반환, 같은 키·다른 입력은 충돌, 새 키 재응시는 허용.
- 채점·저장 실패에서 부분 기록 없음, 과거 시도·오답 근거 조회 및 기존 DB 이관 회귀 확인.
- 다른 context의 attempt 상세·복습 접근 거부, 목록 순서·커서 및 시도 없는 단계 점수 확인.
- 외부 API 없는 자동 테스트 후 테스트 context로 Claude Desktop 조회·제출·결과·복습·재전송 확인.

문서와 실제 서비스 인터페이스의 합의가 끝나기 전에는 이 계약을 구현 완료나 #110 종료 근거로 사용하지 않는다.
