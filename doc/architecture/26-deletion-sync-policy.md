# 삭제 동기화와 tombstone 계약

이 문서는 #368의 A 저장 계약이다. 로컬 행 제거, 동기화 중지, 동의 철회,
서버 논문 삭제와 계정 삭제를 같은 동작으로 취급하지 않는다.

## 의도와 효과

| 의도 | 서버 물리 삭제 | 새 전송/처리 | 기존 결과 조회 |
|---|---:|---:|---:|
| `local_only` | 없음 | 기존 동의에 따름 | 서버 정책에 따름 |
| `stop_sync` | 없음 | 중지 | 유지 |
| `revoke_consent` | 없음 | 새 유료 처리·전송 금지 | 별도 보존 정책에 따름 |
| `server_paper` | 명시적 삭제 요청 | 즉시 금지 | 삭제 상태만 비공개 형태로 반환 |
| `account` | 소유 데이터 전체 삭제 요청 | 즉시 금지 | 인증 종료 뒤 불가 |

클라이언트의 로컬 삭제를 서버 삭제로 추정하지 않는다. 서버 삭제는 인증된 사용자에게
범위와 비가역 효과를 보여 준 뒤 별도 요청 키로 접수한다.

## 순서와 재시도

1. owner와 대상에 tombstone을 설정해 모든 신규 저장·게시를 차단한다.
2. queued/running 작업을 취소하고 lease generation을 폐기한다.
3. 검색 색인, 파생 리비전, 저장 근거·메모 등 자식 데이터를 멱등 삭제한다.
4. PDF/R2 원문과 부모 레코드를 멱등 삭제한다.
5. tombstone과 삭제 요청 상태는 복원 가능한 모든 백업보다 오래 보존한다.

각 단계는 완료 표식을 별도로 저장한다. 부분 실패는 완료되지 않은 단계부터 재개하며,
이미 사라진 객체는 성공으로 취급한다. tombstone보다 먼저 실제 데이터를 삭제하지 않는다.

## 충돌과 부활 방지

- 늦은 기기의 수정·재전송은 tombstone보다 오래됐는지와 무관하게 거부한다.
- 삭제 뒤 같은 로컬 ID가 다시 오면 기존 서버 ID를 부활시키지 않는다. 사용자가 새 등록을
  명시하면 새 서버 ID와 새 요청 키를 만든다.
- worker는 저장 직전에 owner, 대상, 실행 세대와 tombstone을 같은 트랜잭션에서 다시 검사한다.
- 백업 복원 뒤에는 운영 트래픽을 열기 전에 별도 보관한 tombstone journal을 재적용하고
  삭제 작업을 다시 실행한다.

## 보존 기간 결정 gate

`30일`은 승인된 값이 아니다. `tombstone_retention_days`, `backup_expiry_days`,
`account_erasure_days`가 모두 명시되고 tombstone 기간이 백업 만료보다 짧지 않을 때만
물리 정리 스케줄을 활성화한다. 값이 없으면 신규 쓰기 차단과 작업 취소까지만 수행하고,
정책 미승인 상태를 운영 점검에 노출한다.

## 후속 연결

- #394: DB·pgvector·R2 단계별 물리 삭제와 복원 훈련
- #400: 백업 만료, 운영 스케줄, 알림과 책임자
- C: 사용자 확인 화면, 삭제 진행·부분 실패·완료 표시

동기화 중지나 동의 철회를 삭제 완료로 표시하지 않으며, 실제 물리 삭제가 끝나기 전에는
사용자에게 완료를 반환하지 않는다.

## 삭제 worker lease·세대 계약 (#468)

A 처리 작업과 동일하게 새 claim마다 lease token과 attempt를 발급한다. `cleaning` 중
lease가 만료되면 같은 request를 새 세대로 재접수하며, 이전 토큰의 heartbeat·단계 실행·
완료·실패 기록은 거부한다. TTL은 서비스 생성 시 명시적으로 주입하며 운영 기본값을 정하지 않는다.
이전 버전의 lease 없는 cleaning 행도 회수한다. 기존 마이그레이션은 바꾸지 않고 0030을 추가한다.

단계 실행은 작업 행 잠금 획득 후 실시간 만료·owner·논문·token·attempt를 검사한다.
동기 backend 호출과 단계 완료 표식 저장까지 잠금을 유지하므로 해당 호출 중에는 SKIP LOCKED
재접수가 일어나지 않는다. 파생 데이터 완료 표식 후에만 원문 삭제를 실행하며, 완료된 단계는
재시작 후 건너뛴다. 전체 완료 기록 실패는 lease 만료 후 같은 작업을 재접수해 복구한다.

backend는 고정 owner/paper ID의 멱등 삭제여야 하며 객체 부재는 성공이다. 반환 전에 삭제를
끝내고, 비동기 작업을 띄운 뒤 먼저 반환하거나 다른 스레드에서 동일 작업의 lease를 갱신하지 않는다.
현재 서비스는 단계 시작 전 heartbeat를 갱신한다. 각 backend의 제한 시간은 주입된 lease보다
짧게 구성해야 한다. 단계가 이를 초과하면 완료 표식을 기록하지 않으며 안전하게 재시도한다.
DB 연결 유실 후 이미 전송된 외부 삭제의 결과는 되돌릴 수 없다. 따라서 객체 키는 재사용하지 않고
같은 고정 대상의 삭제 재시도를 허용해야 한다. 외부 부작용의 정확히 한 번 실행을 보장하지 않는다.
실제 R2·DB backend 연결, 운영 TTL/시간 제한, 물리 삭제·백업 복원 실측은 별도 범위다.

논문 부모 행과 tombstone/request는 보존하며 backend가 이를 먼저 지우지 않는다.
단계 표식과 오류 응답에는 원문·토큰·객체 key 대신 안전한 상태만 저장한다.
