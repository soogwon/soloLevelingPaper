# #99 로그 보관 계약과 검증 계획 — C 협의안

## 2026-11-07: Windows MCP 기본·상세 로그

로컬 고정 NTFS 드라이브에서 실행마다 새 잠금 파일을 만들고 `LockFileEx`로
비차단 배타 잠금을 잡는다. inspector는 기존 잠금 파일만 연다. 드라이브부터
로그 폴더까지 디렉터리 핸들을 유지하고 재분석 지점은 거부한다. 지원되지 않는
경로나 잠금 실패 시 서버는 해당 파일 로그 없이 요청 처리를 계속한다.

지연 작업 종료, stderr 복원, 로그 flush·닫기 후 파일 식별값과 크기를 대조한다.
종료 JSON은 같은 디렉터리에서 fsync한 임시 파일의 열린 핸들로 이름을 변경해
게시하며 기존 이름은 덮어쓰지 않는다. identity는 `platform=windows` 및
`st_dev`, `st_ino`, `st_size`다. 강제 종료 시 종료 기록은 없고 재시작은 새 묶음을 만든다.
원본·스택 수집과 worker 종료, 보관 기간에 따른 정리는 별도 범위다.

## 2026-11-05: Windows 기반 검증

최신 main의 공통 계약을 유지하고, Windows/NTFS에서 잠금·미상속·파일 동일성·
무덮어쓰기 게시를 합성 테스트로 확인했다. 종료 정리·경쟁 게시 보완 후 관련 회귀
246개 통과, symlink 권한 부족
1개 건너뜀. [결과와 어댑터 구현 전 확인 사항](../history/log-retention-windows-validation.md)을
참고한다. 실제 OS 어댑터·생산자 연결·삭제 기능은 아직 제공하지 않는다.

## 2026-11-05: POSIX MCP 안전 로그 생성·종료 연결

`infrastructure/log_retention/posix.py`에 비차단 flock 잠금과 종료 게시를 구현했다.
macOS/Linux의 기본·상세 MCP 진단 실행기는 새 safe/detail 이름으로 파일을 만든다.
Windows와 원본 수집 모드는 기존 파일명·동작을 유지한다. worker 연결은 A의 후속 범위다.

- writer는 새 UUID의 잠금 파일을 배타 생성한다. 이전 UUID는 재사용하지 않는다.
  inspector는 기존 잠금 파일만 열며 파일을 만들지 않는다. 잠금 파일은 해제 후에도 유지한다.
- 루트의 상위 디렉터리부터 디렉터리 핸들로 열고 심볼릭 링크를 거부한다.
  잠금 직후와 게시 직전에 루트 및 잠금 파일의 장치·inode 동일성을 다시 확인한다.
- 파일은 소유 lease에서 배타 생성하고 일반 파일·단일 링크 여부와 생성 당시 identity를 확인한다.
  기본·상세 로그의 네이티브 stderr는 기존처럼 폐기된다.
- cleanup_scope의 지연 작업 정리 → stderr 복원 → 로그 flush/fsync·close → 종료 JSON 게시 → 잠금 해제 순서다.
  알려진 출력 스트림이 열려 있으면 게시를 거부한다. fork가 발생하면 부모의 게시 자격을 보류하고
  자식의 잠금·루트 핸들을 닫는다. 상속될 수 있는 추가 writer의 종료를 추정하지 않는다.
- 게시 파일은 임시 파일 write/flush/fsync 후 같은 디렉터리의 link로 생성해 기존 종료 기록을 덮어쓰지 않는다.
  임시 링크 정리까지 성공해야 published를 반환한다. 실패·중단으로 링크 수가 2인 경우는 후속 검사에서 제외해야 한다.
- 잠금·새 파일 생성 실패 시 새 규약 로그를 생성하지 않고 진단 출력은 폐기한다.
  안전 로그 쓰기·동기화 실패 또는 종료 게시 실패는 요청 결과를 보존하고 종료 기록을 확정하지 않는다.
  원문을 다른 파일이나 stderr로 우회하지 않는다.
- 추가 검토에서 로그 폴더 생성 실패와 잠금 해제 오류가 요청 종료 코드를 바꾸던 경로를 보완했다.
  폴더 생성은 writer만 디렉터리 핸들 기준으로 수행하며 inspector는 누락된 폴더도 생성하지 않는다.
  임시 링크 정리가 실패하면 재시도로 정상 종료 형태로 승격하지 않고 두 링크를 남긴다.
  메타데이터 스트림 생성 실패 시 열린 fd를 닫고, lease 해제는 한 핸들 오류에도 나머지 핸들 정리를 시도한다.

### identity 구현값과 합의 경계

이 POSIX 생산자는 identity를 `{"platform":"posix","st_dev":정수,"st_ino":정수,"st_size":정수}`로 기록한다.
A/B가 제안한 장치·inode·크기 후보를 구체화한 생산자 구현값이며, Windows 공통 소비 계약의
확정을 뜻하지 않는다. 공통 JSON 파서는 이전과 같이 identity 존재만 확인한다.
미리보기는 종료 JSON을 읽지 않으며 모든 activity는 unknown으로 유지한다.
원본·스택·worker·Windows 새 규약 연결과 실제 OS 동일성 검사 후에 소비 계약을 확정해야 한다.

### 검증과 제한

macOS에서 잠금·미리보기·정책·안전 필터·MCP 실행 및 지연 종료 회귀 274개가 통과했다.
독립 프로세스의 잠금 경합과 해제 후 재획득, 파일·잠금 교체, 상위 심볼릭 링크 거부,
fork 이후 게시 보류, 무덮어쓰기 게시, 지연 종료 전 미게시, 실패 시 stdout·요청 결과 보존을 확인했다.
임시 파일과 합성 서버만 사용했다. Linux/Windows 실행, 실제 Claude Desktop 및 새 wheel 설치 검증은 남아 있다.

이 메타데이터는 프로그램 간 협력 계약이다. 같은 사용자 권한의 악성 writer나 임의 복제 핸들,
동일 inode의 같은 크기 내용 변경을 인증하지 않는다. 로그 루트를 신뢰된 사용자가 관리해야 한다.
전원 장애 내구성, 미지원 파일시스템, 루트/파일 교체의 모든 시점과 별도 프로세스의 동시 게시에 대한
추가 검증도 남아 있다. 파일 순환·삭제·용량 강제 제한은 후속 범위이며 #99를 열어둔다.

### 공통 JSON 검사의 한계

최대 입력은 UTF-8 16 KiB, 파일 항목은 1~4개로 제한한다. 중복 JSON 키, 추가 필드,
중복 종류, owner/run_id 불일치, 잘못된 이름·시각·크기·버전은 거부한다.
closed_at은 `Z`로 끝나는 UTC 시각이며 소수초는 최대 6자리다.

파일 동일성 형식은 실제 OS 어댑터 검증 때 확정하기로 한 합의를 유지한다.
공통 검사는 `identity` 필드의 존재만 확인하며, 특정 값이나 형식을 강제하지 않는다.
내용은 검증하거나 요약 결과에 보관하지 않는다. 테스트의 `null`과 임의 값은 합성 자료이며
실제 생산자가 게시할 형식으로 승인된 것이 아니다. 표준 JSON이 아닌 NaN·Infinity는 거부한다.
`MetadataSummary`는 공통 필드 요약일 뿐 파일의 존재·동일성·실제 종료를 증명하지 않는다.
후속 OS별 검증기는 잠금 아래 원본을 다시 읽고 동일성을 검증해야 하며, 이 요약으로 대체할 수 없다.
현재 `BundlePublisher`의 파일 인자도 이름·종류·크기 정보만 담으며, 실제 게시 구현은
유효한 lease 아래에서 OS 동일성 정보를 수집·검증하도록 연결해야 한다.

기간 판정 결과는 expired / retained / raw_excluded / future_timestamp / unknown이다.
expired는 기간 경과만 뜻하며 삭제 가능 상태가 아니다. 기본 기간은 30/7/1일이고,
순수 함수 설정값은 1~36,500일 정수로 제한한다. CLI의 기존 `--review-days`는
mtime 기준 검토 표시이므로 이 종료 시각 기반 판정과 혼동하지 않는다.
메타데이터를 읽지 않는 CLI에 새 만료 판정을 아직 연결하지 않았다.

## 1. 새 파일명과 종류

새 규약은 `slp-log-v1-<owner>-<kind>-<run_id>.log`를 제안한다.

| 항목 | 허용 값 |
|---|---|
| owner | `mcp`, `worker` |
| kind | `safe`, `detail`, `raw`, `stack` |
| run_id | 매 실행 새로 생성한 UUID의 소문자 32자리 16진수 |

종류는 생성 시 선택하며 실행 중 모드를 변경하지 않는다. 예를 들어 worker 원본·스택은
동일 run_id로 묶되 서로 다른 파일로 생성한다. worker 상세 모드는 현재 없으므로
`worker-detail`은 최초 버전에서 생성하지 않는다.
기존 `mcp-*`, `worker-*`, `import-stack-*` 파일은 새 규약의 정리 대상으로 편입하지 않는다.
기존 파일은 미리보기에서 별도 표시할 수 있지만, 본문을 읽어 종류를 추측하지 않는다.

## 2. 실행 묶음과 종료 증명

로그 본문 대신 `slp-log-v1-<owner>-<run_id>.closed.json`을 사용한다.
메타데이터는 해당 실행의 **모든 쓰기 주체와 핸들이 정리된 뒤** 소유자만 게시한다.

제안 필드는 `schema_version=1`, `owner`, `run_id`, `closed_at`(UTC), `files`다.
files 항목은 `kind`, `name`(루트 아래 파일명만), `size_bytes`와 OS별 파일 동일성 정보를 가진다.
절대 경로, 요청·논문 식별자, 키, 본문, 원본 예외, 사용자 입력은 넣지 않는다.
필드·타입·개수·길이·전체 크기(예: 16 KiB 이내)를 제한하고, 미지원 버전·추가 필드는 제외한다.
파일명은 owner/kind/run_id로 다시 계산해 비교하며 메타데이터가 지정한 임의 경로를 따라가지 않는다.

1. 소유자가 실행 ID와 파일 묶음을 만들기 **전에** 해당 묶음의 OS 잠금을 확보한다.
2. 파일을 새로 생성한다. 기존 파일을 덮어쓰거나 이전 run_id를 재사용하지 않는다.
3. 종료 시 출력 생산자 중단 → 남은 작업·자식 종료 확인 → 타이머/스택 출력 중단 →
   스트림 flush 및 로그를 참조하는 모든 fd/핸들 정리를 수행한다.
4. 크기·파일 동일성을 기록한 종료 메타데이터를 같은 디렉터리의 임시 파일에서 원자적으로 게시한다.
   이후에는 해당 묶음에 다시 쓰지 않는다. 게시가 실패하면 종료 증명 없는 파일로 남긴다.
5. 잠금을 해제한다. 정리 도구도 같은 묶음의 배타 잠금을 확보한 뒤 종료 메타데이터와 파일을 재검증한다.

잠금 파일은 존재 자체가 활성 증거가 아니다. 잠금 파일을 삭제·재생성해 서로 다른 잠금 대상으로
갈라지는 경쟁을 피하도록 최초 구현에서는 유지한다. 잔류 잠금 파일 수와 정리 방안은 별도 한계로 기록한다.
POSIX와 Windows 잠금 방식은 동일 인터페이스 뒤에 두고 실제 OS에서 검증한다.
잠금·파일 동일성·안전한 경로 접근을 지원하지 못하는 환경에서는 **삭제를 비활성화**한다.

### 소유자별 종료 책임

- **MCP(C):** #121의 지연 작업과 자원 정리가 끝난 뒤 stderr 복원·로그 핸들 종료까지 확인하고
  메타데이터를 게시한다. lifespan 반환 시점이나 종료 시작 시점에는 게시하지 않는다.
- **worker(A):** 자식 내부의 마지막 한 줄은 진단 정보로만 취급한다. 부모는 `join` 등으로
  프로세스 종료와 쓰기 핸들 정리를 확인한 뒤 메타데이터를 게시하는 안을 검토한다.
  직접 worker 실행·추가 자식·상속 핸들처럼 확인할 수 없는 경로는 종료 증명을 만들지 않는다.
- **비정상 종료:** 부모가 종료를 확인하고 모든 작성자가 끝났음을 보장할 수 있을 때만 게시할 수 있다.
  부모까지 죽거나 writer가 남을 수 있으면 unknown으로 제외한다. PID 재사용·오래된 mtime은 증거가 아니다.

종료 메타데이터는 로컬 프로그램 간 계약이며 같은 사용자 권한의 악성 프로세스를 인증하는 수단은 아니다.
로그 폴더에 쓰기 권한을 가진 프로세스가 모두 이 규약을 지킨다는 한계를 문서화한다.

## 3. 보관 기간·용량·설정

| 종류 | 보관 기간 후보 | 최초 정리 선택 |
|---|---|---|
| safe | 30일 | 명시적 정리 실행 시 기본 대상 |
| detail | 7일 | 명시적 정리 실행 시 기본 대상 |
| raw, stack | 1일 | 별도 `--include-raw` 선택 필요 |
| 기존/미지원/활성·종료 불명 | 해당 없음 | 제외 |

만료 계산은 검증된 `closed_at`을 기준으로 한다. 미래 시각·잘못된 시각·실행 중 크기 변경은 제외한다.
같은 묶음의 모든 파일이 선택 범위와 만료 조건을 충족할 때만 그 묶음을 정리 후보로 삼는다.
따라서 safe와 raw가 한 묶음이면 safe 기간까지 기다릴 수 있다는 보수적 한계가 있다.

100 MiB·100개는 **경고 및 검토 기준**이다. 넘었다고 활성 파일이나 보관 기간 이내 파일을 삭제하지 않는다.
인식한 파일 합계와 확인 불가/제외 파일 수를 따로 표시하며 디스크 전체 사용량이나 강제 상한으로 표현하지 않는다.
원본·스택은 최초 단계에서 순환하지 않는다. 실행 중 크기 제한은 미지원이다.

최초 설정은 정리 CLI의 명시적 인자와 문서화된 기본값으로 한정한다.
예: `--safe-days`, `--detail-days`, `--raw-days`, `--warn-bytes`, `--warn-count`.
양의 정수와 상한을 검증하고 0일 즉시 삭제는 허용하지 않는 안이다. 환경 변수·설정 파일과의 우선순위는
최초 범위에서 만들지 않는다. 서버 시작 시 자동 삭제하거나 원본 수집 기본 OFF를 바꾸지 않는다.

## 4. 미리보기와 실행 계약

아래 명령 형태는 제안이며 아직 실행 가능한 새 기능이 아니다.

1. 기존 `log_inventory`는 삭제 없는 관찰 도구로 유지한다. 새 메타데이터 검사는 제한된 별도 JSON만 읽으며
   로그 본문 미열람 원칙을 유지한다. 구형 파일은 계속 unknown이다.
2. 정리 도구는 기본값을 미리보기로 둔다. 사용자가 선택한 로그 루트 안에서 현재 후보·제외 이유·바이트 수를 표시한다.
3. 실제 삭제는 별도 `--apply` 실행을 요구한다. raw/stack 포함 여부는 추가 선택이며 자동으로 확대하지 않는다.
   이전 미리보기 결과를 삭제 권한이나 경로 목록으로 신뢰하지 않고 전부 다시 검증한다.
4. 각 묶음의 잠금 확보 후 루트·파일 종류·동일성·크기·종료 메타데이터·기간을 재검증한다.
   하위 디렉터리, symlink, Windows 재분석 지점, 하드 링크, 다른 종류 파일은 제외한다.
   경로 검사와 삭제 사이 교체 경쟁을 막을 수 있는 OS별 접근을 구현·검증하기 전에는 apply를 제공하지 않는다.
5. 로그 파일 삭제 후 종료 메타데이터를 마지막에 삭제한다. 여러 파일 삭제는 원자적이지 않다.
   부분 실패 시 남은 메타데이터를 보존하고 누락된 파일은 처리 완료로 인정하되,
   남은 파일은 다시 검증해 재시도한다. 다른 파일로 교체됐으면 제외한다.
6. 오류는 고정 코드·개수로 보고하고 임의 경로·원본 예외를 출력하지 않는다.
   CLI만 별도 stdout을 쓰며 MCP 통신 경로에서 실행하지 않는다.

종료 코드는 0=성공/정상 제외, 1=파일·잠금 I/O 등 부분 오류, 2=설정·루트·필수 플랫폼 기능 오류를 제안한다.
활성으로 잠긴 묶음은 정상 제외이며, 접근 실패와 구분한다. 모든 unknown 로그는 자동 정리하지 않고
별도 운영 안내에서 사용자가 프로그램 종료·백업·대상을 확인한 뒤 수동 관리하도록 한다.

## 5. 담당과 구현 순서

| 담당 | 범위 |
|---|---|
| A | worker 새 이름, 실행 묶음·부모 종료 확인, 네이티브·스택 writer 정리 |
| C | 공통 메타데이터/잠금 인터페이스 제안, MCP 생성·종료, 미리보기·명시적 정리 CLI |
| B | 안전 로그 필드·본문 미기록, 답변·오류 처리 영향 검증 |
| 공동 | 잠금 구현 위치·API, 종료 증명 주체, 기간·경고 기본값, OS별 지원 범위 확정 |

1. A·B가 위 파일명·메타데이터·종료 책임·설정 후보를 검토한다.
2. #121·#123 및 기존 미리보기 브랜치의 통합 상태를 확인한다.
3. 공통 계약과 읽기 전용 검사 테스트부터 구현한다. A worker/C MCP 생산자는 그 계약에 연결한다.
4. 새 파일 생성·종료 메타데이터·미리보기를 검증한 뒤 별도 변경으로 apply를 구현한다.
5. 실제 OS 검증 후 자동 정리·순환이 필요한지 별도로 결정한다. 이 문서만으로 #99를 종료하지 않는다.

## 6. 테스트 계획과 승인 기준

| 사례 | 합격 기준 |
|---|---|
| 새/구형 이름, 안전/상세/원본 | 새 규약만 종류 확정, 기존 파일과 미지원 조합은 제외 |
| 메타데이터 검증 | 임의 경로·추가 필드·과대 JSON·틀린 ID·미지원 버전 거부, 로그 본문 읽기 없음 |
| 정상/지연 종료 | 마지막 worker·스택·네이티브 쓰기 종료 전 closed 메타데이터 없음 |
| 강제 종료·부모 종료·PID 재사용 | 확인 불가 파일은 제외, mtime/PID로 승격하지 않음 |
| 동시 실행·중복 정리 | 같은 묶음 잠금 배타성, 활성 파일 무삭제, 잠금 객체 교체 방지 |
| 검사 직후 경로 교체 | 링크·재분석 지점·하드 링크·루트 교체에도 로그 루트 밖 무접근 |
| 파일 변경·미래 시각·기간 경계 | 실행 직전 재검증, 새 쓰기 발견 시 제외, 종류별 만료 경계 정확 |
| 원본 포함 선택 | 기본 미리보기/적용이 원본 묶음을 삭제하지 않음 |
| 삭제 실패·부분 완료·재실행 | 종료 메타데이터 보존, 남은 파일만 재검증, DB/PDF/색인 무변경 |
| 디스크·메타데이터·잠금 쓰기 실패 | 본문 미노출, MCP 응답 보존, 종료 확인을 성공으로 위장하지 않음 |
| 경고 기준 초과 | 경고만 발생하며 활성/unknown/미만료 파일 무삭제 |
| macOS/Linux/Windows | 실제 파일 잠금·종료·재접근 확인, 미지원은 명시적 제외 또는 apply 비활성 |

테스트는 임시 디렉터리·합성 문자열·로컬 자식 프로세스만 사용한다. 실제 로그·사용자 DB·API는 사용하지 않는다.
시계·종료 순서는 제어 가능한 시계와 이벤트로 검증한다. 삭제 구현 전에는 미리보기가
파일 내용·크기·수정 시각을 바꾸지 않는지부터 확인한다.
