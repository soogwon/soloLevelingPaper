# #388 후속 인증 검증: A 협의용 준비사항

작성일: 2026-11-16. 상태: 협의 초안, 환경 생성·권한 확대 미승인.
자동 갱신과 독립 PKCE refresh 재사용 거부는 [실측 기록](remote-mcp-staging-validation.md)을 따른다.
이 문서는 남은 실발급 토큰 거부·두 계정 검증을 위한 준비 요청이다.

## A에게 확인할 사항

| 확인 항목 | 필요한 결정·준비 | 완료 증거 |
|---|---|---|
| 테스트 계정 2개 | 실제 논문·학습 기록이 없는 전용 계정 A/B, 서로 다른 subject. 로그인은 계정 담당자가 직접 수행 | 두 계정 구분용 별칭과 담당자만 기록 |
| 격리 환경 | 기존 웹과 Claude 설정에 영향을 주지 않는 인증 검증용 배포를 우선 사용. 공유 staging을 쓰면 변경 항목·시간·복원 담당 확정 | 공개 URL, 배포 SHA, 원래 설정의 비밀정보 없는 기록 |
| 정상 발급 client | PKCE S256·정확한 loopback callback, 사용자 위임 code grant, 전용 audience·spike:read. 해당 검증 배포만 client allowlist에 추가 | 정상 initialize/tools/list/whoami 성공 |
| 비허용 client | 정상 client와 같은 issuer/audience/scope의 사용자 토큰을 발급하지만 검증 배포 allowlist에는 넣지 않음 | 정상 대조군은 성공하고 이 client만 401 |
| scope 부족 | 정상 client에서 spike:read를 요청하지 않은 토큰 발급이 가능한지 확인. Auth0가 권한을 자동 추가하는 설정 확인 | 실제 발급 scope에 spike:read가 없다는 로컬 boolean 검사 |
| 다른 audience | 같은 client·issuer에서 별도 테스트 API audience의 토큰을 발급할 수 있는지 확인 | audience 불일치 및 다른 필수 조건 검사 결과 |
| 다른 issuer | 별도 테스트 issuer 필요 여부 결정. 신뢰 JWKS에 없는 키로 발급하면 서명 단계에서 거부될 수 있음 | 외부 issuer 토큰 거부와 issuer 조건 단독 검증을 구분 |
| 웹·기기 토큰 | 기존 사용자의 토큰을 수집하지 않고 전용 테스트 계정으로 발급 가능한 경로 준비 | 발급 경로·토큰 종류만 기록, 제품 MCP 401 |
| 짧은 만료 | 검증용 API에 한해 짧은 TTL 설정. 자동 refresh를 하지 않는 로컬 검사로 만료 전후 비교 | 동일 access token의 만료 전 성공·만료 후 401 |
| 정리 | 발급 자격·grant 회수, 임시 client 삭제, API 설정 복원, 테스트 배포 종료 담당 확정 | 관리 화면 및 재조회로 잔존 여부 확인 |

기존 Claude client의 secret·토큰을 추출하거나 기존 웹의 issuer/audience/검증 정책을
완화하지 않는다. 새 client 등록과 allowlist 변경은 실행 전 승인받는다. 위 환경의
생성·변경은 이 문서를 작성했다는 이유만으로 승인된 것이 아니다.

## 실행 순서와 판정표

모든 요청은 정확한 공개 Host·Origin 경계를 사용한다. Host 421/Origin 403 또는
session 400이 먼저 발생한 요청을 토큰 검증 성공/실패 증거로 쓰지 않는다.
최신 배포 SHA와 결과를 기록하고 정상 대조군부터 실행한다.

| 순서 | 사례 | 기대 결과 | 판정 시 주의 |
|---|---|---|---|
| 1 | 허용 client, 계정 A의 유효한 사용자 access token | initialize/tools/list/whoami 성공 | 이 기준이 실패하면 후속 거부 사례의 원인 판정 중단 |
| 2 | 같은 조건의 계정 B | 동일 최소 도구 성공 | whoami는 사용자 ID를 반환하지 않으므로 두 계정 구분 증거로 단독 사용 금지 |
| 3 | 무토큰·무효 문자열 | 401 및 metadata 안내 | 이미 실측했으나 새 배포의 기준선으로 확인 |
| 4 | 같은 access token의 만료 전후 | 성공 → 401 | 클라이언트 자동 갱신을 끄고 실제 exp 경과 확인. 토큰을 수정하지 않음 |
| 5 | 같은 issuer/client/audience, scope 부족 | 401 | 현재 검증기는 부족한 scope도 401로 거부. 서명·만료·client 통과를 별도 확인 |
| 6 | 비허용 client, 나머지 정상 | 401 | audience/scope 오류와 섞지 않음 |
| 7 | 다른 audience의 유효한 토큰 | 401 | Auth0 발급 정책상 scope도 달라지면 복합 거부 시험으로 표시 |
| 8 | ID token | 401 | audience·필수 claim 차이 등 여러 조건의 거부이며 단일 typ 검사의 증거는 아님 |
| 9 | 기존 웹/기기/M2M 경로의 테스트 토큰 | 401 | 종류별 발급 경로 기록. typ·issuer·audience·client 중 먼저 실패한 이유를 단정하지 않음 |
| 10 | 다른 issuer의 실제 서명 토큰 | 401 | 신뢰 JWKS가 달라 키 조회/서명에서 먼저 거부될 수 있음. issuer 단독 회귀는 대역 서명 테스트와 병행 |
| 11 | 정상 A/B 토큰 + 합성 Mcp-Session-Id | 400 | 현재 stateless 스파이크는 모든 session ID를 거부. 다른 사용자의 세션을 훔치는 시험과 다름 |
| 12 | 정상 인증 + allowlist 밖 도구명 | MCP 프로토콜 수준 거부 | HTTP 상태만 보지 않고 오류 응답·부작용 없음 확인 |
| 13 | 정상·거부 요청 로그 표본 | 토큰·subject·client·요청 본문 비노출 | Auth0 관리 로그의 계정 감사 정보와 제품 응답/Render 로그를 구분 |

## 두 계정 검증의 경계

현재 whoami는 인증 성공과 환경만 반환하며 계정별 저장 데이터를 읽지 않는다.
두 계정으로 로그인·도구 호출이 가능하다는 사실만으로 사용자 데이터 격리를 통과 처리하지 않는다.
실발급 토큰을 서버 검증기에 전달하는 통제된 검사에서 서로 다른 verified identity인지
boolean으로 비교할 수 있지만, 원문 subject를 출력하지 않는다.

소유자별 자료 접근·교차 context·기존 세션 재사용은 실제 제품 경로의 준비 상태를
A와 확인하고 #399/#397과 연결한다. #388의 stateless 제약을 넘는 기능을 임시로 추가하지 않는다.

## 실행·정리 담당과 전달 형식

아래 담당 구분은 A와 확인할 제안이며, 계정·환경 준비를 이미 합의했다는 뜻이 아니다.

- A: 테스트 계정·발급 경로·issuer/JWKS·claim/권한 조건 확인, 격리 배포와 설정 변경 검토.
- C: 로컬 PKCE 검증기·HTTP/MCP 호출·결과 대조·Desktop 확인·비밀정보 없는 기록 작성.
- 배포/계정 담당자: 승인된 설정 변경과 자격 회수. C가 최종 설정·잔존 자격을 재조회.
- 전달할 내용: 환경 URL, 담당자, 계정 별칭 A/B, 준비 가능한 토큰 종류, 변경·정리 범위.
- 전달하지 않을 내용: 비밀번호·client secret·access/refresh/ID token·원문 subject.
- 토큰은 로컬 검증 프로세스 메모리에만 보관하고 승인된 Auth0/검증 MCP 목적지로만 전송한다.
  URL·로그·파일·클립보드·티켓에 넣지 않는다. JWT payload를 편집한 토큰은 실발급 조건 시험이 아니다.

완료 보고에는 입력 조건 충족 여부, HTTP/MCP 결과, 정상 대조군, 실패 원인과 한계를 함께 적는다.
검사 종료·실패·중단 시에도 자격 회수와 설정 복원을 먼저 확인한다. 서명된 access token의
즉시 철회를 제공하지 않는 경계는 남은 TTL과 함께 기록한다.
