## 취소 재현

`tests/unit/mcp/test_ask_cancellation.py`는 실제 `server.call_tool('ask_paper', ...)` 경로에 이벤트로 제어하는 가짜 답변 서비스를 연결한다. 외부 API·임베딩·DB는 사용하지 않는다.

- asyncio Task 취소: 호출 측은 취소되지만 이미 시작된 동기 스레드는 나중에 가짜 저장 단계까지 실행한다.
- AnyIO CancelScope 취소: 기본 `to_thread.run_sync`는 실행 중 동기 작업을 기다린다. 이번 보완 후에는 작업 종료 직후 취소 체크 지점에서 정상 응답을 차단한다.

두 테스트는 현재 동작의 재현이며 안전한 작업 취소가 구현됐다는 뜻이 아니다. Desktop이 실제 사용하는 취소 경로를 확정하는 테스트도 아니다. 임의 sleep 대신 이벤트로 실행 순서를 제어한다.

## 이번 보완

도구 설명에 시간 초과·대기 취소만으로 서버 중단을 단정하지 말고 자동 재호출하지 않도록 안내했다. 실행 상태를 확인할 수 없으면 그 한계를 알리고 추가 호출을 사용자에게 확인한다. 시간 제한 상향이나 백그라운드 스레드 방치 옵션 변경은 하지 않는다.

### 추가 조사: 취소 알림과 중복 응답

MCP 1.30.0 / AnyIO 4.15.1에서 메모리 전송으로 실제 `notifications/cancelled` 알림을 보냈다. 서버는 즉시 `Request cancelled`를 응답하지만 동기 작업은 계속된다. 보완 전에는 그 작업의 반환 후 SDK가 다시 응답하려다 `Request already responded to` assertion으로 세션이 실패했다.

`ask_paper`의 동기 작업 반환 직후 취소 체크 지점을 추가했다. 취소가 도착했다면 정상 답변을 직렬화·반환하지 않으며 기존 진단에 `CANCELLED`로 남는다. 취소 응답 수신 → 가짜 저장 작업 완료 → 같은 MCP 세션 ping 성공까지 테스트한다. 동기 작업 자체의 취소나 저장 롤백을 보장하는 변경은 아니다.

### 기존 로그의 확인 한계

- Desktop 로그는 `%LOCALAPPDATA%/Claude/logs/`에서 확인했다. 해당 날짜의 `mcp-server-solo-leveling-paper.log`·`mcp.log`에는 초기화·목록·리소스 조회와 연결 종료가 있으나 해당 `tools/call`·`notifications/cancelled` 기록은 없다. 호출 자체도 빠져 있으므로 취소 미전송의 증거로 사용할 수 없다.
- `worker-73b8937b10714322b40d79b6e3759e8f.log`와 `worker-5f02efdcb36a477aac3bc59008566070.log`는 각각 90바이트의 진입 기록뿐이다. 기본 모드에서 `worker.py`가 stdout·stderr를 버리므로 `embedder.py`의 import/construct/encode 단계가 저장되지 않는다.
- 코드상 계측 지점은 라이브러리 import → 모델 생성 → encode이며 캐시 적중도 구분한다. 실제 내부 단계의 시간은 현재 자료로 확인 불가다. 모델 생성 단계가 느려도 다운로드·디스크·모델 초기화를 자동 구분하는 것은 아니다.
- 과거 원본 로그를 이번 요청의 원인으로 대체하지 않았고, 원본 수집 설정이나 사용자 설치 wheel을 바꾸지 않았다.

## worker 기본 단계 진단 연결 제안

2026-10-29 확인한 #85 코멘트에서 기본 단계 진단은 아직 후속 범위·담당 합의 대상이다. #99는 파일 종류·종료 메타데이터·잠금 계약을 제안 중이다. #121은 MCP 자원 종료, #123은 안전 필터의 종료 코드와 쓰기 실패 복구를 변경하므로 공통 필터 이동을 별도로 추진하지 않는다.

| 항목 | 제안 |
|---|---|
| 기록 지점 | 기존 library_import / model_construct / encode / memory_cache_hit를 재사용 |
| 필드 | 형식 제한 request_id·span_id, 고정 stage·event·error_code, 유한한 비음수 elapsed_ms |
| 수집 통로 | Python·네이티브 원본 stderr 폐기는 유지하고, 검증된 구조화 이벤트만 별도 안전 sink로 전달 |
| 공통 모듈 | infrastructure에서 CLI를 import하지 않도록 A·C와 위치 확정 |
| 파일 관리 | #99의 파일명·실행 묶음 계약에 연결. 단계 end를 파일 종료·삭제 가능 증거로 사용하지 않음 |
| 실패 처리 | sink 생성·쓰기 실패가 임베딩 결과를 바꾸지 않음. 원본 출력으로 fallback하지 않음 |
| 담당 | A: worker 연결, C: 공통 sink·필터 및 실행기 통합, B: 단계 분리·본문 미기록·답변 회귀 검증 |

`test_embedding_stage_diagnostics.py`는 기존 embedder의 import·모델 생성·encode 실패를 각각 주입해 단계 구분, 캐시 적중, 고정 오류 코드와 본문 미기록을 검증한다. 이 테스트의 안전 sink는 테스트 내부에서만 연결한다. 실제 worker 기본 로그 연결이나 지연 원인 확정이 완료됐다는 뜻은 아니다.

실제 원인을 좁히려면 합의된 안전 sink 연결 후 새 worker 실행을 관찰해야 한다. 과거 소실된 단계 로그는 복구할 수 없다. 최초 측정은 원격 모델/API 없이 캐시된 모델과 합성 문장으로 진행하고, Desktop 실제 질문 호출과 분리한다. 모델 다운로드가 필요한 환경에서는 측정을 중단하고 준비 상태를 먼저 확인한다.
