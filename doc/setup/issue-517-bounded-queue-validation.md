# 제한적 큐 소비와 종단 검증의 남은 범위

## 구현

`run_processing_queue`는 기존 `create_processing_worker`로 조립한 worker와 stop 신호를 받는다. 작업 수 상한은 필수이며 기본 운영 상한은 정하지 않는다. 유휴 대기는 중단 가능하고, 중지 후 다음 claim을 하지 않는다. 게시 미완료나 예외가 발생하면 자동 반복하지 않는다. 실제 동의·lease·원장·게시 검사는 기존 worker가 수행한다.

이 함수는 운영 배포를 자동 활성화하지 않는다. Render 기본 standby와 단발 검증 bootstrap은 그대로다. 이미 진행 중인 provider 요청을 물리 취소하거나 환급하지 않는다. 재시작 뒤 이전 전송을 안전하게 재사용할 수 있는지 원장과 처리 결과를 먼저 확인해야 한다.

## 검증 결과

새 큐 상한/중지/불확실 실패 테스트와 기존 실제 PostgreSQL의 claim 세대, 철회, 삭제 lease, 저장 근거 수명, 영속 원장 회귀를 함께 실행해 **81 passed**. 이 결과는 로컬 DB·합성 provider 검증이며 실제 두 Auth0 계정이나 Render 프로세스 장애 실측을 대신하지 않는다.

## 실행 연결 전에 필요한 것

- 단발 payload allowlist를 일반 문서 처리로 확장할 토큰 상한 산정과 사용자/서비스 예산 정책.
- 처리 가능한 owner/작업과 전체 작업 수 상한, 재시도 정책의 명시적 승인.
- Render용 운영 bootstrap에서 기존 DB/R2 제한 자격·모델 지문·동의 gate를 조립하고 단발 bootstrap의 scope 검사를 제거하지 않은 채 별도 모드를 구성.
- 새 유료 API 호출 승인. 앞선 합성 PDF 1회 승인은 소진되었다.
- #397 실제 Auth0 계정 두 개와 staging 요청의 교차 접근, 재연결, 삭제 직후 늦은 write, 로그 비노출을 같은 배포 SHA에서 확인.

기존 실제 staging 단발 게시 성공은 #517의 앞선 기록을 따른다. 이 변경에서 staging 설정·동의·예산·데이터는 바꾸지 않았다.
