# #91 Chroma 소유권·서버 종료 협의안

작성일: 2026-10-28

관련 티켓: [#91](https://github.com/soogwon/soloLevelingPaper/issues/91)

상태: A의 제안을 바탕으로 정리한 C의 구현 전 계약안이다. A와의 최종 합의나 운영 코드 반영 완료를 뜻하지 않는다.
기준 소스: `origin/main`의 `e0ae49d017005614c2024791e37edb071ca97ba1`.

## 현재 확인된 문제

- `interfaces/mcp/runtime.py`는 검색용 Chroma 클라이언트를 만들지만 소유 참조와 종료 처리를 보관하지 않는다.
- `workers/ingestion.py`는 수집 과정에서 별도 클라이언트를 만든다. 같은 저장 경로를 사용하는 클라이언트의 수명을 개별적으로 종료하면 검색과 충돌할 수 있다.
- 현재 MCP 종료는 임베더를 먼저 닫고 executor에 `shutdown(wait=False, cancel_futures=True)`를 호출한다. 실행 중인 수집 작업이 끝났다는 보장은 없다.
- 서버 구성 중 오류가 발생하면 lifespan에 진입하지 못할 수 있어, lifespan의 정리만으로 초기화 실패를 처리할 수 없다.

측정 이력은 [macOS 파일 핸들 검증 기록](macos-file-handles.md)을 참조한다. 테스트 fixture의 정리는 운영 서버의 수명 문제 해결과 별개다.

## 소유권 제안

1. MCP 런타임이 해당 서버의 저장 경로에 대한 클라이언트 하나를 만들고 소유한다.
2. 검색 서비스와 수집 작업은 주입받은 클라이언트를 빌려 쓰며 직접 닫지 않는다.
3. MCP 밖에서 단독 실행하는 수집 진입점은 직접 만든 클라이언트만 정리한다. 성공·실패 모두 적용하며 실패 시 부분 색인 정리가 먼저다.
4. 소유자는 공개 종료 API를 사용한다. 전역 캐시 삭제, 내부 시스템 강제 중단, `reset()`으로 종료를 대신하지 않는다.
5. 종료 오류가 원래 작업 오류를 덮지 않게 한다. 로그는 허용된 코드값만 기록하고 원본 예외·본문·키를 남기지 않는다.

여기서 단일 소유는 서버 프로세스 내부의 계약이다. 같은 경로를 여러 서버 프로세스가 동시에 여는 문제까지 해결한다고 간주하지 않는다.
ChromaDB 1.5.9 이상은 A의 최소 버전 후보이며, 버전 범위와 공개 종료 API의 동작 검증은 A 구현에서 확정해야 한다.

## C의 종료 순서 제안

1. 종료 상태로 전환하고 새 등록 및 저장소 사용 요청의 진입을 막는다. 진입 판정과 실행 작업 등록은 같은 동기화 경계에서 처리한다.
2. 아직 시작하지 않은 등록 작업을 취소한다. 취소된 작업이 계속 처리 중으로 보이지 않도록 기존 상태 계약에 맞게 DB에 반영한다. 상태값·제한사항 코드는 A와 확정한다.
3. 실행 중인 수집뿐 아니라 검색 등 공유 자원을 사용하는 호출도 추적하여 종료를 기다린다. MCP 프레임워크가 호출을 모두 기다려 준다고 가정하지 않는다.
4. 모든 사용이 끝난 뒤 임베더와 Chroma 클라이언트를 각각 한 번만 닫는다. 한 자원의 정리가 실패해도 다른 자원의 정리는 시도한다.

대기 중에는 이벤트 루프를 막지 않는다. 종료 함수를 반복 호출해도 중복 정리되지 않아야 한다.
Future가 취소된 경우 완료 콜백에서 `exception()`을 무조건 호출하지 않는다.

### 대기 시간 초과

C 제안은 정상 종료 대기 시간을 30초로 두되, 이 값은 아직 합의·구현되지 않았다.
이 시간은 서버 프로세스가 반드시 종료되는 최대 시간을 뜻하지 않는다.

- 타임아웃 자체가 Python 스레드나 외부 호출을 중단시키지는 않는다.
- 실행 중인 작업이 남으면 Chroma와 임베더를 먼저 닫지 않는다. 새 요청 차단을 유지하고, 마지막 사용자가 반환한 뒤 소유자가 정리하는 경로를 둔다.
- 이 경우 종료 대기 초과를 안전한 코드값으로 기록한다. 타임아웃만으로 실행 중인 DB 작업을 실패로 바꾸지 않는다. 뒤늦은 작업 완료와 충돌할 수 있기 때문이다.
- 작업이 영구적으로 멈추면 위 방식만으로 종료 시간을 보장할 수 없다. 강제 종료가 필요하면 별도의 작업 취소·프로세스 격리 설계가 필요하며 이번 계약에서 해결됐다고 표시하지 않는다.

30초의 적절성, 종료 지연을 허용할지, 마지막 작업의 정리 책임을 어떤 객체가 유지할지는 A와 합의할 남은 항목이다.
`shutdown(wait=False)`만 호출하고 안전하게 종료됐다고 판단하지 않는다.

## 초기화 실패

자원을 만들 때마다 정리 책임을 등록하고, 서버 생성 중 실패하면 생성 완료된 자원만 역순으로 정리한다.
서버 생성 성공 후에는 그 책임을 정상 종료 경로에 넘겨 두 경로에서 중복으로 닫지 않게 한다.
클라이언트 생성 자체가 실패한 경우 존재하지 않는 클라이언트의 종료를 시도하지 않는다.
lifespan 진입 전 생성 실패와 진입 후 종료를 각각 테스트한다.

## 담당별 변경 경계와 선행 조건

| 담당 | 예상 파일·영역 | 필요한 작업 |
|---|---|---|
| A | `infrastructure/storage/vector_store.py` | 공개 종료 API 및 지원 버전 검증, 소유·대여 계약 |
| A | `workers/ingestion.py` | 외부 클라이언트 주입, 직접 생성한 경우만 종료, 부분 색인 정리 순서 보장 |
| A+C | 작업 상태 저장 계약 | 시작 전 취소와 재시작 후 중단 처리의 상태·코드 합의 |
| C | `interfaces/mcp/ingestion.py` | 새 작업 차단, 실행 작업 추적, 취소 콜백과 대기 처리 |
| C | `interfaces/mcp/runtime.py` | 단일 클라이언트 주입, 초기화 실패 정리, lifespan 종료 연결 |
| C | MCP 테스트·운영 문서·핸들 측정 | 아래 검증 기준과 종료 지연 안내 |

진행 순서는 계약 합의 → A의 주입·정리 구현 → C의 런타임 연결 → 통합 검증이다.
C 작업에서 A 담당 파일을 바꿔야 하면 먼저 변경 필요성과 범위를 알린다.
첫 준비 단계에서는 문서만 추가했다. 이후 C의 등록 관리자에 아래 독립 기능을 추가했다.

### C 준비 구현 현황

- `begin_shutdown()`으로 새 등록을 차단하고 executor의 추가 제출을 막는다.
- 제출된 Future를 추적하고 `wait_for_idle(timeout)`으로 완료 여부를 반환한다. 타임아웃은 작업을 취소하거나 자원을 닫지 않는다.
- 즉시 완료·실패·취소된 Future의 완료 콜백을 안전하게 처리한다.
- 새 등록 거절은 `SERVER_SHUTTING_DOWN`으로 변환한다.

이 단계의 대기 작업은 취소하지 않고 실행을 마치게 한다. 위 취소 정책은 A와 상태 계약을 확정한 뒤 연결한다.
런타임 lifespan에서는 아직 이 메서드를 호출하지 않으며, 검색 호출 추적·Chroma 종료·초기화 실패 정리는 미구현이다.
`wait_for_idle()`은 등록 작업만 확인하므로 이것만으로 Chroma를 닫아도 된다고 판단하면 안 된다.
단위 검증은 `tests/unit/mcp/test_ingestion_shutdown.py`에서 수행한다.

## 완료 판정용 테스트

| 상황 | 확인할 결과 |
|---|---|
| 작업 없는 정상 종료 | 소유 클라이언트와 임베더가 각각 한 번 정리됨 |
| 등록·검색 동시 실행 중 종료 | 새 진입 차단, 마지막 사용 완료 전에는 자원을 닫지 않음 |
| 시작 전 등록 취소 | 실행되지 않음, DB 상태가 처리 중으로 남지 않음, 콜백 오류 없음 |
| 수집 실패 | 부분 색인 정리 후 소유 자원 정리, 대여한 자원은 유지 |
| 정상 종료 대기 초과 | 실행 중 자원 유지, 안전한 코드 기록, 마지막 사용 후 한 번 정리 |
| 초기화 단계별 실패 | 이미 만든 자원만 정리, 원래 오류 보존 |
| 종료 자체 실패·중복 호출 | 다른 자원의 정리 시도, 원본 예외·본문·키 노출 없음 |
| 반복 등록·검색·서버 종료 | 파일 핸들과 내부 시스템 수가 반복 횟수에 따라 계속 증가하지 않음 |

동시성 테스트는 고정 시간 sleep에 의존하지 않고 이벤트로 실행·종료 순서를 제어한다.
단위 테스트 후 실제 지원 Chroma 버전으로 수집·검색 통합 테스트를 수행한다.
macOS/Linux에서는 기존 측정 스크립트로 종료 후 잔류 자원과 반복 추세를 기록한다.
Windows에서도 반복 실행과 저장소 재접근을 확인하되, 이것을 macOS 파일 핸들 검증 대체로 기록하지 않는다.
강제 내부 시스템 정리 옵션을 사용한 결과는 정상 종료의 합격 증거로 삼지 않는다.

## 아직 완료되지 않은 항목

- A와 종료 대기·취소 상태·버전 계약 확정
- A의 운영 클라이언트 주입·정리 구현
- C의 실행 작업 추적 및 런타임 연결
- 실제 Chroma 통합 테스트와 OS별 측정

위 항목 완료 전에는 #91이나 운영 파일 핸들 누수 문제가 해결됐다고 판단하지 않는다.
