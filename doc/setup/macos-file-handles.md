# #67 macOS 파일 핸들 검증 기록

운영 서버의 후속 소유권·종료 협의는 [#91 계약안](chroma-lifecycle-coordination.md)에 정리한다.
계약안 작성은 운영 코드의 종료 처리 완료를 뜻하지 않는다.

## 검증 범위

- 검증 기준: `dda8fe5ebca3c0d4ca298aada60ebc70b284a015` (`origin/main`)
- 환경: macOS 26.7.1, Apple Silicon, Python 3.12.14, pytest 9.1.1, ChromaDB 1.5.9
- 이 환경의 시작 시 파일 수 제한은 1048575였다. 낮은 제한 환경을 재현하기 위해
  테스트 프로세스의 소프트 제한만 256과 4096으로 바꾸어 비교했다.
- 실제 모델 다운로드와 유료 API 호출 없이 기존 테스트 대역을 사용했다.
- 최초 측정 후 테스트가 직접 만든 클라이언트를 정리하는 fixture를 추가했다.
  서비스의 클라이언트 수명이나 다른 담당자의 수집·검색 구현은 변경하지 않는다.

## 재현과 결과

저장소 루트에서 가상환경과 개발 의존성을 준비한 뒤 실행한다.
명령의 괄호는 제한 변경을 테스트용 서브셸로 한정한다.

```bash
# 낮은 제한에서 첫 오류까지 확인한다.
(ulimit -Sn 256 && .venv/bin/python -m pytest tests -q -x --tb=short)

# 우회 적용 후 전체 테스트를 확인한다.
(ulimit -Sn 4096 && .venv/bin/python -m pytest tests -q --tb=short)
```

| 제한 | 관찰 결과 |
|---|---|
| 256 | 통합 테스트 진행 중 파일 한도에 도달하여 `Errno 24` 발생. pytest의 임시 파일 정리에도 같은 오류가 발생함 |
| 4096 | `Errno 24` 없이 전체 실행 완료. 882개 통과, 1개 실패, 2개 건너뜀, 하위 테스트 74개 통과 |

4096 실행의 실패는 `test_config_is_only_json_without_secret_or_data_creation`이다.
가상환경 Python의 심볼릭 링크를 해제하는 별도 문제 [#88](https://github.com/soogwon/soloLevelingPaper/issues/88)이며,
#67 브랜치에는 해당 수정이 포함되어 있지 않다. 전체 테스트 통과로 기록하지 않는다.
설치 배포 검증은 별도 wheel 설치 환경이 없어 건너뛰었고, 다른 건너뜀도 포함한 수치다.

## 원인 측정

### 저장소의 진단 스크립트로 재검증

Python 3.11 이상으로 만든 가상환경에 개발 의존성을 설치한 뒤 저장소 루트에서
아래 명령을 실행한다. 스크립트는 macOS·Linux 전용이고 Windows에서는 실행하지 않는다.

```bash
# 통합 테스트별 파일 수와 Chroma 시스템 수를 JSON으로 저장한다.
.venv/bin/python scripts/measure_test_file_handles.py \
  --limit 4096 --report /tmp/solo67-handles.json -- tests -q --tb=short

# 별도 프로세스에서 통합 테스트 종료 후 Chroma 종료 전후를 비교한다.
.venv/bin/python scripts/measure_test_file_handles.py \
  --limit 4096 --report /tmp/solo67-stop.json --stop-chroma \
  -- tests/integration -q --tb=short
```

보고서의 `samples`는 통합 테스트별 파일 수와 공유 시스템 수,
`fds_after_tests`와 `fds_after_stop`은 종료 실험 전후 수치다.
`exit_code`는 pytest 결과를 그대로 나타내며 별도 실패를 숨기지 않는다.
보고서 파일도 열린 파일 수에 포함되며 환경·버전·실행 순서에 따라 수치는 달라진다.
보고서 경로는 기존 파일과 겹치지 않게 정한다. 같은 경로를 사용하면 덮어쓴다.

저장소에 추가한 스크립트로도 Mac에서 재검증했다. 전체 실행은 882개 통과,
#88로 인한 1개 실패, 2개 건너뜀이었고, Chroma 시스템은 1개에서 52개로 늘었다.
통합 테스트 종료 비교는 62개 통과, 1개 건너뜀이고 파일 수는 548개에서 6개로 줄었다.
이 비교에서는 JSON 보고서 파일을 계속 열어 두므로 최초 종료 실험보다 1개 많다.

`--stop-chroma`는 내부 API에 의존하는 선택적 진단이다. 이 명령으로 시작한
프로세스에서 테스트가 끝난 뒤에만 실행하며, 실행 중인 서비스나 사용자 데이터의
클라이언트에 적용하는 명령이 아니다. 저장 데이터 삭제나 `reset()`은 호출하지 않는다.

### 최초 관찰 결과

최초 측정은 저장소 밖의 임시 pytest 관찰 훅에서 통합 테스트의 teardown 뒤에 열린 파일
설명자와 Chroma 공유 시스템 수를 기록했다. 파일 수는 `fcntl(F_GETFD)`가 성공하는
설명자를 세었고, 4096 제한 실행에서는 0부터 4095까지 확인했다.
Chroma 시스템 수는 설치된 버전의 `SharedSystemClient._identifier_to_system`을
관찰했다. 관찰 훅이 여는 로그 파일도 측정 수치에 포함된다.

| 전체 테스트 중 관찰 시점 | 열린 파일 설명자 | Chroma 공유 시스템 |
|---|---:|---:|
| 첫 통합 테스트 종료 | 24 | 1 |
| 마지막 통합 테스트 종료 | 556 | 52 |

별도 프로세스에서 통합 테스트만 실행한 후 종료 실험도 했다.

| 상태 | 열린 파일 설명자 |
|---|---:|
| 통합 테스트 종료 후 (62개 통과, 1개 건너뜀) | 547 |
| 남은 Chroma 시스템 52개를 종료하고 공유 캐시를 비운 후 | 5 |

이 결과는 테스트 프로세스에 유지된 Chroma 시스템이 파일 설명자 누적의 주요
원인임을 뒷받침한다. 단순히 테스트 파일의 직접 호출만 문제인 것은 아니다.
`workers/ingestion.py`도 클라이언트를 생성하므로 테스트의 직접 호출 6곳만
정리하면 해결된다고 단정할 수 없다.

종료 실험은 테스트가 끝난 별도 프로세스에서만 수행했다. Chroma 내부 API에
의존한 진단이며 서비스나 공통 fixture에 적용하지 않았다. 재검증용 스크립트에도
동일한 관찰·종료 절차를 남겼다. Chroma 버전에 따라
수명 관리 동작이 달라질 수 있고, 현재 프로젝트는 Chroma 버전을 고정하지 않는다.

## 적용한 대응과 남은 작업

### 테스트가 직접 만든 클라이언트 정리

`tests/integration/conftest.py`에 `chroma_client_factory`를 추가하고
`test_ingestion.py`와 `test_scoped_search.py`의 직접 생성 6곳에 연결했다.
`ExitStack`에 각 클라이언트의 공개 `close()`를 등록하므로 테스트나 fixture 준비가
실패해도 생성한 클라이언트가 정리된다. 공유 캐시 전체를 비우거나 수집 코드의
클라이언트를 가로채지 않는다. 현재 종료 API 검증 버전은 ChromaDB 1.5.9이며,
이전 버전 호환성과 지원 버전 범위는 후속 협의 대상이다.

| 수정 후 검증 | 결과 |
|---|---|
| 제한 4096, 전체 테스트 | 882개 통과, #88 실패 1개, 2개 건너뜀, 하위 테스트 74개 통과 |
| 제한 256, 통합 테스트 | 62개 통과, 1개 건너뜀 |
| 제한 256, 전체 테스트 | 882개 통과, #88 실패 1개, 2개 건너뜀, 하위 테스트 74개 통과 |
| 의도적인 assertion 실패 후 fixture 종료 실험 | Chroma 시스템 0개, 열린 파일 6개로 정리됨 |

4096 전체 실행에서 통합 테스트 teardown 시점의 파일 수 최고치는 219개,
마지막 Chroma 시스템 수는 19개였다. 최초 측정의 556개·52개보다 줄었으며
256 제한에서도 `Errno 24`는 발생하지 않았다. 다만 전체 테스트 종료 후에도
시스템 19개가 남으므로 서비스 수명 관리까지 해결됐다고 판단하지 않는다.
실패 정리 실험은 저장소 밖의 임시 테스트에서 클라이언트와 컬렉션을 만든 뒤
의도적으로 assertion을 실패시켜 확인했다.

개발 안내의 4096 우회는 테스트 개수와 Chroma 버전이 달라지는 환경을 위한
임시 대응으로 유지한다. 전체 테스트 통과 또는 리소스 누수 근본 해결을 뜻하지 않는다.

근본 수정 시에는 A 담당자와 클라이언트 소유권·종료 시점을 정해야 한다.
테스트가 직접 만든 클라이언트와 수집 경로에서 생성한 클라이언트를 모두 고려하고,
같은 저장소를 공유하는 검색 클라이언트를 일찍 종료하지 않도록 검증해야 한다.
내부 공유 캐시를 무조건 비우는 처리를 서비스 종료 정책으로 사용하지 않는다.
Windows·Linux 및 다른 Chroma 버전에서의 재현·우회 검증은 수행하지 않았다.
