# #395 질문 입력 저장과 재시작 복구 검증

## 구현 범위

- A: migration 0039로 실행 행에 질문·고정 publication/context·검색 조건·처리 설정을 원자적으로 저장한다. 기존 행은 NULL로 유지하며 저장 입력은 변경할 수 없다.
- B: 기존 canonical input hash와 정책 버전을 대조한다. 유효한 lease와 현재 동의가 있는 worker만 입력을 복원하는 실행 어댑터를 제공한다.
- C: 같은 요청 키의 동시 제출은 같은 실행으로 복구한다. 기존 본문 없는 실행을 새 질문으로 해석하지 않는다. 공개 제출 도구는 아직 활성화하지 않는다.

## 로컬 검증

합성 데이터와 격리 PostgreSQL을 사용했다. 외부 API 호출·PDF 전송·staging 변경은 없다.

- 입력 및 정책·중복 방지 단위/DB 회귀 73개 통과.
- migration 재실행·삭제·제품 조회까지 확장한 관련 회귀 90개 통과.
- 동시 8회 제출의 단일 실행, 새 store 인스턴스의 같은 입력 복원, 만료 lease 재할당 후 이전 worker 거부를 확인했다.
- 동의 철회·논문 삭제·다른 사용자·잘못된 hash/정책 버전·입력 변조를 거부한다.
- 재검토 중 동의 철회 뒤 입력 조회가 가능한 경계를 발견하여 읽기 시점에도 현재 동의와 dispatch 상태를 검사하도록 보강했다.

## 남은 범위

- 제출 API/MCP와 동의·예산 admission 조립, 질문 queue 선택·폴링, 실제 검색/번역 provider factory 연결은 별도 단계다.
- 이 변경만으로 원격 질문 전체 제품 흐름이 완료되지는 않는다.
- migration 0039의 staging 적용 및 질문 worker DB 권한은 별도 승인·검토 후 진행한다. 현재 제품 조회 전용 권한을 확대하지 않았다.
- 실제 질문의 외부 전송·유료 호출은 새 승인 후 검증한다. 원문 질문을 로그나 진단에 출력하지 않는다.

## 질문 queue 후속 검증

- `FOR UPDATE SKIP LOCKED`로 저장된 질문만 선택하고 같은 트랜잭션에서 lease를 확정한다.
- A: deadline·삭제·동의·dispatch 중지를 검사하며 종료된 작업과 기존 NULL 입력 작업은 선택하지 않는다.
- B: 전송 이력이 없는 lease 만료 작업만 자동 복구한다. reserved/unknown/observed 전송 이력이 있으면 재전송 없이 종료하고 사용량 상태를 유지한다. 유료 재시도 정책을 추가하지 않는다.
- C: 기존 실행 ID와 입력을 유지한다. 새 요청 키 생성이나 카드 재제출을 queue에서 수행하지 않는다.
- 동시 worker·재시작·이전 lease 차단·철회·삭제·전송 이력과 제한 polling 관련 회귀 32개 통과.
- 이번 단계는 queue 함수와 runner 연결이며 Render standby 설정을 바꾸지 않았다. 실제 답변 factory와 제품 제출 연결은 다음 단계다.
