# 검증 이력 보존·정리 절차 (#82)

범위: #83이 저장하는 의미 검증 이력(`verification_runs`·`verification_claims`·`verification_claim_refs`)의 용량 관리.
학습 맥락·답변 근거(evidences)·청크·논문 파일은 정리 대상이 아니다. 자동 삭제와 예약 실행은 없다.

## 초기 운영 기준 (B 제안, #82에서 합의)

- **권장 보존 기간: 90일.** 검증 실행의 생성 시각(UTC) 기준으로 최근 90일은 보존하고, 90일 경계보다 오래된 실행만 정리 후보로 본다
  (경계 시각 자체는 보존). 성공·실패 실행에 같은 기준을 적용한다. 몇 달 전 답변까지 재검토할 수 있도록 잡은 초기 권장값이다.
- 90일은 **권장값일 뿐 코드의 기본값이 아니다.** 명령은 계속 `--older-than-days`를 직접 지정해야 한다.
  요청당 이력 크기·누적 용량·저장·조회 지연 실측에서도 기간을 바꿀 근거가 확인되지 않아 권장값을 유지한다.
  표본·환경·결과의 한계는 [검증 이력 크기·지연·정리 실측](../history/verification-retention-measurement.md)을 따른다.
- **실행 주체: 로컬 DB 소유자 또는 소유자가 지정한 관리자의 수동 정리.** 유지보수 시간에 `plan`으로 대상 건수와 기간을 확인하고,
  백업 후 같은 기간으로 `run --yes`를 실행한다. 일반 학습·MCP 호출이나 앱 시작 시 자동 삭제하지 않는다.
- 삭제 범위는 대상 실행과 그 주장 판정·검사 근거 연결까지다. 파일 공간 회수(`reclaim`)는 필요할 때 따로 결정한다.

## 원칙

- 보존 기간은 코드에 기본값이 없다. `--older-than-days`를 매번 직접 정해야 하며 값이 없으면 실행하지 않는다.
- 정리 단위는 검증 **실행** 하나다. 실행을 지우면 그 주장·근거 연결도 함께 지운다(참조 → 주장 → 실행 순서).
- 이력은 실행·주장·참조가 한 트랜잭션으로 저장되므로 반쯤 저장된 실행은 보이지 않는다.
  정리는 `created_at`이 기한보다 새로운 실행을 절대 지우지 않는다.
- 변경 명령은 `--yes`가 있어야만 실행한다. 먼저 `plan`(dry-run)으로 대상을 본다.
- 출력과 로그에는 건수·기간·결과 코드만 쓴다. 주장 문구·사유·청크 내용·경로는 쓰지 않는다.

## 명령

```
solo-leveling-verification-retention plan    --db <DB경로> --older-than-days N
solo-leveling-verification-retention run     --db <DB경로> --older-than-days N --yes [--backup-to <백업경로>]
solo-leveling-verification-retention reclaim --db <DB경로> --yes [--backup-to <백업경로>]
```

`--backup-to`는 SQLite 백업 API로 변경 전에 일관된 사본을 만들고, 백업 경로는 배타적으로 확보한다. 이미 있거나 다른 실행이 먼저 만들었으면 아무것도 바꾸지 않고 `backup_exists`로 중단하며 먼저 만든 사본은 보존된다. 백업이 실패하면 이 실행이 만든 파일만 지운다.

**대상 DB 확인(#178)**: 어떤 명령이든 변경(백업 포함) 전에 대상이 검증 이력 테이블의 필수 컬럼·타입·PK·FK를 가진 SQLite 파일인지 읽기 전용으로 확인한다. SQLite 파일이 아니거나 필수 스키마가 다르면 `result=failed`(종료 코드 1)로 멈추고 백업도 만들지 않는다. 확인 중 다른 쓰기가 잠그고 있으면 `locked`(종료 코드 1)다.

**백업 잠금 대기 상한(#178)**: 백업 중 원본이 다른 쓰기에 잠겨 있으면 `--backup-lock-timeout`초(기본 30, 0 초과 3600 이하)까지만 기다린다. 넘으면 `result=locked`(종료 코드 1)로 멈추고, 이 실행이 만든 백업 파일은 지우며 원본은 바꾸지 않는다. 잠기지 않고 진행되는 시간은 제한하지 않는다.

## 실행 순서(수동)

1. 앱(MCP 서버)을 쓰지 않는 시간에 한다. 정리는 짧은 쓰기 트랜잭션을 반복하므로 동시에 저장해도 깨지지 않지만,
   쓰기와 겹치면 `result=locked`로 멈춘다. 끝난 배치는 유지되며 다시 실행하면 이어서 지운다.
2. `plan`으로 대상 건수·기간(`eligible_*`, `oldest`, `newest_eligible`)을 확인한다.
3. `run --yes --backup-to ...`를 실행한다. 결과의 `fk_violations`는 0이어야 한다.
4. 공간이 필요하면 `reclaim --yes`를 따로 실행한다.

## 결과 코드

| result | 뜻 | 다음 행동 |
|---|---|---|
| completed | 기한이 지난 이력이 더 남지 않음 | 없음 |
| stopped | 배치 한도에서 멈춤(코드에서만 사용) | 다시 실행 |
| locked | 실제 잠금(SQLITE_BUSY·SQLITE_LOCKED)과 겹침. 세 명령 모두 종료 코드 1 | 잠시 뒤 다시 실행 |
| failed | 잠금이 아닌 DB 오류(테이블 누락, DB 파일 아님 등). 세 명령 모두 종료 코드 1이고 원본 예외 문구·경로는 출력하지 않음. 진행 중 배치는 되돌림 | 재시도하지 말고 백업에서 상태 확인 후 문의 |
| insufficient_disk | 공간 회수에 필요한 여유 공간 부족 | 공간 확보 후 재실행 |

## 파일 공간

- 행을 지워도 SQLite 파일 크기는 줄지 않는다. 비워진 공간은 파일 안에서 재사용된다(`reclaimable_bytes`).
- `reclaim`(VACUUM)은 전체 쓰기 잠금이 걸리고, 임시로 DB 크기만큼 더 필요하다. 여유 공간은 본체 파일이 아니라 WAL에 커밋된 페이지까지 포함한 논리 크기(`page_count × page_size`)의 2배로 판단하며, 2배 미만이면 VACUUM을 실행하지 않고 `insufficient_disk`로 멈춘다.
- **WAL 실제 회수 결과(#178)**: WAL 모드에서는 VACUUM 결과도 WAL에 먼저 쓰이므로, 끝난 뒤 체크포인트(TRUNCATE)하고 연결을 닫은 다음 본체와 WAL의 실제 디스크 크기를 보고한다(`after_bytes`는 본체+WAL, `wal_bytes_after`는 남은 WAL). 다른 연결이 WAL을 붙들어 남아 있으면 `result=wal_not_truncated`(종료 코드 1)이며 성공으로 보고하지 않는다. `before_bytes`는 시작 시점의 논리 크기다.
- VACUUM은 `INTEGER PRIMARY KEY`가 없는 테이블의 rowid를 다시 매길 수 있다. 실제로는 기존 순서대로 다시 넣지만
  SQLite가 보장하는 동작은 아니므로, rowid를 동률 정렬 보조키로 쓰는 조회(#145 퀴즈 이력 등)는 같은 시각의 기록 순서가
  바뀔 수 있다. 그래서 공간 회수는 정리와 분리해 수동으로만 한다.

## 백업·복구

- 정리 전 `--backup-to`로 만든 사본이 복구 수단이다. 복구는 앱을 끈 뒤 DB 파일을 사본으로 교체한다.
- 정리가 지운 이력은 그 사본에만 남는다. 원본 근거(청크)는 지우지 않으므로 context·`get_evidence`·답변은 정리 전후 같다.

## 조회 쪽 계약: 원문이 바뀐 이력의 표시 (B 제안, 정리 CLI와 별도로 검증)

향후 이력 조회가 지킬 기준이며 이 정리 명령의 범위가 아니다.

- 저장된 리비전·청크가 가리키는 현재 원문의 해시를 검증 당시 해시(`content_hash`)와 비교한다.
- 다르면 해당 근거에 "재검토 불가 · 검증 당시와 원문이 달라졌습니다", 원문이 없으면 "재검토 불가 · 검증 당시 원문을 찾을 수 없습니다"를 표시한다.
- 여러 근거 중 일부만 달라졌으면 어느 근거인지 표시하고, 해당 주장에 "일부 근거 재검토 불가"를 표시한다.
- 당시 판정·시각은 역사적 기록으로 보존한다. 최신 번역이나 다른 리비전으로 대체하거나 자동 재검증하지 않는다.
- 이 표시는 현재 원문으로 다시 확인할 수 있는지를 나타낸다. 당시 판정이나 이력 저장 상태(`saved`)는 바꾸지 않는다.
