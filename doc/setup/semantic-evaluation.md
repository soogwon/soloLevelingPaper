# #81 의미 검증 오프라인 평가 기반

현재 단계는 합성 데이터와 실행·집계 검증이다. 실제 API 호출, 모델 비교 및 배포 판단은 아직 수행하지 않았다.
기존 의미 검사·답변 제외 정책과 DB는 변경하지 않는다. #97의 조건 제외 정책은 별도 작업이다.

## 실행

개발 가상환경에서 저장소 루트를 기준으로 실행한다.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_semantic.py
.\.venv\Scripts\python.exe scripts/evaluate_semantic.py --split all --repeats 2 --max-calls 48
.\.venv\Scripts\python.exe -m pytest tests/unit/test_semantic_evaluation.py -q
```

macOS/Linux에서는 같은 인자에 `.venv/bin/python`을 사용한다. 이번 작업에서 해당 OS를 실행 검증했다는 뜻은 아니다.
위 오프라인 실행기에는 실제 API 실행 옵션이 없다. `.env`나 API 키를 읽지 않는다. `--live`는 거부된다.
`--max-calls`는 검증 서비스 실행 상한이며 이번 오프라인 구현에는 외부 호출이 없다.
예상 실행 수가 상한을 넘으면 실행 전에 거부한다. 자동 재시도는 없다.

## 실행 경로와 한계

자료 검사 → Claim/EvidenceInput 생성 → 기존 SemanticVerificationService.check → 판정 집계.
기대 판정·사유·해설은 검증기에 전달하지 않고 결과 비교에만 사용한다.
사례 ID·근거 ID에 포함될 수 있는 normal/error 같은 힌트도 전달하지 않는다.
입력에는 claim-1, evidence-1, chunk-1처럼 의미 없는 ID를 사용하며,
앞뒤 근거 연결도 치환한 ID로 유지한다. 원래 사례 ID는 실행기 결과 대응에만 사용한다.
근거는 해당 주장에 실제 연결된 목록만 전달한다.

현재 OfflineVerifier는 입력 내용이나 기대값을 읽어 정답을 맞히지 않고 모든 주장을 supported로 반환한다.
따라서 일부 사례가 의도적으로 오판으로 집계된다. 이것은 집계가 정답 복사로 100%가 되는 것을 방지하는 대역이다.
결과에 `mode=offline`, `quality_measurement=false`를 명시한다.

제품의 판정 타입·사유 조합·주장 ID 검사를 재사용한다. 다만 대역은 모델 출력 파싱·원문 구절 ID 선택을
실행하지 않으므로 이 실행으로 그 경로의 의미 품질을 검증했다고 주장하지 않는다.
질문 분해·보완 보존을 검사하는 verify_answer 경로, 생성·재검색·최종 답변 제외도 이번 범위가 아니다.
별도 제공자 실행기는 기존 제공자의 원문 구절 ID·검사 로직을 재사용한다.

## 결과

Git에서 제외되는 `runtime/semantic-evaluation/offline-<고유 ID>.json`에 새 파일로 저장한다.
기존 결과를 덮어쓰거나 DB에 저장하지 않는다. 결과에는 사례 ID·판정·안전한 실패 코드만 남기며
질문·주장·원문·번역문·키·임의 예외 메시지를 넣지 않는다.

- 데이터 버전·SHA256, 코드 커밋·작업 디렉터리 변경 여부, 주요 실행 소스 해시, Python 버전, UTC 실행 시각
- 대역 모델·지침 버전, split·반복 횟수·실행 상한
- 실행별 판정·사유·오류 코드·체크 항목·소요 시간
- 4×4 혼동 행렬 및 유형별 집계
- 결과 schema_version 2: summary는 초안을 포함한 잠정 집계이며
  summary_scope=provisional_including_drafts로 표시한다. reviewed_summary는 reviewed 사례만 집계한다.
- splits.development / splits.holdout에 각각 잠정 summary와 reviewed_summary를 둔다.
  선택하지 않은 집합이나 검토 완료 사례가 없는 집합은 실행 수 0, 비율 null로 표시한다.
- 잘못된 통과: 기대 비지원 중 supported로 나온 비율
- 정상 주장 미승인: 기대 supported 중 다른 판정으로 나온 비율
- 판정 불가와 제공자 장애·시간 초과·형식 오류를 별도 집계
- 반복 시 판정 또는 실행 실패 상태가 달라진 사례 ID

비율의 분모는 명확한 기대 판정이 있고 정상 완료한 실행이다. 실패 실행을 정답이나 undetermined로
간주하지 않는다. 분모가 0이면 비율은 null이다. draft 기대값은 잠정 집계하며 개수를 표시한다.
토큰 사용량과 비용은 측정하지 않았으므로 null이다. 시간은 대역 실행 시간이며 실제 모델 지연이 아니다.
코드 전체의 재현 가능한 기준은 깨끗한 커밋이다. 미커밋 상태의 일부 소스 해시만으로 완전한 재현을 보장하지 않는다.

실제 품질을 비교할 때는 검토 완료 사례의 집계를 사용해야 한다. 현재는 모든 사례가 draft이고
고정 대역을 사용하므로 reviewed_summary는 비어 있으며, 실제 모델 품질을 판단할 수 없다.
실행 실패는 검토 완료 집계에도 실패로 남지만 정확도 분모에는 넣지 않는다.

## 다음 단계

1. 사람이 기대 판정과 판단 이유를 검토하고 모호한 사례를 분리한다.
2. 아래 비교 실행기로 동일 자료의 결과를 비교한다. 모델·지침을 동시에 변경하면 원인을 분리할 수 없으므로 가능하면 하나씩 변경한다.
3. 모델·반복 횟수·총 호출 상한·가격 기준 및 비용 예산을 정한 뒤 별도 승인으로 실제 API 평가한다.
4. 잘못된 통과·정상 주장 제외의 허용 기준을 합의하고 미달 결과를 포함해 기록한다.

이번 PR은 #81의 평가 기반 구현을 완료 범위로 삼는다. 실제 모델 품질이나 배포 가능성을
선언하지 않는다. 사람 판정 확정·실제 평가·페이지 보충 경계 회귀 검증은 후속 #108에서 진행한다.

- Windows 개발 환경에서 신규 평가 테스트 25개와 기존 의미 검증 관련 테스트를 합쳐 191개 통과.

- 고정 대역의 오판 집계는 예상 동작이며 실제 모델 품질 수치가 아니다.
- 실제 API 호출·사용자 DB 변경·macOS/Linux 실행은 하지 않았다.

### 재검토 보완 — 2026-10-28

- 입력 ID의 정답 힌트를 제거하고 원문 구절 생성에 사용되는 입력 및 앞뒤 연결까지 검증했다.
- 검토 완료 전용 집계와 development/holdout별 집계를 추가했다. 결과 형식은 버전 2다.
- 관련 테스트 195개 통과. CLI 48회 오프라인 실행 결과는 개발용 32회·별도 평가용 16회로 분리됐다.
- 검토 완료 사례는 0개이며 해당 집계의 비율은 null이다. 실제 API 호출은 하지 않았다.

## 제공자 연결 준비 — 실제 호출 전

`scripts/evaluate_semantic_provider.py`는 기본적으로 계획만 출력한다.
계획 모드에서는 설정 파일과 API 키를 읽지 않고 제공자를 생성하지 않는다.
현재 24개 사례 모두 사람 검토 대기이므로 기본 선택은 0개다.
검토 기준은 [검토 메모](../../evaluation/semantic/review-notes.md)에 정리했다.

```powershell
# 검토 완료 사례의 실행 계획: 현재 0개
.\.venv\Scripts\python.exe scripts/evaluate_semantic_provider.py --max-calls 3
# 초안 하나의 계획 확인: 전송 없음
.\.venv\Scripts\python.exe scripts/evaluate_semantic_provider.py --include-drafts --case crosspage-normal --max-calls 1
```

실제 호출은 별도 승인 후 `--live`, `--env-file <설정 파일>`, `--model <합의한 모델>`을
명시해야 한다. 설정의 `SEMANTIC_VERIFICATION_ENABLED=true`, `ALLOW_EXTERNAL_API=true`,
`LOCAL_ONLY=false`, API 키도 확인한다. 프로세스 환경변수가 설정 파일보다 우선하며,
모델은 명시한 `--model`로 결정한다. 초안 실행은 `--include-drafts`가 필요하고 모호한 사례는 제외한다.

- 기본 집합은 development다. holdout은 최종 비교 때 별도로 선택한다.
- 반복 횟수×선택 사례 수가 `--max-calls`를 넘으면 호출 전에 거부한다. HTTP 자동 재시도는 없다.
- 기존 어댑터의 원문 구절 ID 검증, 판정 계약, 입력 크기·시간·출력 토큰 제한을 유지한다.
- 질문별 답변 충족도나 보완 생성 전체 흐름이 아닌 주장·인용 근거의 의미 판정을 평가한다.
- 외부로 보내는 것은 합성 주장·근거이며 기대 판정·해설·원래 사례 ID는 보내지 않는다.
- 결과는 `runtime/semantic-evaluation/provider-<고유 ID>.json`에 저장한다. DB에는 저장하지 않는다.
- 결과에는 안전한 실패 코드·체크 항목을 기록하며 본문·키·임의 오류 메시지를 기록하지 않는다.
- 실제 제공자 결과도 초안 포함 집계는 잠정 결과다. 토큰 사용량·금액 수집과 결과 비교는 아직 미구현이다.
- 호출 상한은 금액 상한이 아니다. 실행 전 모델 가격과 출력 제한을 바탕으로 비용 예산을 별도 합의한다.

연결 테스트는 HTTP 응답을 대체하고 실제 소켓 연결을 금지한 상태로 수행한다.
실제 API 호출 성공이나 모델 품질을 검증한 기록은 아니다.

2026-10-28 연결 준비 검증: 관련 테스트 210개 통과. 기본 계획은 0개, 명시적으로 선택한
초안 계획은 1개로 출력되었으며 두 실행 모두 외부 호출은 0회다.

## 저장된 결과 비교

```powershell
.\.venv\Scripts\python.exe scripts/compare_semantic_evaluations.py --baseline runtime/semantic-evaluation/offline-기준파일.json --candidate runtime/semantic-evaluation/offline-비교파일.json
```

위 파일명은 실제 생성된 결과 경로로 바꾼다. 과거 자료로 평가한 경우 `--dataset`으로
그때의 자료를 지정한다. 네트워크·설정 파일·DB는 사용하지 않는다.

- 자료 버전·SHA256·선택 사례·반복 수·입력 제한이 같아야 한다. 서로 다른 모드도 비교하지 않는다.
- 제공자 모드는 시간 제한·출력 토큰 제한·전송 시도 상한도 같아야 한다.
- 모델과 지침 버전은 달라도 되며 둘을 보고서에 표시한다. 코드 변경까지 통제한 실험인지는 별도 확인한다.
- 저장된 집계값을 그대로 믿지 않고 실행별 행을 자료와 대조한 뒤 다시 집계한다.
- 전체 잠정 집계·사람 검토 완료 집계·development/holdout별 집계와 유형별 잠정 집계를 제공한다.
- 비율 차이는 비교 결과에서 기준 결과를 뺀 값이다. 분모가 0이면 차이도 null이다.
- 실행 실패를 오답이나 판단 불가로 바꾸지 않는다. 따라서 양쪽 정상 완료 분모가 다를 수 있다.
- 반복 번호끼리 같은 난수 조건이라고 가정하지 않는다. 사례별 판정·사유·실패의 분포 변화를 표시한다.
- 결과는 `runtime/semantic-evaluation/comparison-<고유 ID>.json`에 새로 저장한다. 입력 결과는 변경하지 않는다.
- 통계적 유의성·배포 승인·우승 모델을 자동 판정하지 않는다. 초안이나 오프라인 대역 점수는 품질 근거가 아니다.

비용·토큰 비교는 아직 제공하지 않는다. 실제 제공자 호출과 사람 정답 검토는 별도 단계다.

2026-10-28 비교 기능 검증: 신규 비교 테스트 21개를 포함해 관련 테스트 231개 통과.
CLI 결과 저장과 입력 파일 보존을 임시 파일로 확인했으며 실제 API는 호출하지 않았다.
