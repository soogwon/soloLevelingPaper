# 근거 문장 단절 진단 및 A·B·C 담당별 보완 계획

작성일: 2026-09-29

상태: 실제 로컬 데이터 진단 및 보완 제안. 코드 수정은 포함하지 않는다.
담당 구분은 협업을 위한 기능 경계이며 파일의 독점 소유를 뜻하지 않는다.

## 확인한 현상

「Attention Is All You Need」에 대해 기존 context로 `ask_paper`를 호출한 결과,
`status: ok`와 `structural_only`가 반환됐지만 Attention 정의와 비교 설명의 근거가 끊겼다.
기존 로컬 DB의 해당 context와 청크·저장 근거를 조회해 다음을 확인했다.
청크 인덱스는 0부터, PDF 페이지는 1부터 센다.

| 내용 | 위치 | 확인 결과 |
|---|---|---|
| Attention 입력·출력 정의 | PDF 3페이지, 청크 20 | 원문·번역 존재 |
| 출력이 가중합이라는 설명 | PDF 3페이지, 청크 21 | 원문·번역 존재 |
| query와 key의 적합도로 가중치 계산 | PDF 4페이지, 청크 22 | 해당 context의 저장 근거에 포함 |
| attention 방식 비교 | PDF 4페이지, 청크 24 | `mu`에서 끊긴 채 저장 근거에 포함 |
| 더 빠르고 공간 효율적이라는 설명 | PDF 4페이지, 청크 25 | 원문·번역 존재 |

누락 설명이 데이터 전체에서 사라진 것은 아니다. 현재 context에서 확인한 저장 근거는
청크 22와 24이며, 검색 후보 전체와 요청별 생성 이력은 이 기록만으로 복원할 수 없다.
따라서 청크 20·21·25가 검색 후보에서 빠졌는지, 생성기가 후보를 받고도 사용하지 않았는지는
확정하지 않는다. 앞서 확인한 PDF 1~2페이지의 번역 실패와는 별개의 현상이다.

## 담당 구분 요약

| 담당 | 주요 책임 | 이번 진단과의 관계 |
|---|---|---|
| A | PDF 추출·청크 분할·원본 위치 정보 | 문장·단어 경계 단절과 수식 텍스트 품질 |
| B | 검색·생성·근거 선택·검증 | 관련 앞뒤 근거 보충, 답변의 부분 충족 감지 |
| C | MCP 계약·호스트 사용 흐름·상태 안내 | 근거 한계 전달, 페이지 범위·context 연결, 장애 시 우회 방지 안내 |

핵심 데이터 처리 개선은 A와 B의 공동 과제다. C는 이를 사용자에게 정확하게 전달하고
도구 흐름을 유지한다. 현재 로그만으로 C의 MCP 전달 코드가 근거를 잘랐다고 볼 증거는 없다.

## A: PDF 추출과 청크 경계

### 확인된 사실

- `infrastructure/parsing/chunker.py`는 페이지별로 500자씩 분할하고 80자를 겹친다.
- 문장·단어 경계를 고려하지 않아 청크 24가 `much`의 중간인 `mu`에서 끝난다.
- 정의는 3페이지에서 시작해 4페이지로 이어져 페이지별 청크만으로 문맥이 완결되지 않는다.
- 저장된 원문에서 수식의 분수·제곱근·첨자가 여러 줄로 흩어져 있다.
  이는 번역 이전 저장 텍스트에서 관찰된 문제다. 실제 PDF 화면과 추출기의 단계별 비교는
  아직 수행하지 않았으므로 세부 추출 원인은 추가 진단이 필요하다.

### 보완 제안

1. 페이지 경계를 유지하면서 문단·문장·공백 경계를 우선하는 분할을 검토한다.
2. 긴 문장과 수식에 대한 최대 길이 및 예외 분할 규칙을 정한다.
3. 청크 순서와 원본 위치를 보존해 B가 인접 청크를 찾을 수 있게 한다.
4. 수식 추출 품질을 PDF 화면과 비교하고 복원이 어려운 구간의 제한 사항 표현을 협의한다.

주요 검토 파일: `infrastructure/parsing/chunker.py`, `infrastructure/parsing/pdf_extractor.py`.
분할 방식 변경은 청크 ID·번역·임베딩·근거 연결에 영향을 주므로 기존 게시 데이터를
바로 다시 분할하지 않는다. 새 파싱 리비전과 기존 참조 보존 정책을 B와 협의한다.

## B: 검색 근거 보충과 답변 검증

### 확인된 사실

- `application/evidence_qa/answer.py`는 사용된 청크 전체를 인용 근거로 저장한다.
  이번 `mu` 단절은 생성기가 짧게 발췌해서 만든 것이 아니다.
- 추가 검색은 정상 생성 결과의 claims가 비어 근거 부족으로 판단되는 경우 등에 한정된다.
- 일부 주장으로 답변을 구성하면 `ok`로 반환하므로, 질문의 일부만 충족하거나 문장 뒤가
  빠진 상태를 자동으로 감지해 추가 검색하지 않는다.
- `structural_only`는 인용 연결 등 구조 검증 수준이다. 의미·수식 정확성이나 답변 완전성을
  보장하지 않는다.

### 보완 제안

1. 선택된 청크의 앞뒤 청크를 제한된 개수·분량 안에서 후보에 보충한다.
2. 같은 context의 논문·파싱·번역·색인에 속하고 검색 가능한 청크만 사용한다.
3. 명시된 페이지·섹션 범위를 벗어나지 않는다. 필요한 문장이 범위 밖에 있으면 범위 확장을
   안내한다. 페이지 제한이 없는 경우에는 페이지를 넘는 인접 청크도 별도 근거로 검토한다.
4. 각 청크의 근거 ID와 페이지는 유지한다. 여러 페이지를 한 페이지의 인용처럼 합치지 않는다.
5. 비어 있지 않은 답변도 질문을 충분히 충족했는지 판단하는 기준과 추가 검색 조건을 설계한다.
6. 검색 후보와 실제 채택 근거를 구분해 진단할 수 있는 최소 관측 정보를 검토한다.
7. 손상된 수식을 배경지식으로 자동 복원하고 검증된 결과처럼 제시하지 않도록 검증·보류 정책을 정한다.

주요 검토 영역: `application/evidence_qa/answer.py`, 검색 서비스와 포트,
`infrastructure/retrieval/sqlite_chroma.py`, 생성·검증 및 관련 테스트.
먼저 앞뒤 청크 보충을 평가하고, 의미 검증과 추가 검색 정책은 별도 변경으로 검토한다.

## C: MCP 전달과 Claude 사용 흐름

### 확인된 사실

- 같은 context를 사용한 재호출은 정상 응답했다.
- 이전 실패 메시지는 Claude Code 권한 검사기가 판정을 반환하지 못한 호스트 오류였다.
  해당 시도의 MCP 서버 도달 여부는 펼친 호출 내역이나 별도 기록 없이 확정할 수 없다.
- Claude가 실패 후 DB 직접 조회를 시도했다. 이는 MCP의 범위 검증과 근거 처리 흐름을
  우회할 수 있는 호스트 행동이며, 서버 내부 검색 실패와 구분해야 한다.

### 보완 제안

1. `ok`와 `structural_only`가 답변 완전성·의미 정확성 보증으로 해석되지 않게 안내한다.
2. 필요 시 `get_evidence`로 이번 응답의 근거를 확인하고 페이지 표시를 일관되게 전달한다.
3. 권한 검사 등 일시적 호스트 오류 후에도 기존 context를 유지한다.
4. MCP 실패 시 DB·PDF 직접 조회로 결과를 대체하지 않도록 호스트 사용 지침을 기록한다.
   MCP 서버만으로 호스트의 별도 파일·셸 권한을 강제 통제할 수 있다고 보장하지 않는다.
5. B가 제공하는 불완전 근거·추출 제한 정보를 MCP 응답에 노출할 계약을 협의한다.
6. 사용자 선택 범위가 PDF 4페이지만이면 정의가 있는 3페이지를 포함하도록 범위 확장을 안내한다.

주요 검토 영역: `interfaces/mcp/server.py`, MCP 사용 문서 및 호스트 연결 지침.
C에서 청크를 임의 결합하거나 근거에 없는 내용을 보충하는 방식으로 해결하지 않는다.

## 협업 순서와 검증 기준

1. A·B: 인접 청크 조회에 필요한 위치·순서·범위 계약을 확인한다.
2. B: 현재 저장 데이터로 인접 근거 보충을 평가하고 정의·비교 설명의 누락 감소를 검증한다.
3. A: 문장 경계 분할과 수식 추출 개선을 별도 평가한다.
4. B·C: 부분 답변·근거 제한 상태와 사용자 안내 계약을 맞춘다.

검증에는 페이지를 넘는 정의, 단어 중간에 끊기는 비교 문장, 번역 실패 청크,
명시적 페이지 범위, 후보 분량 제한, 근거 ID·페이지 보존, 손상된 수식을 포함한다.
실제 Claude 테스트에서는 동일 context로 질문한 뒤 `get_evidence`의 반환값까지 확인한다.
