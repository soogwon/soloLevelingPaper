# B의 명시적 재파싱 실행 서비스 (#116)

기준 main: `81a002c` (A 저장 계약 #253, #99 종료 처리, #259 안전 진단 포함).
`workers/reparse.py`의 `ReparseService`는 A의 저장 함수를 사용한다. DB 스키마·저장소,
기존 등록 실행기, MCP·runtime·카드는 변경하지 않는다. #108의 페이지 보충도 변경하지 않는다.

## 데이터 흐름

```text
명시적으로 승인된 요청을 전달받는 호출자(C 연결은 후속)
  → prepare(version, 기준 parse, 기준 index, request_key)
  → A prepare_reparse: 기준·키·입력 해시 고정
  → 새로 ACCEPTED한 서비스 인스턴스만 run(job_id)
  → 관리 PDF를 작업용 사본에 복사하면서 해시 대조
  → 사본을 현재 파서·청커로 처리, 새 parse·chunk ID와 새 파싱 소속 섹션 원장
  → A save_reparse_result: 새 파싱 결과 원자 저장
  → 새 번역 ID로 TranslationService 실행·저장
  → 성공 청크 임베딩 → 별도 컬렉션 저장·재조회 검증
  → A publish_reparsed_index: 기준 재확인·기본 전환·완료를 원자 처리
  → 해당 작업이 게시한 정확한 새 색인 ID 반환

기존 context → 이전 파싱·번역·색인·인용·메모 그대로 조회
```

파일은 `managed_pdf_root` 안의 경로만 허용한다. 절대 경로도 루트 아래인지 확인하고,
심볼릭 링크가 루트 밖으로 향하면 거부한다. DB의 파일 해시와 사본의 SHA-256이 다르면
파싱·번역을 시작하지 않는다. 파일이 복사 후 바뀌어도 검증한 사본만 파싱한다.
실제 논문 원문·작업용 사본은 커밋하지 않는다.
섹션은 기존 파서 규칙의 `(parse_revision_id, section_id)` 조합으로 식별한다.
제목·순서가 같아 section_id 문자열이 같더라도 다른 파싱 원장을 같은 대상으로 조회하지 않는다.

## 내부 호출 계약

- 생성자에는 DB·Chroma·관리 PDF 루트, 번역 서비스·설정, embedder·모델을 주입한다.
  번역 제공자나 모델을 자동 생성하지 않는다. `provider_available` 기본값은 false다.
  C는 실제 외부 API 허용과 LOCAL_ONLY를 반영한 값만 전달해야 하며 동의로 설정을 해제하지 않는다.
- 파서 버전은 기본 `pdf-parser-current-v1`이며 배포 연결 시 실제 파서/청커 설정 버전으로
  고정해야 한다. 버전·파일 해시·기준 리비전·번역 설정·재시도 예산·임베딩 모델·부분 게시 정책은
  입력 해시에 포함된다. 실행 전후 설정이 바뀌면 게시하지 않는다.
- `prepare`는 실행권을 접수할 뿐 파싱·번역·임베딩을 하지 않는다. **사용자 동의를 증명하는
  도구가 아니며**, 신뢰하는 호출자가 사전에 동의를 확인해야 한다. MCP에 아직 노출하지 않는다.
- `lookup`은 키와 버전·기준 리비전 조합을 확인하고 읽기 전용 SQLite 스냅샷을 사용한다.
  미등록 키는 None, 다른 범위의 키는 작업 ID 없는 REQUEST_CONFLICT다. 없는 DB는 생성하지 않는다.
  상태·실패 사유·결과 건수는 한 스냅샷에서 읽으며, 완료 응답 전에 파싱·번역·임베딩·작업의
  전체 게시 연결을 검사한다. 연결이 손상되면 완료나 최신 색인으로 대체하지 않는다.
- 상태는 A의 ACCEPTED / IN_PROGRESS / COMPLETED / INTERRUPTED / FAILED / BASE_CHANGED /
  REQUEST_CONFLICT를 유지한다. 내부 조회 오류는 고정 예외로 반환하며 FAILED로 추측하지 않는다.
- 완료 결과는 `new_parse_revision_id`, `translation_revision_id`, `new_embedding_set_id`, 성공·실패
  청크 수를 제공한다. 기본 색인이 나중에 바뀌어도 작업 결과가 바뀌지 않는다. context는 생성하지 않는다.

## 실행·게시 방어

| 상황 | 처리 |
|---|---|
| 같은 키·같은 입력 | 저장된 상태·결과 재생, 추가 실행 없음 |
| 같은 키·다른 설정/범위 | REQUEST_CONFLICT, 다른 작업 ID 노출 없음 |
| 같은 버전의 다른 활성 작업 | A 접수 결과 유지. 다른 입력의 작업을 인계받아 실행하지 않음 |
| 같은 job_id의 반복·동시 run | 한 번만 실행, 나머지는 상태 조회 |
| 접수 응답 유실 | 기존 키로 조회. 실행권을 확인하지 못한 작업은 임의 인수하지 않음 |
| 실행 후 DB 결과 불명 | 같은 job의 재실행 금지. 키를 유지하고 조회·운영 확인 필요 |
| 재시작 뒤 기존 processing 작업 | 런타임의 기존 interrupted 확정 계약 사용. 서비스 생성자는 상태를 변경하지 않음 |
| 실패·중단·기준 변경 | 이전 게시 색인 유지. 늦은 결과의 게시 여부는 A 트랜잭션에서 재검사 |
| 게시 성공 후 응답 유실 | 해당 작업의 게시 기록으로 완료 결과 복원 |

`run`은 동기 실행 경계다. C의 백그라운드 실행기·대기열·종료 대기는 후속 연결 사항이다.
동일 서비스의 첫 실행권을 메모리에서 관리하며 다중 서버 lease나 재시작 후 자동 이어하기를
구현하지 않는다. 실행 중인 작업을 시간 초과만 보고 interrupted로 바꾸지 않는다.
번역 배치의 각 제공자 호출(재시도 포함) 직전에도 작업·기준·설정을 재검사한다.
이미 진행 중인 외부 호출을 강제 취소하지는 않지만 중단 확인 뒤 다음 호출은 시작하지 않는다.

기존 등록의 `_ingest_pages`는 최신 파싱 재사용·일반 게시·무조건 상태 변경 경로가 있으므로
재파싱에 그대로 호출하지 않는다. 파서·청커·TranslationService·벡터 저장 검증 함수만 재사용한다.
외부 번역 재시도는 기존 서비스 예산만 적용하며 바깥 재시도는 추가하지 않는다. N개 청크의
제공자 호출 상한은 `N + min(N × (max_attempts - 1), max_batch_retries)`이고 시간 예산으로 더 줄어든다.

벡터는 개수·차원·유한한 수·bool 제외를 검사한 뒤 저장하고, 다시 읽어 ID·번역문·메타데이터·차원을
검증한다. 동일 이름의 기존 컬렉션이나 DB 임베딩 ID를 재사용해 덮어쓰지 않는다.

## 부분 번역 정책: 아직 A·C 확정 전인 제안

기본 `allow_partial=False`에서는 번역 전체 성공 후에만 게시한다. 일부 실패는
REPARSE_PARTIAL_NOT_ALLOWED로 종료하고 기존 색인을 유지한다. 이 기본값을 기존 등록의
부분 게시 정책과 같다고 해석하지 않는다.

명시적 `allow_partial=True`에서는 성공 청크가 1개 이상일 때 검증된 성공 집합만 게시할 수 있다.
실패 기록과 추출하지 못한 페이지의 제한 사항을 보존한다. 성공 0개는 항상 게시하지 않는다.
새 파싱의 누락률이 이전 색인보다 높을 수 있으므로 운영 기본값·게시 품질 기준은 A·C와 확정해야 한다.
실패 청크를 원문으로 대체하거나 이전 파싱 청크를 섞어 채우지 않는다.

## 자원 정리와 현재 저장 계약의 한계

- 주입받은 공유 Chroma 클라이언트는 닫지 않는다. 서비스가 직접 얻은 클라이언트만 기존
  `close_client` 계약으로 닫으며, 종료 미확정 시 참조를 보존하고 고정 종료 코드만 기록한다.
  같은 저장소의 공유 클라이언트가 있다면 호출자가 그 클라이언트를 명시적으로 주입해야 한다.
- 새 컬렉션의 실패·중단·게시 여부가 불명확해도 자동 삭제하지 않는다. 기존 색인·원문·청크·
  번역·context는 절대 정리하지 않는다. 재시작 후 미게시 컬렉션의 영속 소유권·정리 API는 A 협의 대상이다.
- 번역 저장은 기존 `save_translation_batch`를 사용한다. 작업 상태 확인과 번역 저장이 하나의
  트랜잭션은 아니므로 그 사이 중단되면 **미게시 새 리비전 데이터가 남을 수 있다**. 기존 데이터는
  유지되고 중단 뒤 게시와 기본 전환은 A가 원자적으로 거부한다. 모든 미게시 쓰기 자체를 막으려면
  작업 조건부 번역 저장 계약이 추가로 필요하다. 현재 A 파일을 수정해 이 보장을 가장하지 않는다.
- 작업 단계를 무조건 processing으로 갱신하지 않는다. 파싱 저장 후 DB stage는 translate이며,
  임베딩 중 세부 stage를 조건부 갱신하는 API는 A·C 후속 확인 사항이다.

## C·A 후속 인계

1. C는 비용·원문 전송 안내, 명시적 동의, 같은 키 상태 복원과 worker 수명 관리를 연결한다.
   현재 B 서비스만으로 공개 MCP 입력이나 사용자 승인 계약이 확정된 것은 아니다.
2. 새 context는 사용자가 전환을 선택할 때만 해당 작업의 게시 색인에 고정해 생성해야 한다.
   현재 기본 색인을 고르는 기본 context 함수를 대신 호출하지 않는다. 정확한 색인 지정
   context 생성/재사용 helper는 A·C와 별도로 확인하며 이번 서비스는 색인 ID만 반환한다.
3. 부분 게시 기본값·미게시 소유권 정리·조건부 단계/번역 저장을 합의한다.
4. 실제 문제 PDF의 단어 경계·겹침과 실제 모델·Desktop 동의/전환은 별도 승인·검증으로 남긴다.
   #116을 자동 테스트만으로 닫지 않는다.

## 오프라인 검증

```powershell
python -m pytest tests/integration/test_reparse_service.py tests/unit/test_reparse_contract.py -q
python -m pytest tests/unit/test_ingestion_registration.py tests/unit/test_translation_recovery.py tests/unit/test_learning_persistence.py tests/integration/test_recovery_readers.py tests/integration/test_scoped_search.py tests/unit/test_annotation_service.py tests/unit/test_chunker.py tests/unit/test_pdf_extractor.py tests/unit/translation -q
```

기본 pytest 임시 폴더에 접근할 수 없으면 작업 영역 안의 **새 전용 경로**를 `--basetemp`로 지정한다.
합성 PDF를 실제 pdfplumber로 읽고 임시 SQLite·Chroma에 게시해 이전/새 context 검색을 대조한다.
새 통합 테스트는 HTTP를 차단하며 모델·제공자를 생성하지 않는다. 합성 대역 결과는 실제 번역 품질
또는 실제 논문 재처리 성공의 증거가 아니다. 검증에는 실제 API·원본 데이터를 사용하지 않는다.

검증 기록 (2026-11-09 / Windows / Python 3.12.14):

| 범위 | 결과 |
|---|---:|
| 최종 보완 후 신규 재파싱 통합 60개 + A 저장 계약 18개 | 78 passed (165.87초) |
| 기존 등록·번역 복구·검색·메모·파서·번역 서비스 회귀 | 221 passed, 11 subtests passed (145.25초) |

실제 PDF 추출은 자체 작성 합성 PDF로만 확인했다. 기존 context·근거·요약·메모·하이라이트,
새 섹션 원장, 정상 단어 경계와 긴 토큰 강제 분할, 중복·중단·게시 경쟁·응답 유실을 검증했다.
구문 컴파일과 새 파일의 공백 검사도 수행했다. 실제 모델·사용자 PDF·Desktop 및 MCP 연결은
미검증이며, 테스트 통과를 해당 범위의 완료로 해석하지 않는다.
최종 재검토에서 WAL 동시 쓰기 중 상태·사유의 스냅샷 일관성과 손상된 게시 연결 거부를 추가했다.
오프라인 wheel 빌드 후 새 domain·worker 모듈 두 개의 포함 및 소스 바이트 일치를 확인했다.
