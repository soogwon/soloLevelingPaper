# 서버 동기화·동의·충돌 정책

작성일: 2026-11-12  
상태: 구현 전 정책 기준

## 목적

로컬 MCP의 기록을 중앙 서버에 전송할 때 사용자 동의, 멱등성, 수정 충돌과 계정 전환을
일관되게 처리한다. 이 정책은 외부 웹 표시를 위한 서버 동기화에 적용한다. OpenAI 등 외부 AI
제공자에게 본문을 보내는 동의는 [외부 전송 데이터와 실행 시점](external-data-transfer.md)을
따르며 서버 동기화 동의를 대신하지 않는다.

## 동의 종류

| 동의 | 목적 | 기본 동작 |
|---|---|---|
| 계정·기기 연결 | 로컬 MCP가 해당 계정의 서버 API를 사용 | 데이터·PDF 자동 업로드 없음 |
| 기록 동기화 | 선택한 논문과 후속 기록을 외부 웹에서 조회 | 승인한 범위의 구조화된 기록과 필요한 인용만 전송 |
| PDF 업로드 | 다른 기기에서 원문 열람 | 선택한 원문 버전 파일만 별도 업로드 |
| 외부 AI 전송 | 번역·생성·검증 | 목적지·데이터·시점에 대한 기존 별도 안내 적용 |

계정 연결만으로 기존 로컬 데이터를 검색하거나 업로드하지 않는다. 최초 동기화 전에 전송 항목,
제외 항목, PDF 별도 선택, 인용문 포함 가능성과 외부 웹 노출 범위를 안내한다.

## 동의 범위 기록

서버와 로컬은 최소한 다음을 보존한다.

- 동의한 사용자와 기기 또는 로컬 출처
- 선택한 논문과 포함한 기록 종류
- PDF 업로드 포함 여부
- 동의 시각과 안내문 버전
- 범위 변경·철회 시각

사용자는 기존 데이터를 논문별로 선택할 수 있어야 한다. 선택한 논문의 이후 기록을 자동
동기화하려면 그 범위를 명시한다. 메모만 승인한 범위에 PDF나 전체 원문을 추가하는 등 범위를
확대할 때는 다시 동의를 받는다.

동기화 중지는 이후 전송을 멈추는 동작이다. 이미 서버에 저장된 기록이나 PDF 삭제와 같지 않다.
삭제·보존 정책이 확정되기 전에는 동기화 중지로 서버 데이터가 삭제된다고 안내하지 않는다.

## 사용자와 소유권

- 사용자는 검증된 웹 세션 또는 기기 인증 주체로 판단한다.
- 요청 본문의 user_id, 이메일이나 로컬 프로필 ID만으로 접근을 허용하지 않는다.
- 모든 서버 객체는 직접 owner_user_id를 갖거나 소유자를 검증할 수 있는 부모 객체에 연결한다.
- 다른 사용자의 객체 ID를 전달했을 때 존재 여부가 드러나지 않도록 응답한다.
- 웹 로그아웃은 웹 세션 종료이고 기기 연결 해제는 해당 기기의 서버 접근 종료다.
- 기기 연결 해제 뒤 남아 있는 갱신 자격과 접근 토큰도 사용할 수 없어야 한다.
- 계정 전환 시 이전 계정의 outbox를 새 계정으로 자동 전송하지 않는다.

### 로컬 계정 연결 경계

계정 연결과 토큰 갱신은 Claude가 호출하는 일반 MCP 도구 안에서 처리하지 않는다. 로컬 설정 또는
전용 CLI가 시스템 브라우저에서 Authorization Code + PKCE 흐름을 시작하고, loopback callback으로
결과를 받은 뒤 운영체제 자격 증명 저장소에 인증정보를 보관한다.

- access token, refresh token, authorization code를 MCP tool 입력·출력에 포함하지 않는다.
- 인증정보를 Claude 대화, structuredContent, 일반 로그, SQLite 본문 필드에 저장하지 않는다.
- MCP 런타임은 자격 증명 저장소의 참조를 통해 서버 client를 구성한다.
- MCP가 공개하는 연결 상태에는 연결 여부, 안전한 계정 표시명, 기기 ID와 재인증 필요 여부만 포함한다.
- 브라우저 로그인 성공만으로 데이터 또는 PDF 동기화를 시작하지 않는다.

인증 제공자가 확정되기 전 테스트에서는 주입된 검증 주체를 사용할 수 있지만, 운영 HTTP API가
요청 본문의 임의 user_id를 개발용 인증 대체물로 허용해서는 안 된다.

## 서버 ID와 로컬 ID

서버 ID와 로컬 ID의 역할을 분리한다.

- 로컬 ID는 로컬 DB 내부 참조와 오프라인 기능을 유지한다.
- 서버 ID는 웹과 여러 기기가 공유하는 객체를 식별한다.
- source_instance_id는 최초 출처를 구분하며 현재 접속 device_id와 같다고 가정하지 않는다.
- 다른 PC가 서버 기록을 내려받으면 같은 서버 ID를 유지하되 자체 로컬 ID와 매핑할 수 있다.
- 로컬 복원이나 기기 재연결 뒤에도 출처와 서버 ID 매핑을 복구할 방법을 제공한다.

## 멱등성

최초 등록에는 안정적인 객체 출처 키와 `Idempotency-Key`를 모두 사용한다.

| 입력 | 결과 |
|---|---|
| 같은 사용자·같은 키·같은 payload | 이전 상태 코드와 기존 처리 결과 반환 |
| 같은 사용자·같은 키·다른 payload | 충돌 오류, 새 객체 생성 금지 |
| 다른 키·같은 안정적 로컬 객체 | 기존 서버 객체 반환 또는 명시적 수정 요구 |
| 제목·본문만 같은 별도 객체 | 자동 병합 금지 |

서버는 멱등 결과를 사용자의 소유권 범위 안에서만 재생한다. 한 사용자의 키가 다른 사용자의
결과를 조회하는 통로가 되어서는 안 된다. payload 비교에는 정규화된 계약 필드와 hash를 사용하며
인증 토큰이나 전송 시각처럼 결과 의미와 무관한 값을 포함하지 않는다.

## 수정 버전과 충돌

서버에서 수정 가능한 객체는 단조 증가하는 수정 버전 또는 동등한 조건부 갱신 토큰을 제공한다.
클라이언트는 수정 시 마지막으로 확인한 값을 전달한다.

```http
PATCH /v1/mcp/annotations/{annotation_id}
If-Match: "revision-7"
Idempotency-Key: <stable request key>
```

- 버전이 일치하면 갱신하고 새 버전을 반환한다.
- 버전이 오래됐으면 최신 내용을 덮지 않고 충돌을 반환한다.
- 서버 revision과 로컬 수정 횟수는 서로 다른 값으로 취급한다.
- 충돌을 새 객체 생성으로 자동 우회하지 않는다.
- 본문·위치처럼 사용자의 판단이 필요한 충돌은 임의 병합하지 않는다.
- 명백히 교환 가능한 서버 상태가 아닌 이상 last-write-wins를 기본 정책으로 사용하지 않는다.

첫 세로 조각에서는 충돌을 보존하고 사용자에게 재확인이 필요하다는 상태를 반환한다. 구체적인
병합 UI와 해소 API는 객체별 수정 기능을 구현할 때 별도 계약으로 확정한다.

## 부분 실패와 상태 표시

로컬 저장 성공과 서버 저장 성공을 구분한다.

| 상태 | 의미 |
|---|---|
| local_only | 로컬에는 있으나 전송 승인 또는 서버 저장이 없음 |
| pending | 승인 범위 안에서 전송 대기 중 |
| syncing | 현재 한 번의 서버 요청을 처리 중 |
| synced | 서버 성공 응답과 로컬 매핑 기록을 완료 |
| retryable_failure | 일시 오류로 재시도 가능 |
| action_required | 재인증·동의·입력 수정 필요 |
| conflict | 멱등 payload 또는 수정 버전 충돌 |

배치 전송에서 성공한 객체와 실패한 객체를 각각 반환한다. 일부 실패를 전체 성공으로 표시하지
않으며, 실패한 하위 객체 때문에 이미 확정된 상위 객체를 중복 생성하지 않는다.

## 날짜와 로그

- 원래 생성·수정 시각과 서버 반영 시각을 구분한다.
- 시각은 시간대가 포함된 형식으로 전송·저장한다.
- 실제 작성일을 알 수 없는 기존 기록을 업로드 시각으로 바꾸지 않는다.
- 웹 날짜 표시·날짜별 필터는 별도 API 계약대로 Asia/Seoul 기준을 적용할 수 있다.
- 로그에는 토큰, API 키, 메모·인용 본문, 전체 payload, 로컬 절대경로를 남기지 않는다.
- 운영 추적에는 안전한 오류 코드, 요청 ID, 객체 종류와 단계만 사용한다.

## 로컬 revision과 서버 revision

Annotation 등 현재 로컬 모델의 수정 revision은 로컬 동시 수정 검사를 계속 담당한다. 서버는
별도의 revision을 발급하며 두 값을 같은 카운터로 간주하지 않는다.

- 로컬 수정 성공 후 outbox payload에는 해당 로컬 revision을 출처 정보로 기록할 수 있다.
- 서버 조건부 수정은 마지막으로 확인한 server_revision으로 수행한다.
- 서버 성공 응답 뒤 mapping의 server_revision만 새 값으로 갱신한다.
- 다른 기기의 서버 수정 때문에 충돌해도 로컬 revision을 임의로 되돌리거나 맞춰 올리지 않는다.

## 삭제 정책의 현재 범위

#213의 현재 완료 범위에서 삭제 동기화는 미지원으로 유지한다. 정책과 구현은
[#368](https://github.com/soogwon/soloLevelingPaper/issues/368)에서 별도로 진행한다.

삭제 동기화, 휴지통, tombstone 보존 기간, 계정 탈퇴 시 삭제 기한과 백업 만료는 아직 확정하지
않았다. 확정 전 첫 세로 조각은 확정된 서버 객체 삭제를 자동 수행하지 않는다. 단, 완료되지 않은
`private/tmp/` 업로드는 사용자 보존 데이터가 아니므로 1일 수명주기 규칙으로 정리한다.

- 로컬 행 삭제를 곧바로 서버 삭제로 간주하지 않는다.
- 동기화 중지와 서버 데이터 삭제를 구분한다.
- PDF 동기화 중지와 이미 업로드한 PDF 삭제를 구분한다.
- 삭제 기능을 추가할 때 재시도 가능한 tombstone과 참조 데이터 보존 순서를 먼저 정의한다.

## 구현 전 남은 결정

- 인증 제공자와 Authorization Code + PKCE의 구체적 복귀 방식
- 기기 자격의 유효기간·갱신·폐기
- 서버 DB 및 객체 저장소 제품과 운영 위치
- 운영 환경의 PDF 백업 방식·백업 만료·사용자 삭제 및 계정 탈퇴 기한
- 삭제 동기화와 tombstone 보존 기간
- 충돌 해소 UI와 객체별 병합 가능 범위
- 새 후속 기록의 지속 동기화 정책(기존 승인 작업은 저장된 backoff와 최초 전송 포함 5회 상한으로 자동 재시도하며, 카드에서 수동 재개 가능)
- 동의 철회 후 서버 기록의 보존·삭제 요청 흐름

이 결정은 첫 논문 메타데이터 세로 조각을 막지 않는 범위에서 확정하되, 인증과 소유권 검증을
임시 user_id 입력으로 대체해서는 안 된다.
