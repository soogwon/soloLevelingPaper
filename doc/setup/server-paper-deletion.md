# 서버 논문 삭제 연결과 검증 (#368)

2026-11-16. 기준 main `ce1b2eb`. 기존 60/30/30 정책과 A의 삭제 저장소·worker를 재사용한다.
이 문서는 이번 제품 연결 범위이며, [기존 내부 안내 대역](deletion-guidance-preview.md)의
세션 화면 제어와 실제 Desktop 인증 이벤트 연결이 완료됐다는 뜻은 아니다.

## 사용자 흐름

1. 연결된 서버에 동기화된 논문의 로컬 `paper_id`로 `prepare_server_paper_deletion`을 호출한다.
   이 호출은 대상과 안내를 확인하고 확인 토큰만 발급한다. 서버 삭제를 접수하지 않는다.
2. 카드에서 범위를 읽고 체크한 뒤 **서버 논문 삭제**를 누른다. 로컬 삭제·동기화 중지·동의 철회·
   계정 탈퇴와 다른 작업이다. 다른 의미의 요청을 이 도구로 대체하지 않는다.
3. 서버 전송 전에 로컬 SQLite `client_deletion_intents`에 연결·로컬/서버 논문 ID·고정 요청 키를
   커밋한다. 현재 기능은 로컬 논문·PDF를 지우지 않는다. 기존 로컬 삭제를 자동으로 서버에 반영하지 않는다.
4. 서버가 접수하면 `blocking`을 표시한다. worker의 정리 결과를 조회해 `cleaning`, `failed`,
   `complete`를 표시한다. `complete`도 **활성 저장소 정리 완료·백업 완전 삭제 미확인**이다.
5. 오프라인·응답 유실 뒤에는 같은 논문으로 `get_server_paper_deletion`을 호출한다. 조회는 GET만
   사용한다. 미접수 요청은 카드의 같은 요청 재전송으로 재개하며 새 요청 키를 만들지 않는다.

실행 조건: 서버 DB 마이그레이션 적용, 인증된 기기 연결, `SERVER_API_URL` 설정 및 해당 논문의
서버 매핑이 필요하다. MCP는 기존 runtime의 설정 검사를 따른다. 서버 정리 worker의 운영 배포와
스케줄은 이 API가 자동으로 시작하지 않는다. API만 연결하면 `blocking`에 머무를 수 있다.

## HTTP 계약

`/v1/papers/{server_paper_id}/deletion-requests/{request_key}`

| 메서드 | 동작 |
|---|---|
| PUT | `{ "confirmed": true, "notice_version": "server-paper-deletion-v1" }`를 받아 삭제 접수 |
| GET | owner·논문·키가 정확히 일치하는 기존 요청만 조회. 요청 생성 없음 |

owner는 인증 주체에서만 가져온다. 기존 기기 폐기 검사와 웹 세션 CSRF 검사를 재사용한다.
request key는 16~128자의 영문·숫자·`._:-`이다. 응답은 request_id, paper_id, status,
backup_erasure_confirmed(false)다. 같은 키 재전송은 기존 요청을 반환한다. 다른 키를 이미 접수된
논문에 임의 연결하지 않고 409를 반환하며, 타인/미존재는 404, 저장소 오류는 고정 503으로 처리한다.
`confirmed`에는 숫자 1이나 문자열을 허용하지 않는다.

MCP의 confirm/retry는 `visibility: [app]`이며, confirm은 별도 영속 확인 토큰을 소비한다.
visibility는 호스트의 도구 노출 계약이지 HTTP 인증을 대신하는 보안 경계가 아니다.
확인 토큰은 대상과 연결 정보에 묶이고, 재전송은 이미 기록한 의도만 허용한다.

## 영속성과 늦은 응답

- journal은 runtime 초기화 시 별도 테이블로 생성한다. 논문 행에 cascade FK를 걸지 않아 로컬 행이
  제거돼도 삭제 요청이 남는다. 전송 전 저장 실패 시 네트워크를 호출하지 않는다.
- pending에서는 같은 키로 PUT, 접수 확인 후에는 재시도 버튼도 GET만 한다. 실패한 물리 정리 작업을
  클라이언트가 새 키로 다시 접수하지 않는다. worker의 기존 lease·재시도 정책이 담당한다.
- 계정/기기 연결이 바뀌면 예전 의도를 다른 연결에서 재전송하지 않는다. 응답 후 연결도 검사한다.
- 응답 대상·요청 ID·상태를 검증하고, 저장한 complete를 늦은 이전 상태로 낮추지 않는다.
- 카드의 새 입력·취소 후 늦은 응답은 폐기한다. 제목과 오류는 HTML로 실행하지 않는다.

## 검증 및 남은 완료 조건

자동 검증에는 인증·엄격한 확인·조회 무변경·다른 키 충돌, 전송 전 영속화, 응답 유실 후 재시작과
동일 키 재전송, 계정 전환, 대상 변경, 완료 상태 역행, 카드 확인·취소·늦은 응답이 포함된다.
PostgreSQL 통합 사례는 테스트 전용 스키마에서 두 인증 클라이언트의 동일 키 재전송과 tombstone
이후 쓰기 차단을 확인한다. **두 HTTP 클라이언트 테스트는 실제 두 기기 검증을 대신하지 않는다.**

### staging 학습 상태 tombstone 후속

실제 staging에서 삭제 접수·같은 키 재전송·다른 키 거부·미인증 조회 거부는 통과했으나,
삭제 접수 뒤 학습 상태가 `reading` revision 1에서 `completed` revision 2로 변경되는 결함을 확인했다.
원인은 학습 상태 읽기·쓰기의 논문 소유권 쿼리가 `server_papers.deleted_at`을 검사하지 않은 것이다.

학습 상태 GET은 tombstone 논문을 미존재 논문과 같은 `paper_not_found`로 숨긴다. PUT은 논문 행을
`FOR UPDATE`로 잠그면서 `deleted_at IS NULL`을 함께 검사하므로 삭제 접수와 직렬화되고, 삭제가 먼저
커밋된 뒤에는 같은 operation 재생을 포함한 모든 상태 쓰기를 거부한다. 기존 상태 행은 물리 정리
단계 전까지 변경하지 않으며 외부 조회만 차단한다. 실제 PostgreSQL 회귀는 삭제 요청이 `blocking`인
상태에서 GET/PUT 404와 기존 `reading` revision 1 불변을 함께 확인한다.

이 후속은 활성 저장소의 접근·처리 차단 보완이다. 실제 R2·백업 물리 삭제 또는 두 실제 기기의
수정↔삭제 경합 검증을 완료한 것으로 해석하지 않는다.

남은 제품·운영 검증:

- 배포 후 합성 논문으로 실제 Desktop 카드 표시·확인·오프라인/재시작, 두 기기 수정↔삭제 경합 확인.
- 다른 기기가 새 키를 만든 경우 자동 접수는 409로 막힌다. 기기 간 기존 키 전달/발견 UX는 아직 없다.
  재연결로 device ID가 바뀌는 경우의 기존 journal 인계도 별도 계약이 필요하다.
- 실제 인증 UI의 로그아웃·같은 계정 재로그인 이벤트와 카드 폐기 연결은 아직 없다.
  서버 접근은 매번 인증하지만, 이미 표시된 상태를 즉시 지우는 호스트 동작은 검증해야 한다.
- 웹 삭제 버튼, 로컬 자료까지 지우는 별도 확인 흐름, 계정 삭제·복구 기능은 이번 범위에 포함하지 않는다.
- A/운영의 worker 배포·R2 정리·실패 복구 실측, 백업 만료 집행/복원 후 tombstone 재적용 및 백업
  완료 adapter 증거가 필요하다. 시간 경과만으로 백업 삭제 완료를 추정하지 않는다.

#368은 위 실제 다중 기기·운영 증거가 모이기 전까지 닫지 않는다.
