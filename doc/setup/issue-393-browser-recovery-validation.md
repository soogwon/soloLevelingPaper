# #393 제품 웹 요청 복구 검증

- 기준: main `840de8a3ef21670076db9b655ef01b601a1ee22b` (#510)
- 실행: 2026-11-16, macOS Chrome
- 범위: 변경하지 않은 제품 웹 HTML/JS/CSS + 로컬 HTTP 오류 주입 서버
- 실제 staging 인증·DB·R2 검증이 아니다. PDF 바이트 전송 및 AI 호출은 없다.

## 재현 방법

1. 저장소 루트에서 `python3 web/tests/upload-recovery-server.py`를 실행한다.
2. `http://127.0.0.1:8793/#/uploads`를 Chrome에서 연다. `mock=1`은 붙이지 않는다.
3. 합성 PDF를 선택한다. 파일 정보 전송 확인 전에는 저장이 비활성화되어야 한다.
4. 동의 체크 후 저장한다. 서버는 메타데이터를 저장한 뒤 응답 본문을 중간에 끊는다.
5. 화면의 `같은 등록 준비 요청 확인`을 누른다. 정상 의도 ID가 표시되어야 한다.
6. 기존 요청 상태 확인을 누른다. 같은 ID를 유지해야 한다.
7. 별도 터미널에서 `curl -s http://127.0.0.1:8793/__report`로 POST 두 건의 키·본문 동일성, 의도 1건 및 같은 ID GET을 확인한다.
8. 선택 취소 후 합성 PDF를 다시 선택하고 동의·저장한다. 두 번째 의도의 응답은 보류된다.
9. 제품의 계정 링크 → 로그아웃 버튼을 누른다. 서버는 로그아웃 뒤 1초 후 보류한 성공 응답을 보낸다.
10. 보고서의 `logged_out`, `late_sent`가 true인 상태에서도 로그인 화면에 이전 파일명·의도 ID가 없어야 한다.
11. 서버를 Ctrl+C로 종료한다. 메타데이터는 메모리에만 있고 재실행 시 초기화된다.

서버는 127.0.0.1에만 바인딩한다. 실제 인증 서버가 아니며 모든 브라우저가 한 합성 계정과 상태를 공유한다. 실제 계정이나 개인 PDF로 사용하지 않는다. 업로드 생성 본문은 메타데이터 네 필드와 2 KiB 미만 크기로 제한한다. prepare/complete 등 나머지 API는 거부하며 외부 호출 기능이 없다.

- 기존 늦은 응답 테스트는 이름과 달리 auth:expired만 호출했다. auth:logout과 auth:expired를 각각 검증하도록 보강했다.
- 제품 페이지 → 실제 API 어댑터 → fetch 대역에서 성공 응답 JSON 유실 후 동일 키·본문 복구와 GET 전환을 확인한다.
- 로그아웃 후 늦은 403 오류가 닫힌 상태를 덮지 않는지 확인한다.
