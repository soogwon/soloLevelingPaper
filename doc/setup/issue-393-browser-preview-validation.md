# #393 로컬 업로드 미리보기 브라우저 검증

## 대상과 환경

- 기준: main `ce52f3d02776b07b25df6f625cf250ab5ece7254`, 2026-11-15 검증.
- macOS Codex 내장 브라우저, 로컬 `http://127.0.0.1:8765`.
- `ui/remote-upload-preview`만 정적 제공. 제품 웹·Claude Desktop 검증이 아니다.
- 합성 파일 `slp393-browser-fixture.pdf`(49 bytes)의 이름·크기만 선택했다. 실제 PDF 파싱·업로드·외부 AI 요청은 수행하지 않았다.

## 남은 검증

- 실제 인증 웹 adapter, 소유권 검증, presigned PUT, 서버 완료 조회, 원자 접수 연결.
- 실제 PDF의 내용·크기·SHA 검증과 네트워크 실패·지연·응답 역전.
- 파일 선택 대화상자 자체의 취소, 파일 교체, Windows 브라우저, 화면 낭독기·모바일 레이아웃.
- 같은 선택 세대의 서버 응답 순서 보장. 현재 대역 관찰은 서버 revision 검증을 대체하지 않는다.

이 기록은 #393의 전체 완료 근거가 아니며 티켓은 열어 둔다.

## 2026-11-16 선택창 취소·기존 작업 복구 후속 검증

기준 main `af64094`에서 분기한 `fix/issue-393-file-picker-cancel` 수정본을
macOS Chrome의 로컬 정적 미리보기(`127.0.0.1:8768`)로 확인했다.
45 bytes 합성 PDF의 파일명·크기만 선택했다. 실제 업로드·동의 저장·AI 호출은 없다.

### 보완과 자동 회귀

기존 화면은 `change`와 별도 선택 취소 버튼만 처리했다. 실제 HTML 스크립트를
EventTarget 기반 DOM 대역에서 실행한 회귀 검사에서 선택창 `cancel` 이벤트 뒤
기존 파일·작업이 남았다(수정 전 35 통과/1 실패).
`cancel`도 공통 초기화 함수에 연결하여 파일 입력·선택 세대·의도·작업 조회 상태를 함께 비운다.
브라우저는 같은 파일을 다시 선택해도 `cancel`을 발생시킬 수 있으므로 이때도 초기화하며,
화면에 이 동작을 설명한다. 서버 작업을 취소하거나 삭제하는 동작은 아니다.

`node --test ui/remote-upload-preview/upload.test.mjs`: **36 통과, 실패·건너뜀 0**.
새 회귀 4개는 선택창 취소, 별도 취소 버튼, 파일 교체, 응답 유실 후 동일 작업 복구다.
기존 모델 회귀는 선택 변경 후 늦은 응답과 역전·중복 응답 거부를 검사한다.
DOM 대역은 네이티브 파일 선택창이나 실제 서버 통신의 검증을 대신하지 않는다.

## 인증 원격 업로드 HTTP 경계

최신 원격 업로드 저장 포트를 웹 세션 전용 HTTP 계약에 연결한다. 기존 기기 업로드
`/v1/papers/{paper_id}/uploads`를 재사용하거나 가짜 기기·로컬 버전 ID를 만들지 않는다.

- `POST /v1/remote-uploads/intents`: `Idempotency-Key`와 PDF 이름·크기·형식·SHA-256으로
  원격 paper/version 및 업로드 의도를 멱등 생성한다.
- `GET /v1/remote-uploads/intents/{intent_id}`: 응답 유실 뒤 소유자 범위에서 상태를 조회한다.
- `POST /v1/remote-uploads/intents/{intent_id}/prepare`: 서버 생성 임시 object key에만 사용할
  짧은 presigned PUT URL과 반드시 함께 보내야 할 헤더를 발급한다.
- `POST /v1/remote-uploads/intents/{intent_id}/complete`: 실제 객체의 크기·형식·PDF header·SHA-256을
  검사하고 검증된 최종 객체로 승격한다. 완료 재요청은 이미 확정된 결과를 반환한다.

네 경로는 인증된 `web_session`만 허용한다. 기기 자격은 기존 로컬 동기화 경로에만 쓰며,
타인 의도와 존재하지 않는 의도는 같은 `remote_upload_not_found`로 응답한다. 응답에는 owner ID와
object key를 넣지 않고 `Cache-Control: no-store`를 적용한다. presigned URL은 URL 자체가 권한인
bearer capability이므로 대화·일반 로그·티켓에 기록하지 않는다.

이 경계는 PDF 업로드와 서버 검증까지만 담당한다. 보관 동의·AI 전송 동의 발급, 검증된 의도의
처리 접수, 제품 웹 화면, 실제 R2·두 계정 스테이징 종단 검증은 후속 범위다. 링크 GET과 상태
조회는 업로드·처리 job·유료 provider 호출을 만들지 않는다.
