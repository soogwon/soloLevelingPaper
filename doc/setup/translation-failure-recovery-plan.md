# 부분 번역 실패 보완 계획

작성일: 2026-09-29

상태: 제안 단계. 이 문서는 보완 계획이며 재시도·복구 기능이 구현됐다는 의미는 아니다.

## 확인된 사례

Claude MCP를 통해 「Attention Is All You Need」를 등록한 뒤 기존 로컬 DB에서 다음을 확인했다.

| 항목 | 확인 결과 |
|---|---|
| 전체 청크 | 98개 |
| 번역 성공 및 게시 색인 포함 | 96개 |
| 번역 실패 | 2개, `provider_unavailable` |
| 실패 위치 | 청크 인덱스 2: PDF 1페이지, 인덱스 8: PDF 2페이지 |
| 작업 상태 | `ready`, 단계 `index` |

실패한 청크의 번역문 `text`는 NULL이며 한국어 검색 색인에서 제외됐다.
해당 청크를 원문으로 대신 검색하는 기능은 없다. 페이지 전체가 누락된 것은 아니지만,
실패한 구간에만 있는 내용은 현재 검색·답변의 근거로 사용할 수 없다.

## 현재 동작과 제약

- `ready`는 성공한 번역 청크의 벡터 저장·검증·게시가 완료됐다는 뜻이다.
  논문 전체의 번역 완료를 보장하지 않는다. 부분 실패는 작업의 `limitations`에 남는다.
- 번역 요청은 청크당 한 번이며 자동 재시도는 없다.
- `provider_unavailable`에는 연결 오류, 시간 초과, HTTP 오류, 미완료·거절·형식 오류 등이
  함께 들어간다. 따라서 이를 단순히 “번역 서비스에 연결되지 않았다”로 단정하면 안 된다.
- 이번 저장 기록만으로 실패한 두 요청의 정확한 원인을 소급해서 확인할 수 없다.
- 게시되지 않은 실패 작업을 재등록하면 기존 성공 번역을 보존하며 누락 구간을 다시 처리할
  수 있지만, 이미 게시된 `ready` 결과는 같은 파일을 등록해도 그대로 재사용한다.
- 게시 후 누락 번역을 채우고 색인을 갱신하는 전용 기능은 없다.

## 1차 보완: 게시 전 실패 진단과 제한적 재시도

### 안전한 오류 분류

번역 제공자 예외에 허용된 원인 코드와 재시도 가능 여부를 구분해 전달한다.
기존 `provider_unavailable` 계약과의 호환을 확인하고, DB 진단 정보 확장은 별도 검토한다.
API 키, 요청 헤더, 원문, 제공자 응답 본문은 진단 로그나 사용자 응답에 남기지 않는다.
오류를 숨기기 위해 모든 원인을 연결 실패로 표현하지 않는다.

| 원인 | 제안 처리 |
|---|---|
| 연결 오류·시간 초과 | 제한적으로 재시도 |
| 일시적 호출 제한 | 재시도 가능한 경우만 대기 후 재시도 |
| 일시적 서버 오류 | 제한적으로 재시도 |
| 인증·권한·잘못된 요청·사용량 소진 | 같은 요청을 자동 반복하지 않고 설정 확인 안내 |
| 거절·응답 형식 오류·출력 잘림·빈 번역 | 별도 원인으로 기록하고 원인별 정책 검토 |

`provider_unavailable` 전체를 무조건 재시도하지 않는다. HTTP 상태만으로 원인이 불명확한
경우 안전하게 분류할 수 있는 제공자 오류 코드의 허용 목록을 검토한다.

### 재시도 상한

- 초기 제안은 최초 호출을 포함해 최대 3회다. 설정값과 기본값은 구현 시 확정한다.
- 지수적으로 늘어나는 대기 시간과 작은 무작위 지연을 사용한다.
- 제공자가 재시도 대기 시간을 알려주면 유효성을 검사하고 상한 안에서 반영한다.
- 청크별 시도 횟수뿐 아니라 누적 대기 시간과 작업 기한도 제한한다.
- 시간 초과 후 재호출은 제공자 측 중복 처리·추가 비용 가능성이 있으므로 무제한 반복하지 않는다.
- 마지막 시도도 실패하면 기존처럼 실패를 기록하고 부분 게시 정책을 적용한다.
- 이미 성공한 청크는 다시 번역하지 않는다. 인증 등 전역 오류에서 나머지 청크까지 계속
  요청할지는 배치 중단 정책으로 별도 결정한다.

이 보완은 이후 등록 요청의 일시적 실패를 줄이기 위한 것이다.
이미 게시된 이번 2개 누락 청크를 자동 복구하지는 않는다.

## 2차 보완: 게시된 부분 색인의 복구

기존 context와 근거가 번역·색인 버전을 참조하므로 게시된 번역문과 벡터를 즉시 덮어쓰지 않는다.
아래 사항을 먼저 합의한 뒤 별도 기능으로 구현한다.

1. 명시적인 복구 요청과 작업 ID를 정의하고 중복 실행을 방지한다.
2. 실패 청크만 번역하되 기존 번역 설정을 유지할지, 새 리비전으로 처리할지 결정한다.
3. 기존 성공 번역을 재사용할 수 있는 리비전 저장 구조를 정의한다.
4. 복구 결과를 별도 색인으로 검증한 후 게시하고, 실패 시 기존 검색 결과를 유지한다.
5. 기존 context·근거는 이전 데이터를 계속 참조할지, 새 context로 전환을 안내할지 결정한다.
6. 현재 논문 버전당 게시 색인 하나라는 제약과 청크 번역 저장 구조의 확장 범위를 검토한다.
7. 중단·동시 복구·미게시 벡터 정리와 복구 후 제한 사항 갱신을 검증한다.

단순 재등록, DB 기록 삭제 또는 Chroma 데이터 직접 수정은 복구 절차로 제공하지 않는다.
현재 데이터의 복구에는 위 정책과 저장 구조 검토가 선행돼야 한다.

## MCP 사용자 안내

권장 안내 예시:

> 논문을 사용할 수 있습니다. 전체 98개 구간 중 96개가 번역·검색 준비됐고,
> PDF 1페이지와 2페이지의 일부 구간은 번역 실패로 검색에서 제외됐습니다.
> 해당 구간에만 있는 내용은 답변 근거에 포함되지 않을 수 있습니다.
> 현재 기록만으로 번역 실패의 정확한 원인은 확인할 수 없습니다.

검색 결과에 정보가 없다는 이유만으로 논문 전체에 그 내용이 없다고 단정하지 않는다.
전체·성공·실패 청크 수와 누락 페이지를 구조화된 MCP 응답으로 제공할지는 별도 계약으로 검토한다.

## 예상 영향 범위와 검증

- 번역 제공자·예외 계약: 안전한 원인 분류, 재시도 여부와 대기 정책.
- 번역 서비스·등록 작업자: 성공 결과 보존, 최종 실패 집계, 배치 중단 정책.
- 저장소·리비전·색인: 게시 후 복구 단계에서 변경 범위 협의 필요.
- MCP 상태 응답·문서: 부분 완료와 검색 제외 범위를 정확하게 안내.

자동 테스트는 HTTP와 대기 함수를 대체해 외부 호출 없이 수행한다.
일시적 실패 후 성공, 재시도 상한 소진, 재시도 불가 오류, 대기 상한,
성공 청크 재사용, 비밀 정보 비노출을 확인한다.
부분 게시 결과의 청크 수·limitations와 재등록 시 기존 결과 재사용도 검증한다.
게시 후 복구 테스트는 리비전 정책 확정 후 기존 context·근거 보존까지 포함한다.

실제 호출 검증은 자동 테스트와 분리하고 소량의 허용된 샘플로 진행한다.
