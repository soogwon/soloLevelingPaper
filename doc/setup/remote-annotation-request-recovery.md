# #502 원격 메모 요청 키 복구 — C 내부 포트

기준 main: `af64094`. A·B의 #371 의견은 로컬 DB + context 범위의 생성 멱등성 계약이다.
이 모듈은 원격 연결에 필요한 C의 키 보관·복구 경계를 준비한다. 공개 wire 계약이나
실제 원격 메모 생성 API를 새로 정의하지 않으며 제품 카드에는 아직 연결하지 않는다.

## 제공하는 동작

`createRemoteAnnotationRecovery`는 storage, Web Crypto, Web Locks, currentScope를 받는다.
`currentScope()`의 service·owner·session은 인증 adapter가 제공해야 한다.
사용자 입력, 모델 인자, 검증하지 않은 JWT payload를 인증 범위로 사용하지 않는다.
service는 안정적인 배포/저장소 식별자, owner는 인증된 내부 사용자 식별자,
session은 로그아웃·같은 계정 재로그인 때도 바뀌는 현재 세션 세대다.

- 저장 공간은 service + owner의 SHA-256으로 구분한다. 세션 세대는 영속 키에 넣지 않아
  같은 계정의 재로그인 후에도 같은 입력을 명시적으로 다시 준비하면 기존 키를 찾는다.
- 요청의 context_id와 생성 입력 전체로 키를 찾는다. 객체 속성 순서만 정렬하며
  본문·공백·유니코드·배열 순서·생략 필드를 임의 변경하지 않는다.
- 같은 원격 범위의 구형 origin 생략 미확정 요청은 기존 helper의 정책대로 생략을 유지한다.
  비범위 로컬 키를 원격 범위로 가져오지 않는다.
- `prepare(request)`는 기본적으로 복구만 한다. 키가 없으면 null이며, 기존 기록을 확인하고
  신규 저장을 명시한 경우에만 `{allowNew:true}`로 키를 발급한다. 본문 기반 자동 병합은 없다.
- 같은 origin의 Web Locks로 여러 카드의 키 생성·저장을 직렬화한다. API 미지원 또는
  저장 실패 시 잠금 없는 전송으로 우회하지 않는다. 별도 origin·기기는 이 잠금을 공유하지 않는다.
- 반환된 `ticket.send(sender)`는 전송 직전 키가 여전히 있는지, 계정·세션이 같은지 검사한다.
  응답 도중 계정이 바뀌면 결과를 버린다. sender는 준비 당시 인증 주체에 결합된 전송 함수를
  사용해야 하며, 내부 대기 후 다른 계정의 자격으로 요청을 보내면 안 된다. 이미 전송한 요청을
  이 모듈이 회수하지는 못한다. 서버는 owner 경계를 따로 검사해야 한다.
- 정상 응답의 대상·ID·현재 revision을 검증한 뒤에만 호출자가 `ticket.confirm()`을 부른다.
  send 자체는 성공 여부를 추정해 키를 삭제하지 않는다. 오류·유실·삭제·충돌 응답에는 키를 유지한다.
- 미확정 입력을 사용자가 동일하게 다시 제공해야 한다. 초안·본문·인용문·토큰은 저장하지 않는다.
  저장하는 해시와 키는 익명화나 인증 수단이 아니며, 서버에서 소유권을 반드시 재검증한다.
- 원시 오류는 `ANNOTATION_RECOVERY_UNAVAILABLE`로 감춘다. UI는 목록 확인·재로그인 안내로
  연결해야 하며 이를 성공이나 새 키 발급 조건으로 처리하면 안 된다.

이 경우 null을 반환하고 기존 목록 확인으로 안내해야 한다. 여러 기기/호스트 사이의 복구는
서버에 보관한 생성 의도를 인증 후 조회하는 별도 계약이 필요하다. 임의의 본문 검색으로
기존 요청 키를 추정하거나 새 키로 자동 재접수하지 않는다. 원격 후속 범위는 #502에서 관리한다.

## #502 인증 연결 고정 (2026-11-16)

`createAuthenticatedAnnotationRecovery`는 기존 키 복구 helper 위에 인증 연결 경계를 추가한다.
기존 `createRemoteAnnotationRecovery`는 하위 내부 포트로 유지하며, 원격 연결에는 새 경계를 사용한다.
실제 서버 API·인증 adapter나 제품 카드 연결을 구현한 것은 아니다.

- `getConnection()`은 신뢰할 수 있는 인증 adapter가 제공한다. 같은 로그인 동안 안정적인
  연결 객체 `{service, owner, session, send}`를 반환하고 로그아웃 시 null, 재로그인 시 새 객체를 반환한다.
  단순 토큰 갱신으로 로그인 세대를 바꾸지 않는다면 같은 연결을 유지할 수 있다.
- 준비 시 연결 객체·범위·send 함수를 잡아 둔다. 반환된 `ticket.send()`는 sender를 외부에서
  받지 않으며 그 연결의 함수만 사용한다. 원시 인증 토큰을 이 helper나 저장소에 넘기지 않는다.
- 키 준비·전송·응답·확정 시 현재 연결의 동일성과 service/owner/session 및 함수 변경을 검사한다.
  다른 계정으로 갔다 돌아와도 새 로그인에는 새 객체·세대가 필요하다.
- 연결의 `send(payload, {assertCurrent})`는 **대기/자격 갱신 뒤 실제 네트워크 전송 직전**
  `assertCurrent()`를 호출해야 한다. 연결 당시의 인증 주체로만 전송하고, 전역 최신 계정의 자격으로
  바꿔 보내면 안 된다. 자동 재전송이 있다면 매 전송 전에 같은 검사가 필요하다.
  helper는 adapter 내부 대기나 전송을 강제 취소하지 못하므로 이 계약을 실제 adapter 테스트로도 검증해야 한다.
- 이미 전송한 요청의 취소나 서버 저장 취소를 보장하지 않는다. 세션이 바뀐 뒤 온 응답은 버리고
  미확정 키를 보존한다. 같은 계정 재로그인 후 동일 입력을 다시 준비하면 같은 키를 복구한다.
- 응답 대상·ID·revision 검증과 `confirm()` 호출은 실제 응답 계약 확정 뒤 연결한다.
  키 유실 시 자동 새 키 발급이나 본문 검색으로 복구하지 않는 기존 규칙은 유지한다.

새 회귀는 인증 연결 고정, 로그아웃·연결 교체·범위/함수 변조, 대기 중 계정 전환의 전송 0회,
늦은 응답 폐기와 재로그인 복구, 연결 조회 오류 비노출을 검사한다. 원격 복구 테스트는 기존 15개에
7개를 추가해 22개가 통과했다. 입력/구형 입력 해시 계산 중 연결이 바뀌어도
키를 저장하지 않도록 저장소 접근 직전 재검사를 추가했다. 전송 전 키 재조회 도중
연결이 바뀌면 sender 호출 없이 기존 키를 보존한다. 상세 UI 전체 회귀는 151개 통과(실패·skip 0)했다.
합성 adapter 검증이며 실제 인증·서버 멱등성·여러 기기 복구 증거는 아니다.

A의 원자 생성/복구 조회 및 B의 입력 동일성 계약이 확정되면 인증 adapter, 응답 검증, 제품 카드 순으로
연결한다. A/B 서버 파일은 이번 변경에 포함하지 않으며 #502는 미완료 상태로 유지한다.

## 제품 카드 연결 점검 (2026-11-16, #375 / #499)

- `main.js → mountDetailApp → prepareAnnotationRequest → create_annotation`은 제품 경로다.
  같은 origin의 저장 공간과 같은 입력이 남아 있으면 미확정 키를 재사용한다.
  초안을 자동 복원하는 기능은 아니며 사용자가 같은 입력을 다시 제공해야 한다.
- 저장 공간에 키가 없으면 기존 기록 확인과 명시적인 신규 생성 확인을 요구한다.
  새 시크릿 origin·저장 공간 유실·다른 기기에서 새 키로 자동 제출하지 않는다.
- 성공 응답의 context, 종류, ID, 본문과 양의 안전 정수 revision을 검사한 뒤 키를 지운다.
  revision 누락·무효 응답은 미확정으로 남겨 같은 키로 다시 확인할 수 있게 한다.
  재사용 응답은 수정된 현재 본문과 revision을 반환할 수 있으므로 최초 본문 일치를 강제하지 않는다.
- `createRemoteAnnotationRecovery`는 여전히 제품 카드에서 호출하지 않는다.
  현재 MCP App 연결만으로 인증된 service/owner/session을 알아낼 수 있다고 가정하지 않는다.
  원격 생성 API 및 인증 adapter 계약 없이 로컬 context나 모델 인자로 계정 범위를 만들지 않는다.
- #499는 A의 실제 읽기 상태 API 인증 거부 검증 문서다. 요청 키 복구 구현이나
  원격 메모 API 계약을 추가한 PR이 아니며, 실제 completed의 지연 전송·동일 operation 재생과
  메모 API 불변 검증은 별도로 남아 있다.

이번 C 보완은 기존 제품 카드의 응답 확정 경계다. 원격 계정 복구·여러 기기 복구를
구현한 것으로 간주하지 않는다. 실제 Desktop 검증 결과는 아래와 같다.


### 실제 macOS Desktop 오류 응답 주입 검증

2026-11-16, macOS 26.7.1 arm64 / Claude Desktop 5.11492.5의 일반 대화에서
이 브랜치의 제품 상세 카드 번들과 합성 SQLite DB를 사용했다. 임시 launcher가 실제
생성 처리 이후 첫 create_annotation 응답의 revision만 제거했다. 테스트 장치는
저장·키 발급 로직을 바꾸지 않았으며 별도 임시 경로에 두었다.

1. 카드에 합성 메모를 입력하고 신규 생성 확인 후 저장: DB 1건, 카드에서는
   저장 결과 미확정 안내 및 저장 버튼 비활성화를 확인했다.
2. 같은 대화에서 상세 카드를 재조회하고 동일 본문을 입력했다. 신규 생성 확인 없이
   저장했으며 실제 도구 요청 2회의 request_key가 같았다. DB와 카드 목록은 1건 유지됐다.
3. 정상 응답 뒤 같은 본문을 다시 입력해 저장하면 이전 요청 키 없음 안내로 차단됐다.
   생성 도구 호출 수는 2회 그대로여서 정상 확정 후 키 정리도 확인했다.
4. 임시 MCP 연결 제거 후 원래 설정과 동일함을 확인하고 Desktop을 재시작했다.

UI 139개 및 생성 멱등성·MCP·stdio 35개 테스트 통과. 이번 실기 검증은 같은 origin의
카드 재조회 복구이며, 앱 재시작·새 시크릿 origin·원격 계정·여러 기기 복구 증거는 아니다.
실제 논문·외부 유료 API·서버 동기화는 사용하지 않았다.

읽기 상태·자동 재시도·HTTP 조회·실제 stdio·MCP→동의/outbox→HTTP 계약이다.
HTTP 검증의 인증과 서버 저장소는 대역이며 실제 staging 격리 검증을 대신하지 않는다.
처음에는 로컬 fastapi 미설치로 수집/실행이 실패했으며 임시 경로에 개발 의존성을
설치한 뒤 전체를 다시 실행했다. 최종 실패·skip은 없고 의존성 폐기 예정 경고 1건이다.

이번에 일반 대화의 같은 origin·저장 공간을 유지한 재시작 증거를 추가했다.
새 시크릿 origin·저장 공간 유실·원격 계정 전환·여러 기기 복구와 원격 adapter 연결은
여전히 남는다. #375의 실제 학습 시작/추가 질문, 늦은 완료·재전송, 실제 서버의

검증한 환경과 미검증 환경을 구분하며, 모든 플랫폼에서 동일한 실기 검증을 완료했다고
표시하지 않는다.

## 서버 복구 내부 포트 보완 (2026-11-18, #502)

기존 원자 생성에 이어 `PostgresRemoteAnnotationStore`에 아래 내부 포트를 추가한다.
기기 동기화 upsert와는 별개이며 HTTP/MCP 도구를 등록하거나 권한을 활성화하지 않는다.

| 포트 | 입력 | 결과 |
| --- | --- | --- |
| `lookup_request` | 인증 owner/service/context + 정확한 request key | 현재 메모·revision, 원장 상태, `recovery=exact`; 없거나 논문 삭제/범위 불일치이면 None |
| `recover_request` | 같은 인증 범위 + 전체 최초 생성 입력 | 같은 지문·미확정 요청이 정확히 1개면 키와 현재 상태, `recovery=unique_unconfirmed`; 0개 None, 2개 이상 `annotation_recovery_ambiguous` |
| `confirm_request` | 같은 인증 범위 + 키 + 응답 annotation ID/revision | 현재 ID/revision이 일치하면 `client_confirmed_at`을 최초 한 번 기록하고 True; 불일치/범위 없음은 False |

입력 지문 v1을 재사용하며 본문 공백·Unicode·배열 순서를 변경하거나 부분 검색하지 않는다.
수정된 메모의 재생은 **최초 입력 지문**으로 찾고 현재 본문·revision을 반환한다.
삭제된 미확정 요청도 후보에 포함하여 새 키 자동 발급으로 삭제를 우회하지 않도록 한다.
삭제 상태 응답은 본문·구간을 비워 반환한다. 확인된 요청은 자동 복구 후보에서 제외하지만
정확한 키 조회는 가능하다. 확인은 생성/수정/삭제를 하지 않는다.

세 포트는 생성·삭제와 같은 부모 논문 우선 잠금 순서를 사용한다. tombstone이 먼저 확정되면
뒤따르는 조회/확인을 거부한다. 조회는 메타데이터를 수정하지 않지만 행 잠금이 필요하므로
향후 제한 역할 설계에서 잠금 권한과 수정 방어를 함께 검토해야 한다. 조회 후보는 SQL에서
정확한 키 1개 또는 같은 지문 최대 2개로 제한한다.

### 검증 및 연결 경계

실제 로컬 PostgreSQL에서 새 store의 응답 유실 복구, 현재 revision 반환, stale 확인 거부,
반복 확인 시각 보존, owner/service/context 교차 접근 거부, 모호한 후보 거부,
메모 삭제·논문 tombstone, 확인/삭제 경합을 검증한다. 실제 사용자·staging 자격은 쓰지 않는다.

이 저장소 포트의 owner/service는 **신뢰된 서버 인증 adapter 전용 인자**다. 모델·카드 입력을
직접 넘기는 공개 API로 사용하면 안 된다. 공개 transport에서는 아래가 추가로 필요하다.

1. 검증된 principal→owner와 서버 고정 논리 service 연결, 쓰기 권한/동의 경계 확정.
2. create/exact/recovery/confirm의 안전한 wire 오류와 응답 schema, 제한 DB 역할.
3. C adapter가 현재 인증 연결·context·키·ID·revision·상태를 검사한 뒤 서버 확인 호출.
   확인 응답 유실 시 같은 확인을 다시 호출하며, 실패하면 로컬 키를 지우지 않는다.
4. 서버 확인 후 계정이 바뀌었으면 로컬 확정도 거부. 미존재/모호함/삭제는 자동 새 키 생성 사유가 아니다.
5. 실제 두 계정·다른 기기·Desktop의 응답 유실 검증은 별도 승인 후 수행.

앱에 아직 연결되지 않은 내부 포트만으로 #502를 종료하지 않는다. DB migration·staging 설정·
실제 외부 전송은 이번 변경에 포함하지 않는다.

## 원격 수신 확인 카드 (#580 / #502)

`show_remote_annotation_recovery(context_id, request_key)`는 기존 키의 현재 결과만
조회하는 MCP App이다. 본문을 텍스트로 표시하고 사용자가 확인 버튼을 눌러야
`confirm_remote_annotation_card`가 서버의 동일 ID/revision 수신 확인을 호출한다.
확인 응답 유실·충돌에서는 확정을 추정하지 않고 같은 키로 다시 조회한다.
삭제 결과는 본문/구간을 표시하지 않으며 신규 생성 도구를 호출하지 않는다.

A: 카드 연결값은 검증된 access token을 HMAC 키로 하고 서버 service·owner·context를
결합한다. 토큰이나 사용자 ID는 카드에 제공하지 않는다. 연결값은 인증 자격이 아니며
매 호출의 OAuth/owner/scope 검사를 대체하지 않는다. 토큰 갱신·계정 변경 뒤 과거
카드의 조회/확정은 차단되므로 새 카드를 열어야 한다. 이 값은 영속 저장하지 않는다.
동일 토큰을 재사용하는 로그인 세대까지 구분하는 기능은 아니다.

B: 서버의 현재 annotation ID·revision·맥락·요청 키와 삭제 상태를 검사한다.
원문/번역 인용은 저장 값을 그대로 표시하며 재검색·생성을 하지 않는다.

C: 새 호스트 입력·취소·페이지 종료는 이전 결과와 확인 동작을 무효화한다.
카드 표시나 조회 성공만으로 자동 확인하지 않는다. 호스트가 앱을 지원하지 않으면
기존 텍스트 조회/확정 도구를 사용할 수 있다. 호스트가 계정 변경을 통지하지 않으면
이미 표시된 내용을 즉시 지울 수 있다는 보장은 없으며, 이후 서버 요청은 현재
토큰과 연결값을 대조해 차단한다.

이번 변경은 정확한 기존 요청 키를 알고 있는 경우의 조회·확정 연결이다. 새 메모 작성
카드, 저장 공간 소실 시 전체 입력으로 후보를 찾고 선택하는 UI, 실제 원격 Desktop의
오류 주입·두 계정 종단 검증은 남는다. 이 카드만으로 #580/#502를 닫지 않는다.

검증: UI 161개, 서버·인증/이미지 계약 21개, 별도 로컬 PostgreSQL의 카드·기존 복구
회귀 15개 통과. 저장 응답 유실 뒤 같은 ID 조회, 다른 기기의 revision 변경 후 stale
확인 거부, 재조회 후 확인, 확인 응답 유실 후 반복해도 최초 확인 시각과 기록 1건 유지,
토큰 변경 후 과거 카드 확인 거부를 확인했다. 실제 staging/Claude 실기 결과는 아니다.
