# #119 C 요청 키 복구 계약 검토

2026-11-03 · 기준 main `2230865` · macOS · Python 3.12

## 결론

호출자가 전송 전에 키를 보관하고 서버가 그 키로 조회를 제공하면, 최초 접수 응답의
execution ID 없이도 조회할 수 있다. 실제 MCP 메모리 전송으로 이 조건을 검증했다.
현재 제품에는 이 기능이 없으며 Claude Desktop이 키를 영속 보관한다는 검증도 아니다.
이번 산출물은 독립 실험과 C 협의안이다. 제품 도구·DB·Desktop 설정을 변경하지 않는다.

## 현재 코드와 호스트 경계

- `src/solo_leveling/interfaces/mcp/server.py`의 `ask_paper`에는 request_key 입력과 실행 조회 도구가 없다.
  기존 호출은 동기 응답 계약이며 시간 초과 후 자동 재호출하지 않도록 안내한다.
- PR #144 (`2c634abe`)의 `ui/quiz/quiz.js`는 제출 전에 UUID를 만들고 같은 카드의
  재시도에서 원래 키·답안을 사용한다. 보관 위치는 함수의 메모리 변수다.
  화면 재생성·채팅 종료·Desktop 재시작 이후까지 보존하는 근거가 아니다.
- MCP 전송 요청 ID, 안전 진단 request_id, 논리 실행 request_key, 서버 execution_id는
  목적과 수명이 다르다. 전송 ID나 진단 ID를 재조회 키로 대신 사용하지 않는다.
- 채팅 모델이 이전 도구 인자의 키를 기억하거나 iframe 저장소가 계속 유지된다고
  가정하지 않는다. 호스트별 키 보존 경로가 없으면 재시작 복구는 미지원으로 표시해야 한다.

## 합성 실험

저장소 루트에서 개발 의존성이 설치된 Python으로 실행한다.

```sh
PYTHONPATH=src python -m pytest mini-projects/c-request-key/test_request_key_probe.py tests/unit/mcp/test_ask_cancellation.py -q
```

결과: **7 passed** (실험 1개, 기존 취소 회귀 6개).

실험 도구 `probe_submit`, `probe_lookup`은 제품 공개 이름 제안이 아니다.
외부 API·모델·사용자 DB 없이 FastMCP, MCP ClientSession, 임시 호출자 파일을 사용한다.

1. 호출자가 UUID와 합성 context를 임시 파일에 기록한 뒤 전송한다.
2. 대역 서버는 접수 기록을 만들고 이벤트로 최초 응답을 보류한다.
3. 최초 응답이 아직 없는 상태에서 키와 context로 조회하여 접수 상태와 execution ID를 얻는다.
4. 다른 context와 없는 키의 조회는 같은 NOT_FOUND 내용을 반환한다.
5. 늦은 접수 응답은 복구 정보로 사용하지 않는다. 새 MCP 클라이언트를 열고
   임시 파일의 키로 재조회한다. 제출 호출은 총 1회다.

이는 응답을 받지 못한 호출자 관점을 재현한다. 패킷 손실·Desktop 60초 제한을
직접 재현한 것은 아니다. 서버는 같은 메모리 대역을 사용하므로 서버 재시작·DB 내구성·
동시 접수 원자성·접근 통제 구현을 검증한 것으로 해석하지 않는다.
호출자 파일도 합성 키 보관 조건을 보여주는 장치이며 제품용 저장소가 아니다.

## C 권장 호출 흐름 — 미합의 제안

1. 사용자 의도에 따른 새 요청에서 호출자가 키를 생성하고 전송 전에 보관한다.
   보관 실패 시 제출을 시작하지 않는다. context와 보존 기한을 함께 관리하고
   키·질문·입력 해시를 진단 로그에 넣지 않는다.
2. 접수는 짧게 반환하되, 접수 응답 자체가 유실될 수 있음을 전제로 한다.
   accepted는 완료가 아니며 접수 이후 실제 작업 인계 주체는 A/B와 별도 확정한다.
3. 응답 유실 시 원래 context와 키로 조회한다. 조회는 생성·재접수·재실행을 유발하지 않는다.
   폴링 간격·최대 대기·사용자 중단 정책은 호스트 통합 시 정한다.
4. NOT_FOUND는 미접수, context 불일치, 기록 만료 등을 단정하지 않는 응답이다.
   새 키로 자동 제출하지 않는다. 같은 키 재접수도 중단·만료 정책 합의 후에만 허용한다.
5. succeeded는 최초 공개 응답의 값·배열 순서·null·ID를 그대로 반환한다.
   답변의 partial/insufficient_evidence와 실행 실패를 구분한다.
6. 기존 `ask_paper`의 입력과 동기 반환은 유지한다. 새로운 접수·조회 도구는
   합의 후 별도 추가하며 기존 호출에 몰래 비동기 실행이나 자동 재시도를 적용하지 않는다.

Desktop 경로 후보는 별도 질문 카드에서 호출 전 키를 생성·보관하는 방식이다.
현재 카드 메모리만으로는 같은 화면 내 복구만 가능하다. 재시작까지 지원하려면
호스트 저장 기능의 실제 지속성 또는 C가 소유하는 로컬 호출자 저장소가 필요하다.
서버에서 키를 발급해 주는 준비 호출만 추가해도 그 준비 응답이 유실될 수 있으므로
최초 응답 유실 문제를 완전히 해결했다고 볼 수 없다.

## A/B에 확인할 사항

| 쟁점 | C 의견과 확인 요청 |
| --- | --- |
| interrupted 재접수 | A 최초안은 새 키로 명시적 재요청, 최신안은 같은 키 자동 이어 실행이다. C는 같은 키 조회·재접수로 자동 실행하지 않는 쪽을 권장한다. 하트비트 만료는 이전 API 실행 중단 증거가 아니다. 새 키 실행도 중복 비용 가능성을 알리고 사용자 의도를 확인해야 한다. |
| 소유권과 하트비트 | 늦은 DB 쓰기 차단은 외부 API 중복 호출 차단과 다르다. accepted 인계 전 종료·running 소유권 상실·서버 재시작을 구분하고 실제 실행자 생존 판단과 인계 규칙을 합의한다. 10초/60초는 아직 제안값이다. |
| 키 보존 30일 | 키 기록을 삭제한 뒤에는 옛 키가 새 요청으로 보일 수 있다. 만료 표시를 장기 보존하거나 서버가 검증 가능한 키 유효기간을 두는 등 거부 규칙이 필요하다. 조회 NOT_FOUND만으로 자동 재실행하지 않는다. 7일/30일은 확정값이 아니다. |
| context 범위 | 키+context 일치 확인에 동의한다. 이는 로컬 데이터 범위 검사이며 사용자 인증을 대체하지 않는다. 원격형은 인증된 소유 범위까지 필요하다. 충돌 응답에서도 다른 context의 존재가 드러나지 않게 한다. |
| 입력 동일성 | B의 effective question·기본값·필터 정렬·비교 규칙 버전에 동의한다. 키만 보관하면 조회는 가능하지만 재접수 입력을 복원할 수는 없다. 입력 복원 없이 모델이 원 질문을 재구성해 재제출하지 않는다. |
| 상태 응답 | failed/interrupted/EXPIRED/NOT_FOUND를 구분하고 사용자의 다음 행동을 정한다. 전체 결과·오류 응답 모델과 도구 이름은 아직 확정하지 않는다. |

## 다음 구현과 완료 조건

- C: 호스트별 호출 전 키 보관 방식·호환 범위 확정. 실제 Desktop에서 최초 응답 유실,
  카드 재생성, 앱 재시작 후 동일 키 복원, 키 보관 실패 경로를 별도 검증한다.
- A: 합의한 저장소·동시 접수·소유권·원자적 결과 저장·만료 거부 규칙 구현.
- B: 같은 저장 트랜잭션에 근거와 최초 공개 응답 연결, 입력 동일성 보장.
- 공동: 실행 중 조회·최초 응답 유실·재시작·결과 만료·context 격리·늦은 쓰기를 통합 검증한다.

M1에서는 계약 검토까지, 영속 실행·조회 도구는 공동 후속 구현이라는 A/B 제안을 따른다.
이번 결과만으로 #119를 종료하지 않는다. 실제 API 호출이나 Desktop 설정 변경은 수행하지 않았다.
